# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state: playable

The full loop works — look, move, jump, shoot, enemies spawn and close in, contact damage, death, restart. There are no `TODO` stubs left. Difficulty ramps by shortening the spawn interval from `ENEMY.spawnInterval` to `ENEMY.spawnIntervalMin` over `ENEMY.rampDuration`.

On top of that, `rounds.js` runs the round structure: clear `ROUNDS.killsPerRound` floaters, fight a boss alone in an empty arena, next round. There are two enemy tiers (floater and boss) and no more planned — the five bosses in `bosses.js` are one tier wearing five faces, not five tiers.

Not implemented (deliberately, not oversights): weapon variety, persistent high score, mobile/touch controls. **`ROUNDS.speedStep` is the only thing that scales with the round** — a flat +0.5 per round (1.0x, 1.5x, 2.0x, …) on floater speed, boss speed, *and* the floater spawn rate, so one number covers both how fast they come and how many. Boss health and `killsPerRound` deliberately don't scale, so every round is the same length and the boss takes the same 50 shots; that's a balance decision, not a missing feature.

## Commands

```bash
npm run dev      # Vite dev server on http://localhost:5173/, hot reload
npm run build    # production bundle into dist/
npm run preview  # serve the built bundle
```

`assets/` holds every asset file in the repo: `images/` the five boss portraits, `audio/doom.mp3` the music bed. They're reached with ES imports from `bosses.js` and `sound.js`, never literal paths, so Vite emits them into the bundle and rewrites the URLs against the base. That's why they don't need to live in `public/`, and it's the whole reason the deploy still works with assets in play.

**`vite.config.js` exists only to set `base: './'`, and that line is load-bearing for the deploy.** GitHub Pages serves the game from a `/DoomSlop/` subpath; Vite's default base of `/` emits `/assets/index-xxx.js`, which resolves above the project and 404s. Relative is used rather than a hardcoded `/DoomSlop/` so the base survives a repo rename and — more importantly here — so the dev server stays at the root, where every headless driver navigates. Don't "tidy" it to an absolute base: `npm run dev` and `npm run preview` both serve from the root, so the failure is invisible locally and only shows up on the live site.

**There is no test suite, linter, or formatter configured.** Don't invent `npm test` — it will fail. Verification is done by running the app (see below).

### Node on PATH

Node 24 LTS lives at `C:\Program Files\nodejs`, but an agent shell's environment may predate the install and not have it on PATH. If `node: command not found`, prefix it:

```bash
export PATH="/c/Program Files/nodejs:$PATH"
```

The full-screen shot is the best check of all: with enemies at known bearings, the dots inside the cone and the enemies visible in the 3D view have to be on the same sides, which no amount of self-consistent minimap math can fake.
- `%TEMP%\doomslop-rounds.mjs` — 71 assertions on the round loop: announcement order and that nothing flashes behind the click-to-start overlay, the field wipe at `killsPerRound`, the boss's size/health/score/identity, the health bar's screen position relative to the boss's head, boss contact damage arriving on a cooldown rather than every frame, the `KILLS n/25` progress field (counts shot kills, ignores contact deaths, hidden for the boss fight, back to zero next round), the health refill (a damaged player is carried through the wipe and the whole boss fight, and only topped up by the killing blow — plus a floater kill that must *not* heal), the per-round speed and spawn-rate growth, and that a retry returns to round 1.

The roster is hardcoded in the driver rather than read out of the game, so a dropped or renamed image fails instead of being agreed with, and 80 `spawnBoss()` draws have to produce all five names and nothing else.

That is exactly how it broke when the halo was added. It now also asserts the portrait is the *last* child, which is what stops the additive halo painting over the face.
  - Two screenshots for the parts assertions can't judge: the `BOSS ROUND` flash with a name under it, and a close-up of the orb. Whether the ring of purple left around the face still reads as the boss underneath is the entire justification for `BOSS.portraitScale` being under 1, and no number tells you that. Note `rounds.bossIdentity` is null by the time the screenshot section runs — the retry test reset it — so the flash shot draws its own name through `spawnBoss()`.
  - The speed checks **measure displacement** — a lone enemy's position over ~450ms of real frames, timed off the rAF timestamp — rather than reading `speedScale` back. Asserting the multiplier is 1.5 proves nothing about whether `update()` multiplies by it. One frame of travel is 2-3% of that window, so they compare against a percentage band, and the *measured* case uses round 5 (3.0x) where the bands can't overlap; round 2's exact `1 + speedStep` is checked as a pushed value and as flash text instead. It also measures the boss, since one multiplier serving both tiers is the thing that could silently regress.
  - The ladder is checked as **equal differences, not equal ratios**, plus one assertion that round 3 is `1 + 2 * step` and *below* what compounding would give. Round 2 is identical under both formulas, so it's round 3 where a reintroduced `**` would show, and nothing else in the suite would notice.
  - The spawn-rate check **counts real spawns** — it times how long a fixed 12 take at scale 1 and again at round 5 — because `currentSpawnInterval()` returning the right number proves nothing about whether the spawn timer is actually fed from it. Two things make that measurable: it flattens the within-round ramp by setting `ENEMY.spawnInterval = spawnIntervalMin` through `__game.config` (restored afterwards), or `elapsed` advancing between the two runs moves the interval underneath the comparison; and it keeps that flat interval **well above a frame time** (0.4s), because the spawn timer is decremented once per frame and reset to a whole interval, so each spawn really takes `ceil(interval / dt)` frames. At 0.1s and ~95fps that rounding alone costs 5% of the rate at 1x and 13% at 3x, which reads as the scaling being weaker than it is — it's what made the ratio come out 2.63 against an expected 3.00. Timing a fixed count also avoids the ±1 discretization a fixed window leaves on the slower run. The reset ordering has its own assertion in the restart section: after dying in round 2 and clicking retry, `spawnTimer` has to be a full `ENEMY.spawnInterval`. The wrong order leaves it a third short — invisible unless measured, and that one check is the only thing that catches it.
  - The layout of the two-line flash is checked with `getBoundingClientRect()`: the speed line below the title, centered on it, smaller than it, and above the crosshair. A stylesheet slip that stacks the lines or hides one behind the other is invisible to a text assertion. It also screenshots the readout mid-round, since four fields on one line can crowd or wrap and no assertion would notice. Three traps it encodes: **score assertions must be relative** (the driver has already banked floater kills by the time it reaches the boss, so asserting an absolute total is asserting the driver's own history), and **the opening announcement is a race** — `isRunning()` flips inside the pointer-lock handler, which can land before the frame that flushes the announcement, so wait on it rather than sampling once. Third: **anything that sets `rounds.kills` by hand must derive the number from `ROUNDS.killsPerRound`.** A hardcoded tally that was safely mid-round under the old quota sits *above* a retuned one, and the next `update()` quietly starts a second boss round underneath every assertion that follows — which is how the readout screenshot's `kills = 37` broke when `killsPerRound` came down to 30. Its announcement screenshot uses a stretched `animationDuration` *plus* a negative `animationDelay` to park the flash on its opaque plateau; stretching alone lands inside the fade-in and looks worse than doing nothing.

- `%TEMP%\doomslop-jump.mjs` — 20 assertions on the space-bar jump, plus a **pair** of screenshots. The arc is *measured*, not read back: player and camera Y are sampled every frame off a rAF loop and compared against the closed form, since asserting `velocityY === jumpSpeed` after a tap passes on a build that teleports the view up and leaves it there. Three traps it encodes:
  - **The apex band is derived from the measured frame time, not picked.** Explicit Euler steps velocity before position, so a *correct* implementation undershoots `jumpSpeed²/(2·gravity)` by `jumpSpeed · dt / 2` — 3% of the hop at 95fps and 5% at 60fps. A flat 4% band would fail on a slower machine; predicting the undershoot from the sampled `dt` is tight at any frame rate (measured 1.020u against a predicted 1.021u). Airtime carries a few frames of slack on top of its percentage because it's quantized at both ends.
  - **A launch is a grounded → airborne transition, so the recorder has to start before the tap.** Tapping first and recording afterwards misses the transition and reads as *zero* jumps — which is how the held-key check first failed against a working build. Each case banks a grounded sample first and asserts it was grounded, or the count is vacuous.
  - **Cases have to start from a known *input* state, not just a known position.** The buffering being tested means a press outlives the case that made it: the mechanism check taps Space for real, and that press was launching the player in the middle of the next case's measurements. The `quiet()` helper clears `input.presses` for that reason.
  - Behaviour covered: resting flat with no accumulated gravity, the camera following the arc rather than just `player.position` (only `_syncCamera()` connects them), a held key jumping once and not pogoing, a mid-air tap not double-jumping but *being* buffered to fire on landing (asserted as **two** launches — expecting one passes on a build that drops the second tap), air control and the X/Z clamp still applying mid-flight, Space doing nothing while paused and not banking, and a retry after dying mid-jump starting flat. Plus the one that guards a boundary in another file: **a floater reaching the player mid-jump still lands its hit**, which is what catches anyone making `enemies.js`'s contact check 3D.
  - The screenshots are a matched pair — the same frame grounded and at the apex, enemies pinned at fixed points so height is the only difference. One shot alone can't be judged: a 1-unit rise on a 1.7-unit eye height is subtle, and "the view lifted" and "the floor dropped away" look identical in isolation.
- `%TEMP%\doomslop-spawnheight.mjs` — 23 assertions on the spawn-height band and the levelling-out, plus a screenshot. What it exists to measure is a **slope, not a position**: the settle is tied to ground covered, so it runs the same flight at `speedScale` 3 and 9 and asserts both shed the same height per unit travelled. It taps the master gain with an `AnalyserNode` and measures peak amplitude, so it proves each effect actually *generates signal* rather than merely not throwing — the audio equivalent of looking at a screenshot. Also covers autoplay hygiene, event wiring, and clipping under sustained fire. **Its silence baseline has to wait out the resume click** that the overlay click played, and quiet the field first: the game is live during the measurements, so a floater reaching the player fires `playerDamaged` straight into the sample window. When a driver places an enemy by hand, **keep it above the floor.** The arena is solid, so a target buried under `y=0` is legitimately unhittable — a test that positions one there is testing nothing. This is how the gameplay driver used to place its target.

`main.js` exposes `window.__game` (player, enemies, weapon, effects, sound, hud, minimap, rounds, input, config, score/state getters) behind `import.meta.env.DEV`, which is how the gameplay driver reaches in. Vite strips it from production builds — verified by grepping `dist/`.

Two things the gameplay driver learned the hard way, worth preserving in any replacement:

- **Let real frames elapse after setting player state.** Writing `player.yaw` then immediately calling `weapon.fire()` tests the harness, not the game — `_syncCamera()` hasn't run. Wait ~120ms.
- **Freeze `enemies.spawnTimer` to a huge value** during targeted assertions, or the spawn timer injects an extra enemy mid-check and the count assertions fail spuriously.
- **Read effect buffers after a frame boundary.** `effects.update()` writes `drawRange` and the position buffer later in the same frame as the shot, so reading them synchronously after `fire()` sees stale values. `await` a `requestAnimationFrame` first.
- **`window.__game.config` lets a driver retune live** (the config objects are read at use time). The effects screenshots stretch `tracerLife`/`particleLife` this way, since a 0.07s tracer is otherwise impossible to capture.

Two more assertions worth keeping:

- Read `#health` / `#score` text. They start as literal `HP --` / `SCORE --` in the HTML and are only filled in by `hud.update()`, so `HP 100` proves the loop actually reached the HUD rather than dying at import time.
- Always check `console --errors` / `pageerror`. A dark scene and a failed scene are hard to tell apart in a screenshot.

Headless Chrome needs `--use-angle=swiftshader --enable-unsafe-swiftshader` or WebGL won't come up at all. Pointer lock *does* work headless, so the click-to-play path is testable.

## Architecture

`src/main.js` owns everything: it constructs the renderer, scene, camera, and each system, then drives them from one `requestAnimationFrame` loop. Systems never call each other's `update()` and never schedule their own frames — if something needs to run per-frame, main.js calls it.

Boundaries that are load-bearing:

- **`config.js` is the only place tunable numbers live.** Speeds, damage, spawn rates, sensitivity. Gameplay code reads from it; it must not hardcode values. Balancing should stay a single-file edit.
- **`input.js` reports hardware, not intent.** Held keys, accumulated mouse delta, whether the trigger is down. It has no notion of "forward" or "shoot" — `player.js` and `weapon.js` interpret. Keep gameplay meaning out of it.
  - `consumeMouseDelta()` is destructive: it returns the accumulated delta and zeroes it. Exactly one caller per frame, or look input gets eaten.
  - **`presses` / `consumePress(code)` is the edge, `keys` / `isDown(code)` is the held state.** Anything that should happen once per tap — the `~` skip, any future toggle — has to use the former: `isDown()` in the frame loop is true every frame the key is down, so one tap on a 60fps display fires sixty times. `consumePress()` is destructive for the same reason `consumeMouseDelta()` is, and one physical tap therefore reads true for exactly one caller. `keydown` filters `e.repeat` so the OS auto-repeat isn't a stream of presses, and it records `e.code` rather than `e.key` because `~` only arrives as a key with Shift held while `Backquote` is the physical key either way.
  - Losing pointer lock clears held keys and the trigger, so nothing sticks after Esc or alt-tab. It clears unread `presses` too, alongside the mouse delta and for the same reason — main.js only drains them while running, so a tap during a pause would otherwise fire on the frame after resume.
  - **Two guards in here exist because the camera used to jump to a random heading. Both are load-bearing and neither is obvious from reading the happy path.**
    - **A mousemove whose `movementX`/`movementY` exceeds `INPUT.maxLookDelta` is discarded whole.** Under pointer lock the browser can report half a screen width of movement in one event when the underlying cursor gets warped; at `PLAYER.lookSensitivity` a 960px reading is a 121° teleport, which is exactly what the bug looked like. The event is dropped rather than clamped — a spike is a bad *reading*, so the honest response is to have seen nothing, where clamping still swings the view 50° on invented data. Both axes go together: a reading wrong on X isn't trustworthy on Y.
      - **This has to live here, not in `player.js`.** It's only decidable per-event; by the time `_look()` reads the accumulator the events are summed and a single 960px spike is indistinguishable from legitimate fast movement across a slow frame. That's also why the cap is a per-*event* ceiling and must never become a per-frame one — a real flick arrives as several events and has to add up.
      - The threshold sits in its own `INPUT` block rather than next to `PLAYER.lookSensitivity`, because sensitivity is interpretation (`player.js`'s job) and this is noise rejection (`input.js`'s job).
    - **`pointerlockchange` zeroes the accumulator, in both directions.** `player.js` only consumes it while the game is running, so movement landing after a session's final `update()` — a flick that ends in the same breath as Esc — used to sit there through the whole pause and get applied as one jump on resume. Same path on death, where it would rotate a view `player.reset()` had just zeroed. The `if (!this.locked)` block below it handles keys and the trigger; this is deliberately outside it.
- **The camera *is* the player.** No body mesh — nothing renders from another viewpoint. `player.js` keeps `yaw`/`pitch` separately from `camera.rotation` and applies them via `YXZ` Euler order so pitch can be clamped without gimbal problems. Mutate `player.position`/`yaw`/`pitch`, then let `_syncCamera()` push to the camera.
  - **`_jump()` owns Y and nothing else does.** `velocityY` is the only piece of motion state carried between frames — walking is positional, with no acceleration or inertia — and `_clampToArena()` deliberately touches X/Z only, since there's no ceiling. `PLAYER.eyeHeight` doubles as the ground.
    - **Grounded is a height test, not a flag.** The floor is flat and at a known height, so there's no landing event to detect and no second piece of state that can drift out of step with the position. The early return while resting is what stops gravity accumulating a growing downward velocity while standing still — harmless against the landing snap, but it would fire the player through the floor the first time that snap was loosened.
    - **`grounded && consumePress('Space')` short-circuits in that order, and the order is the feature.** `consumePress()` is destructive, so testing `grounded` first leaves a mid-air press *queued* rather than eating it: a tap a few frames before touchdown fires on landing instead of being silently dropped. The same property is what makes double-jumping impossible — nothing reads the press until the player is back on the floor. Swapping the operands loses jump buffering and gains nothing.
    - **Jumping is not a dodge, and that's structural.** `enemies.js` measures steering and contact on the XZ plane only, so height buys nothing defensively at any `jumpSpeed`. Nothing needs to enforce it — but making that distance check 3D would silently turn jump into invulnerability, which is why the jump driver asserts a hit still lands mid-air.
    - `PLAYER.jumpSpeed`/`gravity` fully determine the arc: apex `jumpSpeed² / (2 * gravity)`, airtime `2 * jumpSpeed / gravity`. `eyeHeight` plus that apex has to stay under `WORLD.wallHeight` or a jump sees out over the arena — a balance constraint noted in `config.js`, not a clamp in code, same as the uncapped `speedStep` ladder.
- **Pointer lock drives pause.** Locked means running; unlocked means paused. `running` is derived from the lock state via `input.onLockChange`, not tracked independently. Game over calls `document.exitPointerLock()`, and the overlay doubles as the pause and death screen.
- **Score flows weapon → main via callback.** `Weapon` takes an `onKill(score)` and doesn't own the tally; `EnemyManager.damage()` returns points earned and the weapon forwards them. Enemies and the weapon stay ignorant of the score.
- **Enemies share one geometry and one material** at module scope in `enemies.js`. At this fidelity per-enemy assets are pure waste. Iterate the enemy array backwards when removing mid-loop. The boss gets its own module-scope pair rather than a scaled-up floater — at radius 3 a 20-facet icosahedron reads as a few flat slabs, and the different hue is what makes it legible as a different tier of thing.
  - **Every enemy carries `kind`, a pointer at the config block it was spawned from** (`ENEMY` or `BOSS`), and `update()` reads speed/radius/damage/spin off that rather than off an import. So a new per-enemy tunable has to be added to *both* blocks — one of them missing it is an `undefined` that silently means "0" or "NaN", not an error.
  - **Enemies spawn somewhere in a height band and *level out* to `kind.hoverHeight` as they close**, so a wave arrives at mixed heights instead of all on one plane. Two halves, and the second is what makes the first safe.
    - **The settle is a slope against the horizontal step, not a rate against `dt`.** `levelSlope` is frozen at spawn as `|y - hoverHeight| / spawnDistance` — vertical units to shed per horizontal unit travelled — and `update()` multiplies it by the same `step` that already carries `speedScale`. So the descent finishes on arrival at *any* round: a round-8 floater crosses the arena four times faster and comes down four times faster with it. A per-second rate would look identical in round 1 and leave enemies attacking from overhead in round 8, which is why the driver measures the same flight at two speed scales rather than reading `levelSlope` back.
    - **That convergence is what keeps the XZ-planar contact check honest.** `update()` steers and measures contact on the plane only (which is also why jumping isn't a dodge — see `player.js`), so something still 6 units overhead landing a hit would read as damage out of nowhere. Height is deliberately *not* part of the pursuit: enemies never dive at the camera. The one way to meet one before it has come down is to charge a fresh high spawn, and that's the player's doing. **Don't "fix" this by making the contact check 3D** — it would silently turn jump into invulnerability, which the jump driver asserts against.
    - `Math.sign(remaining)` handles both directions and the step is clamped to `Math.abs(remaining)`, so it stops exactly level rather than oscillating across the target on a long frame. The clamp is the only thing stopping a fast round from overshooting, and the driver checks both signs for it.
    - **The boss opts out by setting both ends of its band to its hover height**, which makes the settle a no-op for that tier — its entrance is staged, and a radius-3 orb arriving at a random altitude reads as a glitch rather than as variety. The fields are *present* rather than omitted, per the `kind` rule above: a missing one is a NaN, not an error. `config.js` holds the shared number in a module-local `const` so it isn't written three times.
  - **Every enemy carries a halo sprite from `_halo()`** — the aura burning around the body, the other half of the glow whose point light lives in `effects.js`. The light is what the enemy throws on the floor; the halo is what the enemy looks like. **Both read the same `kind.glow.color`**, which is the whole reason those fields live in one block: let them drift and the pair stops reading as one glow.
    - **What makes it a halo rather than a blob painted over the enemy is depth testing against the body it's centered on.** The near facets hide the middle of the quad, so all that's left is the overhang past the silhouette — which is why `haloScale` has to be over 1, and why the gradient in `HALO_TEXTURE` puts its brightness in the outer half. This is the opposite call from the boss portrait below, which turns depth testing *off*; the contrast is deliberate, and `depthWrite` is off on both so overlapping sprites don't punch holes in each other.
    - **The silhouette's edge lands at `1/haloScale` of the gradient's radius, so that ratio is what decides how the aura reads — not its world size.** Both tiers therefore hold the same `haloScale` (see `BOSS.glow` in `config.js`): the boss shipped at a smaller one first, on the reasonable-sounding grounds that a multiple of a radius-3 body is already big, and ended up with a fainter aura than the floaters it towers over. A wider aura is *not* the fix for a weak one — past ~2.6 it stops belonging to the body and just tints the wall behind it. Opacity is.
    - The texture is one `CanvasTexture` built at import time, shared by both tiers, with the per-tier color as the sprite material's tint over white — asset-free for the same reason `sound.js` synthesizes its effects. One material per tier, like the shared geometry. **Those materials read `config.js` at import time**, unlike the light, which reads it per frame, so a driver retuning `glow.color` live moves the light and not the halo.
    - **The halo is parented first and the portrait second, and the order is load-bearing.** Both sit at the orb's centre, so they tie on depth and the transparent sort leaves them in scene-graph order; with the additive halo drawn second it paints over the face and washes the portrait purple. The rounds driver asserts the ordering.
  - **The boss's portrait is a `Sprite` parented to its orb**, built in `_portrait()` from the material on the `bosses.js` entry it was spawned with. A sprite because it billboards — the face turns toward the player with nothing per-frame driving it — and parented rather than tracked so it rides the orb and vanishes with it. The orb's cosmetic tumble can't spin it: a sprite takes only position and scale off its world matrix. It's added *before* the `updateMatrixWorld()` in `_add()`, which recurses.
    - **It is never a hit target, and `weapon.js`'s non-recursive `intersectObjects(TARGETS, false)` is what guarantees that.** Flip that flag and a shot to the face returns the sprite, which misses `damage()`'s `e.mesh === mesh` lookup — leaving the boss unkillable from the front, which is the only side you ever see. The rounds driver fires one shot dead into the portrait for exactly this, and the lighting driver does the same through a floater's halo — **every** enemy has a sprite over it now, so that flag stopped being a boss-only concern.
  - **`BOSS.spawnDistance` must stay below `arenaSize/2 - BOSS.radius`.** `_spawnPoint()` rejects bearings that land out of bounds; if the distance exceeds the limit then *every* bearing is out of bounds and it falls through to its center-ward fallback on every attempt, so the boss always arrives from the same spot.

- **`bosses.js` is the boss roster: an enum of the five portraits, keyed by name.** The only module that imports an asset file. Each entry is `{ name, material }`, and the enum keys double as the displayed names so there's no second list to keep in step — add an image to `PORTRAITS` and that's the whole change.
  - **The `SpriteMaterial`s are built at import time, which is the point.** Reaching a boss takes `ROUNDS.killsPerRound` kills, so every texture is decoded long before one is needed and there's no lazy-load path to get wrong. One shared material per boss, same reasoning as the shared geometry in `enemies.js`.
  - **`depthTest: false` on those materials is load-bearing and arena-specific.** The sprite sits at the orb's center, where the near facets of a radius-3 icosahedron would hide nearly all of it. It's safe here only because the arena is one open box with nothing standing in it and floater spawning is off for the boss fight, so nothing can legitimately occlude a boss. Add cover to the level and this becomes wrong.
  - `randomBoss()` is a uniform pick with no memory, so the same boss can turn up twice running. With five of them that's an occasional repeat, not something worth tracking state to avoid.

- **`rounds.js` owns the phase machine, and it's the only module that knows what a "round" is.** `fighting → incoming → boss → breather → fighting`. It drives `EnemyManager` (wiping the field, gating spawns, summoning the boss) and reports announcements out through a callback, so it needs the manager but nothing needs it. It has no DOM access, like every other system here.
  - **Kills are tallied in `enemyDefeated()` but every phase change happens in `update()`.** The kill is reported from inside `EnemyManager.damage()`, so acting on it immediately would call `removeAll()`/`spawnBoss()` re-entrantly — mutating the enemy array from inside a method that's iterating it. Deferring to the next frame boundary is the cheap fix; don't "simplify" it back.
  - **`rounds.js` draws which boss is coming, and it does it at the field wipe rather than at the spawn a beat later** — because the `BOSS ROUND` flash is what names it, and that flash fires `ROUNDS.bossDelay` before the orb walks in. The pick is held in `rounds.bossIdentity` and handed to `enemies.spawnBoss()`, so the face on the orb is the name that was announced. `reset()` nulls it, or a retry would carry the dead run's boss into the next flash. `spawnBoss()` defaults the argument to a fresh `randomBoss()` so a bare call still works.
  - **`skip()` is the `~` cheat, and it's one implementation for all four phases.** It wipes and gates spawning unconditionally: from `fighting` that clears a live field, and from the other three it's a no-op on an already-empty arena. Two things it deliberately doesn't do, both of which existing boundaries hand over for free — **no score or kill credit**, because the sweep goes through `removeAll()`, which never fires `onDefeat`, so skipping past a live boss can't pay out its 5000; and **no heal**, because `refillHealth()` is the boss-death transition's payment for actually killing it, and a skip that healed would double as a medkit. It routes through `_startRound()` rather than repeating its two steps, so a skip can't drift from a real round start — skipping to round 5 and fighting round 1's floaters is exactly the drift that method exists to prevent. main.js reads the keypress and calls this; `input.js` never learns what `~` means.
  - **`rounds.js` formats its own readout strings** — `label` (`ROUND 3`, `ROUND 3 BOSS`) and `progress` (`KILLS 12/25`) — plus `speedLabel` (`ENEMY SPEED: 1.32x`) for the flash's second line, and `hud.update()` just writes them. `_pending` is therefore a `{ text, sub }` object rather than a string, and the flush passes both to `onAnnounce`. `progress` returns **null during the boss fight**, which the HUD treats as "hide the field": a frozen `25/25` sitting there looks like it's still counting. Because null is a real value, the HUD's change-cache for it starts as `undefined`, not null.
  - **Announcements are queued in `_pending` and flushed at the top of `update()`**, which main.js only calls while running. That's what keeps `reset()` from flashing `ROUND 1` behind the click-to-start overlay, and it's why the inter-round timers pause with the game.
  - **`removeAll()` vs `clear()` is load-bearing.** `clear()` also calls `reset()`, which zeroes `elapsed` — using it for the between-rounds wipe would restart the difficulty ramp every round and the game would never get harder. The round wipe uses `removeAll()`; only a player restart uses `clear()`.
  - **`onDefeat` fires only from `damage()`, never from `remove()` or `removeAll()`.** Contact deaths and between-round sweeps stay silent, so floaters suiciding into the player can't advance the round and a restart can't credit a kill for every enemy it swept. Same rule the score already follows: you have to actually kill them.
  - **`rounds.js` owns the per-round speed growth, and `EnemyManager` just holds the number.** `speedScale` is a getter over `1 + ROUNDS.speedStep * (round - 1)` — a step **added** to round 1's speed, not a rate compounded on the previous round, which is why the field is `speedStep` rather than `speedGrowth`; and derived from the round rather than accumulated in a field, so it can't drift out of step with it. `_startRound()` pushes it via `enemies.setSpeedScale()`. `EnemyManager.update()` multiplies `kind.speed` by it, which covers the boss for free since both tiers read speed off `kind`.
    - **The same multiplier scales the spawn *rate*, so `currentSpawnInterval()` divides by it** rather than scaling `ENEMY.spawnInterval` alone. Dividing the already-ramped interval moves both ends of the ramp together; scaling only the starting interval would flatten it against a fixed `spawnIntervalMin` and every late round would converge on the same pressure. Rate is the reciprocal of interval, so a 1.15× rate is a division, not a multiplication — the sign of that is easy to get backwards and the driver measures spawns per second rather than reading the interval.
    - **Push the scale *before* `setSpawning(true)`.** `setSpawning()` re-derives `spawnTimer` from `currentSpawnInterval()`, so the order is load-bearing in `rounds.reset()` — `_startRound()` first, then `setSpawning()`. Reversed, a retry after dying on round 7 opens with the dead run's compressed interval.
    - `EnemyManager.reset()` deliberately leaves `speedScale` alone. `rounds.reset()` is the only writer, and it runs right after `clear()` on a restart.
    - The ladder has no ceiling, so it eventually passes `PLAYER.moveSpeed` (round 6 for floaters, 10 for the boss at the shipped 0.5) and enemies stop being outrunnable; the spawn interval likewise shrinks past `spawnIntervalMin` with no floor under it. Both are balance calls to make in `config.js`, not bugs to fix in `enemies.js`.
  - **The boss dying refills the player to full**, via `player.refillHealth()` at the `boss → breather` transition. That's why `Rounds` takes a `player`: it's the second gameplay system to hold one and move health, after `EnemyManager`. Two placements that look equivalent and aren't — hanging it off `onDefeat` heals on every floater, and putting it in `reset()` is dead code, since a restart goes through `player.reset()`, which is already full health.
  - **The boss is not consumed on contact.** Floaters are removed when they touch the player; the boss sits on them and hits on an `attackInterval` cooldown instead. Removing it on touch would let a 50-shot enemy be beaten by walking into it, and with no cooldown it would land a hit every frame and erase a full health bar in a fraction of a second.
- **`hud.js` anchors two things to world points, both DOM, both through `_place()`:** the boss health bar and the floating `+points` score popups. `_place()` projects, converts NDC to CSS pixels, and returns false for anything behind the camera — `project()` mirrors x/y through the origin there and would put the element somewhere plausible-looking but wrong. Off to the sides needs no such check; it clips at the viewport edge. Keep both callers on that one helper rather than reimplementing the `z >= 1` rule.
  - **`#announce` is a wrapper, not the text.** It holds `#announce-title` (`ROUND 3`, `BOSS ROUND`) and `#announce-sub`, and the `flash` class plus the `opacity: 0` base live on the *wrapper* so both lines fade as one thing. The second line is in normal flow under the first rather than pinned to its own `top`, so the title's font size can change without re-deriving an offset. **`#announce-sub` carries two unrelated things** — the round's enemy speed (`ENEMY SPEED: 1.32x`) on a round flash, and the boss's name (`KYLE`) on `BOSS ROUND` — hence the generic id; it was `#announce-speed` before the bosses got names. `hud.announce(text, sub)` writes both children and empties the sub for any announcement that doesn't have one. **Anything reading the announcement out of the DOM must read `#announce-title`** — the wrapper's `textContent` concatenates both lines plus the whitespace between them, so it is never `''`.
  - **Score popups are pooled**, like everything in `effects.js` — a fixed set of divs built in `_buildPopups()` from `POPUP.pool`, with a kill on a full pool recycling the one closest to expiring. Kills come several a second, so creating and dropping DOM nodes per kill would give the GC steady work.
  - **`hud.updatePopups(dt)` must run after `weapon.update()` in the frame.** A popup spawned by a kill this frame is placed by that call; run it earlier and a fresh popup paints one frame at the top-left corner before jumping to the kill.
  - **The popup's rise and fade are driven in JS, not by a CSS animation**, so `POPUP.life` is the single source of truth. `#announce` does it the other way — its 1.2s is in `style.css` and `ROUNDS.bossDelay`/`roundDelay` have to be kept longer by hand. That coupling is tolerable for one number; don't add a second. The popup's *color and font* are still CSS, like the rest of the HUD.
  - The popup's number comes from `enemy.kind.scoreValue` via `enemies.onDefeat`, while the score tally comes from `damage()`'s **return value** forwarded through the weapon's `onKill`. Same number, two hooks — safe only because `damage()` has exactly one real caller. A second caller would make the popup and the readout disagree.
  - **`#controls` (top left) is static text like `#build`** — no JS touches it. It's in the one corner nothing else occupies, which is the reason it can be absolutely positioned at a flat `top`/`left` with no coordination: the radar's `MINIMAP.size` and the readout's length both move things it isn't next to. It's a two-column grid so the actions line up against keys that run 1 to 5 characters, both columns left-aligned so the panel's left edge stays flush with the screen edge it's anchored to. **It's the only list of the controls anywhere.** The overlay used to repeat the movement keys in a second `<p>`; that's gone, so there's one copy to keep current. It stays drawn behind the pause overlay like the rest of the HUD, which is what lets it cover the start screen too — dim there, but legible. Note the removal left `hud.showOverlay()`'s `querySelector('p')` matching exactly one element, and re-adding a paragraph above the subtitle would silently turn it into the pause message.
  - **`#build` (bottom right) is the one HUD element `hud.js` doesn't own.** The build number is a literal in `index.html` — no JS reads or writes it, and it is deliberately not in `config.js` (tunables are numbers gameplay reads; nothing reads this) nor derived from `package.json`'s `version`, git, or a build timestamp. It's bumped by hand, so the value lives next to the element that shows it and changing it is a one-line HTML edit. The pages driver asserts the *shape* (`/^BUILD \d+\.\d+$/`), not the value, so bumping it doesn't break a test — but emptying the element, or "tidying" it into `hud.update()` and leaving it unwritten like `HP --`, still fails.
- **`effects.js` draws; `weapon.js` doesn't.** The weapon has no scene access — it reports `{ muzzle, endpoint, direction, hit }` through `onShot` and main.js turns that into tracers and sparks. Keep it that way; handing `Weapon` a scene reference is the easy wrong move.
  - The vectors in that shot object are **module-scope scratch**, overwritten on the next shot. Handlers must consume them synchronously, never retain them.
  - Everything in `effects.js` is preallocated: a fixed tracer pool and a particle pool with a contiguous `[0, live)` active prefix, dead particles swapped with the last live one so `drawRange` stays valid. Effects fire several times a second, so per-shot allocation would give the GC steady work during play.
  - Ray origin is the **eye** (so aim matches the crosshair exactly), but the tracer is drawn from an offset **muzzle**. These are deliberately different points.
  - **The arena is solid.** `createWorld` returns a `solids` array (floor + four walls) and `weapon.fire()` raycasts it in the *same* cast as the enemy hitboxes, so the nearest surface wins. Don't split this into two casts — an enemy behind a wall would become hittable through it. The floor grid is deliberately excluded from `solids`: it's `LineSegments` 1cm above the floor, and raycasting it would scatter sparks off invisible wires.
  - **`shot.hitEnemy` is what gates gameplay, not `shot.hit`.** Scenery stops bullets and throws sparks but deals no damage, awards no score, and must not flash the crosshair hitmarker — otherwise the marker fires on every shot and stops meaning anything.
  - `shot.normal` is the **world-space** surface normal, already flipped to face back toward the shooter. `face.normal` is object-local and enemies tumble, so it has to be run through a normal matrix; `_impactNormal()` does that and falls back to the reversed shot direction if a hit carries no face data.
  - **`WEAPON.muzzleOffset` is specified in screen space, not world units** — `screenX`/`screenY` are normalized device coords (`0,0` is the crosshair, `-1` is the bottom/left edge) and `forward` only sets depth. `weapon.fire()` converts them using the live `camera.fov`/`aspect`, so the muzzle holds its on-screen spot when the FOV or window changes. Expressing it as a world offset instead looks right at one FOV and drifts at every other.
  - That offset puts the muzzle ~1.3 units *below* the eye, which swings it under the floor past ~15° of downward pitch and lets the floor clip the start of the tracer. `muzzleOffset.minHeight` clamps world Y to stop that. Don't remove it without re-running the pitch sweep in the effects driver.
  - **`effects.js` also owns the scene's dynamic lights** — the red glow riding each enemy and the flash when the player shoots — for the same reason it owns the particles: they're pooled, and the pool has a harder constraint than the others.
    - **The light count in the scene must never change, and that is what makes the glows a fixed pool rather than one light per enemy.** Three bakes the number of lights into every material's shader program, so adding a light, removing one, *or setting `visible = false`* makes it rebuild all of them — and it would happen on every spawn and every kill. An unused slot therefore idles at `intensity = 0` and stays in the scene; `clear()` dims them rather than removing them. `EFFECTS.glowPool` is the budget, and the nearest `glowPool` enemies win it.
      - Nearest rather than first-come: the pool is smaller than a late round's field, and a distant enemy holding a light while one in the player's face has none is the single arrangement that would be obvious. The pick is redone every frame by insertion into a preallocated window, so it survives spawns and kills without allocating.
      - The cost is **fill rate**, not light count as such: under swiftshader at 1280×800 the seven lights push the frame from the 72fps bucket into the 48fps one, while at 480×300 they are free. That's a software rasterizer's per-fragment shading, i.e. the one thing a real GPU is built for — but it's also why the budget exists and why `glowPool` is the knob to turn if a machine struggles.
    - **Glow color, intensity, and reach come off `kind`**, like speed and radius, so `ENEMY` and `BOSS` each carry a `glow` block and the boss's orb glows purple while floaters glow red. The boss's intensity is several times a floater's, and that part is geometry rather than taste: intensity is candela at 1/d², and nothing a radius-3 orb lights is nearer than 3 units where a floater's light works at 1.6.
    - **The glow lights the floor, not the enemy.** A point light at a mesh's center is inside it, and the arena renders front faces only, so what reads is the pool of colored light under each enemy. That is the effect, and it's also why intensity has to be read against `hoverHeight` — the numbers were chosen by looking, not derived.
    - `effects.updateGlows()` is called from main.js **outside** the `if (running)` check, alongside `minimap.draw()`, so the arena keeps its glows behind the pause overlay instead of going flat. It takes `enemies.enemies` raw for the same reason the minimap does: `hitboxes()` allocates.
    - The flash is **one light, not a pool** — `EFFECTS.muzzleFlash.life` is shorter than `WEAPON.fireInterval`, so two can't be alight at once and retriggering just restarts the decay. It gets the same **grace frame** as a tracer (`flashBorn`), because `update()` runs after the shot that armed it and the flash is shorter than a clamped worst-case frame. Its `decay` is deliberately below the physical 2: the muzzle sits ~0.4 units off the floor and is clamped nearly onto it when aiming down, where inverse-square is a blown-out spot at the barrel and nothing beyond it.

- **`sound.js` synthesizes every *effect*; `assets/audio/doom.mp3` is the one audio file.** Oscillators plus one shared noise buffer, via the Web Audio API — a deliberate match for the flat-color visuals. The music is the exception because a minute and a half of it isn't something oscillators produce; that's not licence to add samples for the effects.
  - **The `AudioContext` is built lazily, inside `resume()`.** Constructing one at import time leaves it suspended and logs an autoplay warning, and the drivers treat console warnings as failures. `resume()` is called from the overlay click, which is the one gesture every path (start, resume, retry) passes through.
  - `OscillatorNode`/`AudioBufferSourceNode` are single-use by spec — they can't be restarted, so each sound builds fresh ones. Unlike the effects pools, there is nothing poolable here; that is not an oversight.
  - **The music is a looped segment, and that's why it's an `AudioBufferSourceNode` rather than an `<audio>` element.** `loopStart`/`loopEnd` are sample-accurate and gapless; seeking an element from a `timeupdate` handler is quantized to ~250ms and audibly stutters at the seam. The cost is decoding the whole 2.4MB file on one click, once. `src.start(t, loopStart)` also offsets the *first* pass, so the trimmed lead-in never plays at all.
    - A `loopEnd` past the end of the buffer is **not an error** — the spec treats it as the buffer's end — so an over-long window's symptom is the loop running long, not a failure. `_startMusic()` clamps it and the sound driver asserts the clamp didn't fire.
  - **It plays through pause, round changes, death and retry because nothing can reach it.** `_startMusic()` is called once, guarded, and there is deliberately **no stop, no restart and no seek anywhere in the codebase** — that absence *is* the feature. Pausing only stops main.js's frame loop, which the `AudioContext`'s own clock doesn't depend on. Adding audio teardown to any reset path breaks it.
    - **The guard is set before the `await`, not after.** Two clicks in quick succession both land while the decode is in flight, and the second source wouldn't replace the first — a single-use node means it would start a second copy of the track playing over the top of it.
  - **The music has its own gain node straight to the destination, not through `master`.** Two reasons: `masterVolume` is headroom for several *effects* stacking, which one sustained bed doesn't participate in; and the sound driver taps `master` to measure whether each effect generates signal, which music underneath would swamp. So `SOUND.music.gain` is an **absolute** level and has to be read against an effect's *effective* peak (`masterVolume` × that effect's gain), not against the other gains in the block.
  - **Damage feedback hangs off `player.onDamage`.** `enemies.js` calls `player.takeDamage()` directly and main.js never sees it, so without that hook there is nowhere to attach a hit sound. `takeDamage` only fires it when health actually drops, so a hit landing at 0 HP stays silent.
  - Death releases the pointer lock, which would otherwise fire the pause click on top of dying. `onLockChange` gates the click on `!gameOver` for that reason.

- **`minimap.js` is a 2D canvas, not three.js.** It's part of the HUD layer, drawn with the Canvas 2D API on its own `<canvas id="minimap">`; the scene never contains it and the WebGL renderer never touches it. Same reasoning as the rest of the HUD — cheaper and far easier to style than in-scene geometry. Consequently `MINIMAP` colors in `config.js` are **CSS strings**, not the `0x` literals everything else uses.
  - **The map rotates; the player doesn't.** The player sits pinned at the center pointing up and the world spins around them, so map-up is always straight ahead. That's why the view cone is drawn *fixed*, pointing up, rather than swung around by the yaw — swinging it would be the non-rotating (north-up) convention, and doing both at once is the classic way to get a radar that's subtly wrong.
  - The whole rotation is one `ctx.rotate(player.yaw)` before plotting enemies at their raw world `(dx, dz)` offsets. Positive `yaw` is the right amount in the right direction only because world `+X/+Z` map to canvas `+x/+y` and canvas rotation is clockwise; flipping either convention needs `-yaw`. Verify with the minimap driver rather than by reasoning — this sign is easy to talk yourself into.
  - Cone half-angle is the **horizontal** FOV, `atan(tan(vFov/2) * aspect)`, read from the live camera. `camera.fov` is vertical, so using it directly draws a cone narrower than what the player actually sees.
  - main.js passes `enemies.enemies` (the raw `{mesh, health}[]`), not `hitboxes()` — the latter allocates a new array via `.map()` and this runs every frame.
  - `draw()` is called **outside** the `if (running)` check, alongside `hud.update()`, so the radar stays visible behind the pause overlay instead of going blank.
  - The circular mask is CSS `border-radius: 50%` *and* a `ctx.clip()` arc. Both, deliberately: the CSS handles the rim border, the clip keeps a dot near the rim from being drawn into the square's corners. Note that a clip region survives until `restore()`, hence the `save()`/`restore()` around the whole frame.

## The matrixWorld invariant (read this before touching hit detection)

`Raycaster` reads `object.matrixWorld` and **never refreshes it**, and three only recomputes world matrices inside `renderer.render()` — which runs *after* every system's `update()` in a frame. So anything that mutates a transform and is then raycast in the same frame must call `updateMatrixWorld()` itself.

Three places depend on this, and dropping any of them produces a silent aiming bug rather than an error:

- `Player._syncCamera()` — without it, `weapon.fire()` aims along the *previous* frame's rotation and aiming lags the mouse by a frame.
- `EnemyManager.update()` after moving each mesh — without it, shots test against last frame's enemy positions.
- `EnemyManager.spawn()` — most severe. A new mesh has an identity `matrixWorld`, so until the next render a raycast treats it as sitting at the **world origin**, not where it spawned.

If shots visibly pass through enemies, suspect a missing `updateMatrixWorld()` before suspecting the raycaster.

## three.js notes

- **Use `THREE.Timer`, not `THREE.Clock`.** Clock is deprecated in the pinned version and warns. Timer is exported from core; `timer.connect(document)` wires up the Page Visibility API so a backgrounded tab resumes with a sane delta. Call `timer.update()` once per frame before `getDelta()`.
- The per-frame delta is additionally clamped to `0.1s` so a GC pause can't tunnel anything through a wall.
- `require('three/package.json')` throws — three doesn't export it. Use `npm ls` to check the installed version.
- Graphics are intentionally minimal: flat colors, `MeshLambertMaterial`, no textures, no shadows. Match that when adding visuals.
- **A scene's light count is compiled into every material's shader program.** Changing it — adding a light, removing one, or hiding one with `visible = false` — makes three rebuild all of them. That's why the enemy glows are a fixed pool that dims to `intensity = 0` instead of a light per enemy; see `effects.js`. Point-light `intensity` is also candela falling off as 1/d² in the pinned version, so a glow's number only means anything read against how far its surfaces are.
- **`PointsMaterial` uses `sizeAttenuation: false`** in `effects.js`, making `EFFECTS.particleSize` a **pixel** value rather than world units. With the default world-space attenuation, muzzle sparks spawning ~0.5 units from the camera rendered as screen-filling squares. Don't "fix" this back.
- `LineBasicMaterial.linewidth` is ignored by the WebGL renderer — tracers are always 1px. That suits the look, so there's nothing to work around.
- `PointsMaterial` has no per-particle alpha, so particle fade-out is done by scaling vertex color toward black under `AdditiveBlending`. That only reads as a fade against a dark background; it would look wrong on a light one.

## Conventions

Plain ES modules, no TypeScript, no JSX, no build step beyond Vite. The HUD is DOM on top of the canvas (`hud.js`, `minimap.js`, `style.css`), not drawn in the scene — cheaper and easier to style. Comments explain *why* a boundary exists, not what a line does; match that density.
