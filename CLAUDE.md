# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state: playable

The full loop works — look, move, jump, shoot, enemies spawn and close in, contact damage, death, restart. There are no `TODO` stubs left. Difficulty ramps by shortening the spawn interval from `ENEMY.spawnInterval` to `ENEMY.spawnIntervalMin` over `ENEMY.rampDuration`.

On top of that, `rounds.js` runs the round structure: clear `ROUNDS.killsPerRound` floaters, fight a boss alone in an empty arena, next round. There are two enemy tiers (floater and boss) and no more planned — the bosses in `bosses.js` are one tier wearing a handful of faces, not a tier each.

Kills also roll for a drop. `pickups.js` runs that: a `PICKUP.dropChance` roll off every shot kill, then a second roll for which of two items it is — a health cube that refills the bar, or an armor cube that fills the `PLAYER.maxArmor` pool that soaks damage ahead of health. The second one cost a config block, a branch in `main.js`'s `onCollect` and an icon to draw, which is what the system was shaped for; a third would cost the same again and no new machinery.

Not implemented (deliberately, not oversights): weapon variety, persistent high score, mobile/touch controls. **`ROUNDS.speedStep` is the only thing that scales with the round** — a flat +0.5 per round (1.0x, 1.5x, 2.0x, …) on floater speed, boss speed, *and* the floater spawn rate, so one number covers both how fast they come and how many. Boss health and `killsPerRound` deliberately don't scale, so every round is the same length and the boss takes the same 50 shots; that's a balance decision, not a missing feature.

## Commands

```bash
npm run dev      # Vite dev server on http://localhost:5173/, hot reload
npm run build    # production bundle into dist/
npm run preview  # serve the built bundle
```

`assets/` holds every asset file in the repo: `images/` the boss portraits (one per `bosses.js` roster entry), `audio/doom.mp3` the music bed. They're reached with ES imports from `bosses.js` and `sound.js`, never literal paths, so Vite emits them into the bundle and rewrites the URLs against the base. That's why they don't need to live in `public/`, and it's the whole reason the deploy still works with assets in play.

**`vite.config.js` exists only to set `base: './'`, and that line is load-bearing for the deploy.** GitHub Pages serves the game from a `/DoomSlop/` subpath; Vite's default base of `/` emits `/assets/index-xxx.js`, which resolves above the project and 404s. Relative is used rather than a hardcoded `/DoomSlop/` so the base survives a repo rename and — more importantly here — so the dev server stays at the root, where every headless driver navigates. Don't "tidy" it to an absolute base: `npm run dev` and `npm run preview` both serve from the root, so the failure is invisible locally and only shows up on the live site.

**There is no test suite, linter, or formatter configured.** Don't invent `npm test` — it will fail. Verification is done by running the app (see below).

### Node on PATH

Node 24 LTS lives at `C:\Program Files\nodejs`, but an agent shell's environment may predate the install and not have it on PATH. If `node: command not found`, prefix it:

```bash
export PATH="/c/Program Files/nodejs:$PATH"
```

## Verifying changes

`npm run build` catches import/syntax breakage cheaply (it transforms every module). But a clean build proves nothing about rendering — WebGL failures are runtime-only and silent.

To actually check the game runs, drive headless Chrome. `playwright-core` is installed **globally** (deliberately not a project dependency), and two driver scripts live outside the repo:

- `%TEMP%\doomslop-preview.mjs` — navigates, screenshots, dumps console errors.
- `%TEMP%\doomslop-gameplay.mjs` — 20 assertions covering look/move/bounds/spawn/steering/shooting/damage/death/restart. Run it after any gameplay change. Its two height assertions read the band out of `config` rather than hardcoding a number, because this one watches a *timer*-spawned enemy and so gets whatever height the band allows; `doomslop-spawnheight.mjs` owns the detail.
- `%TEMP%\doomslop-effects.mjs` — 33 assertions on tracer origin/endpoints/lifetime, hitsparks on each surface type, and particle spawn/decay/pool-ceiling, plus effect screenshots. The muzzle assertions project the tracer's start point to NDC and sweep the pitch range, since "bottom center of the screen" is only checkable in screen space.
- `%TEMP%\doomslop-hitsparks.mjs` — screenshots of a floor hit and a wall hit. Assertions can't tell whether sparks *read*; two bugs this project has already had (screen-filling muzzle sparks, a long diagonal tracer) passed every assertion and were only caught by looking.
- `%TEMP%\doomslop-minimap.mjs` — 25 assertions on the minimap, plus a full-screen and a close-up screenshot. It reads pixels back off the minimap canvas with `getImageData` and finds the centroid of the enemy dot, then sweeps 25 (yaw, bearing) pairs asserting each dot lands at the right *bearing* clockwise from straight up. Numbers, not eyeballs: a mirrored or quarter-turn-off radar looks entirely plausible in a screenshot. Filter Chrome's `willReadFrequently` warning in any replacement — the driver's own readback triggers it, not the game. The full-screen shot is the best check of all: with enemies at known bearings, the dots inside the cone and the enemies visible in the 3D view have to be on the same sides, which no amount of self-consistent minimap math can fake.
  - **The drop blips get the same (yaw, bearing) sweep the enemy dots do, not a single "it's drawn" check, and both kinds get it separately.** They're plotted by the same `ctx.rotate(player.yaw)`, so a copy-pasted sign error is exactly the failure that would land on one of them and not the others. The readback picks them out by hue (`healthColor` green and `armorColor` blue against the enemy red and the white player), and one case puts an enemy, a health drop and an armor drop on three sides of the same frame, which is what proves they're told apart rather than one filter catching two of them. **Test blue before green:** the armor color is green enough in its own right to pass a loose green test, so the blue filter has to run first and the green case needs a `greenPixels === 0` guard to be worth anything.
  - **Both glyphs are asserted as *shapes*, which is the whole reason neither is a third and fourth color of dot.** Each must stay square to the screen across six yaws — left in the rotated frame a cross leans into an X and a shield hangs sideways, and both stop being the symbol painted on the cube. The cross's lit pixels must also come to well under the area of its bounding box, since a filled dot of the same extent would be ~79% of it; the shield is checked as taller than it is wide instead, which is what separates it from the dots before the color does. None of that is visible in a screenshot at 148px. The close-up is still worth looking at: it's the only thing that says whether a 7px cross and a 6px shield read as things to go and get when they're sitting next to an enemy dot, which is how the shot stages it.
- `%TEMP%\doomslop-rounds.mjs` — 71 assertions on the round loop: announcement order and that nothing flashes behind the click-to-start overlay, the field wipe at `killsPerRound`, the boss's size/health/score/identity, the health bar's screen position relative to the boss's head, boss contact damage arriving on a cooldown rather than every frame, the `KILLS n/25` progress field (counts shot kills, ignores contact deaths, hidden for the boss fight, back to zero next round), the health refill (a damaged player is carried through the wipe and the whole boss fight, and only topped up by the killing blow — plus a floater kill that must *not* heal), the per-round speed and spawn-rate growth, and that a retry returns to round 1.
  - The boss-identity checks tie the flash to the orb: the `#announce-sub` name must equal `rounds.bossIdentity`, and the sprite's **texture URL** must contain that same name — the one thing that catches an announcement and a face drifting apart. It also asserts the sprite's scale sits between half the orb's diameter and all of it, `depthTest === false`, and that **a shot dead into the portrait still damages the boss**, which is the guard on `weapon.js`'s non-recursive raycast. The roster is hardcoded in the driver rather than read out of the game, so a dropped or renamed image fails instead of being agreed with, and 80 `spawnBoss()` draws have to produce every name on it and nothing else.
    - **It finds the portrait by `boss.identity.material`, never by child index.** The orb carries two sprites and the glow halo is parented first, so `children[0]` is the halo — whose map is a generated canvas with no `.complete`, which means an index here doesn't fail loudly, it hangs the `waitForFunction` for its full 30s timeout. That is exactly how it broke when the halo was added. It now also asserts the portrait is the *last* child, which is what stops the additive halo painting over the face.
  - Two screenshots for the parts assertions can't judge: the `BOSS ROUND` flash with a name under it, and a close-up of the orb. Whether the ring of purple left around the face still reads as the boss underneath is the entire justification for `BOSS.portraitScale` being under 1, and no number tells you that. Note `rounds.bossIdentity` is null by the time the screenshot section runs — the retry test reset it — so the flash shot draws its own name through `spawnBoss()`.
  - The speed checks **measure displacement** — a lone enemy's position over ~450ms of real frames, timed off the rAF timestamp — rather than reading `speedScale` back. Asserting the multiplier is 1.5 proves nothing about whether `update()` multiplies by it. One frame of travel is 2-3% of that window, so they compare against a percentage band, and the *measured* case uses round 5 (3.0x) where the bands can't overlap; round 2's exact `1 + speedStep` is checked as a pushed value and as flash text instead. It also measures the boss, since one multiplier serving both tiers is the thing that could silently regress.
  - The ladder is checked as **equal differences, not equal ratios**, plus one assertion that round 3 is `1 + 2 * step` and *below* what compounding would give. Round 2 is identical under both formulas, so it's round 3 where a reintroduced `**` would show, and nothing else in the suite would notice.
  - The spawn-rate check **counts real spawns** — it times how long a fixed 12 take at scale 1 and again at round 5 — because `currentSpawnInterval()` returning the right number proves nothing about whether the spawn timer is actually fed from it. Two things make that measurable: it flattens the within-round ramp by setting `ENEMY.spawnInterval = spawnIntervalMin` through `__game.config` (restored afterwards), or `elapsed` advancing between the two runs moves the interval underneath the comparison; and it keeps that flat interval **well above a frame time** (0.4s), because the spawn timer is decremented once per frame and reset to a whole interval, so each spawn really takes `ceil(interval / dt)` frames. At 0.1s and ~95fps that rounding alone costs 5% of the rate at 1x and 13% at 3x, which reads as the scaling being weaker than it is — it's what made the ratio come out 2.63 against an expected 3.00. Timing a fixed count also avoids the ±1 discretization a fixed window leaves on the slower run. The reset ordering has its own assertion in the restart section: after dying in round 2 and clicking retry, `spawnTimer` has to be a full `ENEMY.spawnInterval`. The wrong order leaves it a third short — invisible unless measured, and that one check is the only thing that catches it.
  - The layout of the two-line flash is checked with `getBoundingClientRect()`: the speed line below the title, centered on it, smaller than it, and above the crosshair. A stylesheet slip that stacks the lines or hides one behind the other is invisible to a text assertion. It also screenshots the readout mid-round, since four fields on one line can crowd or wrap and no assertion would notice. Three traps it encodes: **score assertions must be relative** (the driver has already banked floater kills by the time it reaches the boss, so asserting an absolute total is asserting the driver's own history), and **the opening announcement is a race** — `isRunning()` flips inside the pointer-lock handler, which can land before the frame that flushes the announcement, so wait on it rather than sampling once. Third: **anything that sets `rounds.kills` by hand must derive the number from `ROUNDS.killsPerRound`.** A hardcoded tally that was safely mid-round under the old quota sits *above* a retuned one, and the next `update()` quietly starts a second boss round underneath every assertion that follows — which is how the readout screenshot's `kills = 37` broke when `killsPerRound` came down to 30. Its announcement screenshot uses a stretched `animationDuration` *plus* a negative `animationDelay` to park the flash on its opaque plateau; stretching alone lands inside the fade-in and looks worse than doing nothing.
- `%TEMP%\doomslop-popups.mjs` — 27 assertions on the score popups, plus a screenshot. The placement checks re-derive the expected pixel from raw trigonometry (`fov`, `aspect`, distance) instead of three's projection, so they can't agree with `hud.js` by sharing its bug, and one case kills on each side of the crosshair — a popup pinned to the screen center passes every "dead ahead" check. **Sample animation over wall-clock fractions of the configured life, not a frame count:** headless Chrome runs uncapped here (~95fps), so counting frames covers a much smaller and less predictable slice than you'd expect, which shows up as "it never fades" and "the ease-out looks linear" — any easing curve is nearly straight over a short enough early window. Its screenshot kills one of two floaters placed symmetrically about the crosshair, so the popup landing opposite the survivor is visible rather than argued.
- `%TEMP%\doomslop-look.mjs` — 16 assertions on the look-input path, guarding the camera-jump bug. It drives the real `document` mousemove listener with synthetic `MouseEvent`s, since Chrome honours `movementX` from the init dict — and asserts that first, because every check below it is vacuous otherwise. Covers the per-event spike cap (at the cap, one pixel over, one axis taking the whole event with it, and a spike mid-flick costing only itself), that the cap does **not** become a per-frame cap (four near-cap events in one frame must add up to four times the ceiling), and that no unread delta survives losing pointer lock — through a pause *and* through death and retry. Run it after touching `input.js` or `player._look()`.
- `%TEMP%\doomslop-cheat.mjs` — 30 assertions on the `~` skip cheat and the top-left controls panel, plus a screenshot. Synthetic `KeyboardEvent`s carrying `code` drive the real `input.js` listener (asserted first, or the rest is vacuous). The round number going up is the easy part; what it's really there for is the three things a skip must *not* do: **pay out a boss it never killed** (it reaches a real boss the config-derived way, then checks the score is unmoved against `BOSS.scoreValue`), **heal** (skips at 37 HP, asserts 37, then trips the real boss-death transition on the same damaged player and asserts 100 — the contrast is the point, since asserting only the first would pass on a build where nothing heals at all), and **fire once per frame** (a press plus 40 auto-repeats over 20 frames must advance exactly one round, which is the bug an `isDown()` implementation has). Also that `~` at the pause screen neither acts nor banks, that the breather resumes into a real fight with floaters actually spawning, and that the additive speed ladder survives being skipped up. The panel checks measure the corner with `getBoundingClientRect()` — top left, clear of both the minimap and the readout, and the minimap still pinned top-right. Run it after touching `rounds.js`, `input.js`, or the HUD corners.
- `%TEMP%\doomslop-jump.mjs` — 20 assertions on the space-bar jump, plus a **pair** of screenshots. The arc is *measured*, not read back: player and camera Y are sampled every frame off a rAF loop and compared against the closed form, since asserting `velocityY === jumpSpeed` after a tap passes on a build that teleports the view up and leaves it there. Three traps it encodes:
  - **The apex band is derived from the measured frame time, not picked.** Explicit Euler steps velocity before position, so a *correct* implementation undershoots `jumpSpeed²/(2·gravity)` by `jumpSpeed · dt / 2` — 3% of the hop at 95fps and 5% at 60fps. A flat 4% band would fail on a slower machine; predicting the undershoot from the sampled `dt` is tight at any frame rate (measured 1.020u against a predicted 1.021u). Airtime carries a few frames of slack on top of its percentage because it's quantized at both ends.
  - **A launch is a grounded → airborne transition, so the recorder has to start before the tap.** Tapping first and recording afterwards misses the transition and reads as *zero* jumps — which is how the held-key check first failed against a working build. Each case banks a grounded sample first and asserts it was grounded, or the count is vacuous.
  - **Cases have to start from a known *input* state, not just a known position.** The buffering being tested means a press outlives the case that made it: the mechanism check taps Space for real, and that press was launching the player in the middle of the next case's measurements. The `quiet()` helper clears `input.presses` for that reason.
  - Behaviour covered: resting flat with no accumulated gravity, the camera following the arc rather than just `player.position` (only `_syncCamera()` connects them), a held key jumping once and not pogoing, a mid-air tap not double-jumping but *being* buffered to fire on landing (asserted as **two** launches — expecting one passes on a build that drops the second tap), air control and the X/Z clamp still applying mid-flight, Space doing nothing while paused and not banking, and a retry after dying mid-jump starting flat. Plus the one that guards a boundary in another file: **a floater reaching the player mid-jump still lands its hit**, which is what catches anyone making `enemies.js`'s contact check 3D.
  - The screenshots are a matched pair — the same frame grounded and at the apex, enemies pinned at fixed points so height is the only difference. One shot alone can't be judged: a 1-unit rise on a 1.7-unit eye height is subtle, and "the view lifted" and "the floor dropped away" look identical in isolation.
- `%TEMP%\doomslop-spawnheight.mjs` — 23 assertions on the spawn-height band and the levelling-out, plus a screenshot. What it exists to measure is a **slope, not a position**: the settle is tied to ground covered, so it runs the same flight at `speedScale` 3 and 9 and asserts both shed the same height per unit travelled. "It ends up at `hoverHeight`" passes on a build that snaps it there, and a descent rate in units/sec passes on a build that arrives from overhead in a fast round — the two scales are what separate those.
  - The band is **pinned through `__game.config`** (`spawnHeightMin = spawnHeightMax = h`, restored immediately) for every measured case, because the expected slope depends on the spawn height and a driver that re-derived it from a random spawn would be reimplementing the formula it's checking. The distribution checks use the real random band: 60 spawns, all inside it, spread over most of it, and landing on both sides of the hover height.
  - Arrival is sampled **every frame**, since the failure to rule out is an overshoot that a before/after pair steps straight over. It asserts the descending case never dips below `hoverHeight` and the *rising* case never crosses above it — the rise gets its own case because the settle is signed and a sign slip is invisible on the descending half. The height at contact is checked against `hover + slope * lastDistance` rather than against `hover`: contact happens ~1 unit out, so a correct implementation still has one stride of height left, and asserting it arrives exactly level would fail on working code.
  - Also: `spawnDistance` is still the **horizontal** distance at every height (folding the height into it would pull high spawns closer on the plane contact is measured on), the band clears the floor and the walls by `ENEMY.radius` at both ends, an enemy spawned level has `levelSlope === 0` and doesn't drift, 20 `spawnBoss()` draws all sit at exactly `BOSS.hoverHeight`, and **an enemy near the top of the band can still be shot down** — placed along the *real* camera forward after the pitch is synced, so it tests the aim path rather than the driver's trigonometry, with the resulting height asserted so it can't quietly become a level shot.
  - The screenshot lays the band out evenly and **in order at 11 units**, not at the 25-unit spawn distance: the whole 5-unit band is only ~150px tall out there and reads as a flat row, so the shot can't be judged. It also waits out `POPUP.life + EFFECTS.particleLife` first — the previous case's popup and sparks are on timers, so `removeAll()` doesn't clear them and they land in the middle of the frame.
- `%TEMP%\doomslop-sound.mjs` — 44 assertions on the audio. It taps the master gain with an `AnalyserNode` and measures peak amplitude, so it proves each effect actually *generates signal* rather than merely not throwing — the audio equivalent of looking at a screenshot. Also covers autoplay hygiene, event wiring, and clipping under sustained fire. **Its silence baseline has to wait out the resume click** that the overlay click played, and quiet the field first: the game is live during the measurements, so a floater reaching the player fires `playerDamaged` straight into the sample window. Either way the peak is real, so the check would be measuring the wrong thing, not flaking.
  - **The music loop is *rendered*, not read back.** Asserting `loopStart`/`loopEnd` only proves the game set two numbers; it says nothing about whether playback returns to the right sample 93 seconds later, which is the only part the player experiences and which no realtime test can sit through. So the driver takes the loop points **off the live source** and replays the buffer through an `OfflineAudioContext`, which renders past the wrap in a second or two, then compares output either side of the seam sample-for-sample (it comes out bit-exact). Separate assertions tie those numbers back to `config`, so neither half is vacuous — config → source → actual audio.
    - Three of those checks exist to stop the match being an accident: the compared window must be **non-silent**, a **50ms-shifted** comparison must *fail* (a repetitive passage would otherwise agree with itself and pass a loop that wrapped at the wrong point), and the trimmed lead-in must be **audibly different** from `loopStart`, or "the offset was honoured" is asserting nothing. A short unlooped control render supplies the lead-in, which avoids reimplementing the stereo→mono downmix to compare against the raw buffer.
  - **The music's isolation from the effects bus is proven by measuring both taps over one window** — effects silent *while the music is demonstrably loud*, rather than silent because nothing at all is playing. That pairing is also what the `SOUND.music.gain` balance is checked against: the loudest effect has to peak above the bed.
  - The persistence checks turn on **source identity**: an `AudioBufferSourceNode` can't be restarted, so a different object is the exact signature of the music having gone back to the top. It's compared after a pause, a resume, a death, a retry (which runs `restart()`), a real `rounds.skip()`, and direct `rounds`/`enemies`/`player` resets. A spy counts `_startMusic()` calls, so those all-passing can't be because it simply never got asked twice.
  - **The pickup choir is the one effect measured as a *curve* rather than a peak**, because swelling instead of striking is the whole thing that distinguishes it from every other sound here — and a peak measurement can't see the difference. The tap is read at four points across one chord (inside the first voice's attack, past the last voice's entry, and twice down the release), asserting quiet → full → decaying → still above the silence floor. **It deliberately doesn't assert a *level* late in the release.** The release is exponential, so the tail is ~-26dB by 70% of `duration` and any threshold picked for it is really a restatement of the curve; full > mid > tail > silence catches the failure that matters — a `stop()` landing on the attack, or a `duration` that doesn't cover the release — without encoding today's envelope. Sample times come off `SOUND.pickup`'s own `attack`/`stagger`/`duration`, so retuning the chord moves the measurement with it.


- `%TEMP%\doomslop-lighting.mjs` — 77 assertions on the glow in both its halves, the point lights and the halo sprites, plus three matched screenshot pairs. The light assertions are all *bookkeeping*, because that's the half that's checkable: how many lights exist, that the count doesn't move across ten spawns / a boss / a sweep, that the nearest `glowPool` enemies are the lit ones (placed in a line at known distances, then the array reversed so the pick can't be passing on iteration order), that killing the closest promotes the next one in, that a floater and a boss alight at once keep their own `kind`'s color, and that `clear()` dims every light **without removing any from the scene**. Four traps it encodes:
  - **A glow's position has to be asserted against the mesh as it stands, not against the numbers the driver wrote.** A frame of `enemies.update()` steers the enemy between the write and the read, so `light.position === [4, 1.6, 0]` fails on a working build — it's asserting the game was paused. Compare `light.position.distanceTo(enemy.mesh.position)` to zero instead, and prove the light *moved* by teleporting the enemy far enough that one frame of steering can't account for it.
  - **The flash's full intensity is only readable synchronously after `fire()`** — `update()` decays it later in the same frame. Its decay is then sampled over wall-clock fractions of a stretched `life`, like the popups driver, not over a frame count.
  - **The halo assertions are about the two things a driver *can* settle**, since how an aura looks isn't one of them: that its color and opacity come off the same `kind.glow` block the point light reads (a halo drifting off the light's color is what makes the pair look like two unrelated effects), and that it's `depthTest: true` / `depthWrite: false` / additive, which is what makes it an aura rather than a decal. Plus one shared material per tier over one shared texture, its `matrixWorld` being current on the frame it spawned, that `hitboxes()` is meshes only, and **a shot dead into a floater's halo still killing it** — the same non-recursive-raycast guard the rounds driver aims at the boss's portrait, now that every enemy has a sprite covering it. It also asserts the two tiers hold the *same* `haloScale`, which is a real invariant and not a coincidence: see `BOSS.glow` in `config.js`.
  - **Whether any of it reads is judged by pairs, never by one lit frame.** The same frame with `ENEMY.glow.intensity` zeroed and restored, the same frame with the halos at opacity 0 and back, and the same frame with and without a shot — the last with sparks off and `tracerLife` at 0.001, so the light is the only difference. "The floor is reddish" and "the floor was always that color" are indistinguishable in isolation. Two things about those shots: the halo can't be switched off through `config` the way the light can, because the sprite materials are built at **import** time, so a live retune has to write the material; and the halo shots deliberately run *before* the flash pair, which stretches `muzzleFlash.life` to 1.5s and zeroes the spark counts without putting them back. The close-up with a floater beside the boss is the one that earns its keep — it's what showed the boss's aura was fainter than the floaters' it towers over. `%TEMP%\doomslop-glowtune.mjs`, `-bosstune.mjs`, `-flashtune.mjs`, `-halotune.mjs`, `-bosshalotune.mjs` sweep intensity, decay, scale and opacity on one fixed frame; they're tuning aids, not tests. `%TEMP%\doomslop-lightcost.mjs` measures the pool's frame cost by hiding lights out of the shader count — the one thing the game must never do — and is what established the cost is fill rate.
- `%TEMP%\doomslop-pickups.mjs` — 124 assertions on the drop system, plus five screenshots. It wraps `pickups.onCollect` rather than replacing it, since main.js's handler is what does the healing, the sound and the HUD message — half of what's under test. **The two faces are one system, so the file is split the way the code is:** everything physical is checked once through the health cube, and the armor section covers only the *difference* — the second roll, the per-face assets, the blue light, and a pool that fills nothing but itself. Four things it encodes:
  - **The roll's *rules* are checked with real kills; the rates are checked with bulk `maybeDrop()` calls.** Which deaths can pay out is the part that would silently regress, and it only shows up if the kill goes through `weapon.fire()` like a player's does — so there's a shot kill at `dropChance` 1 and 0, a **contact death** that must drop nothing (with its own assertion that the player really was damaged, or the case proved nothing), and a **`removeAll()` sweep** that must drop nothing. Both rates then need thousands of trials to pin down: 4000 rolls put `dropChance` inside ±0.022 at ~4σ, where 300 real kills would leave a band wide enough to pass a build at 0.25. An inverted comparison fails it outright at 0.85. `PICKUP.armorShare` gets the same treatment with `dropChance` forced to 1, which is what isolates the *second* roll from the first — plus an assertion that every drop is one of the two faces and nothing else, since a share that landed on `undefined` would otherwise pass as "not armor".
  - **Collection is planar, and that is load-bearing standing still** — not just mid-jump. The cube hovers at `PICKUP.hoverHeight` 1 and the eye is at 1.7, so a 3D test against the same reach misses a drop the player is standing next to. Reach is computed in-page as `PICKUP.radius + PLAYER.radius`; a driver that hardcoded 1.0 would be asserting today's balance. Cases at rest, one unit up, just inside and just outside.
  - **The two glow pools must not feed each other.** Six enemies crowding the player *and* a distant drop are all lit at once, which one pool of `EFFECTS.glowPool` could not do — plus neither pool carrying the other's color, and a mixed frame where a health drop and an armor drop each keep their own face's color rather than both taking whichever was assigned first. `ENEMY.speed` is zeroed through `config` (restored after) so the crowd holds position instead of landing contact damage mid-measurement.
  - **Each icon is measured as a *row profile*, not as a pixel count.** The generated textures are read back with `getImageData` and filtered by hue, then reduced to first-row / last-row / widest-row widths: the cross has to be narrow at top and bottom and widest through the middle, and the shield has to be widest on its very first row and taper to under 30% of its maximum by its last. A count or a top-vs-bottom weighting is too weak to tell a shield from a cup — the quadratic bulges, so the cup shape that shipped first came out only 12% top-heavy and passed. Both are also checked symmetric left-to-right. **Filter blue before green:** the armor body color is green enough in its own right to satisfy a loose green test.
  - **The screenshots are for the things no number settles**: whether each icon reads at range, and whether the colored light reads at all — the latter as a matched pair with *both* faces' `glow.intensity` zeroed and restored, and with a red floater in frame so "a different kind of thing" is visible rather than argued. Note the **halo can't be switched off through `config`** the way the light can (the sprite material is built at import time — see `glow.js`), so that pair isolates the light only. The `HP RESTORED` and `AP RESTORED` shots use the rounds driver's stretched `animationDuration` plus negative `animationDelay` to park the message on its opaque plateau — and both **wait out the bar's 140ms CSS transition first**, or the shot catches a full `AP 50` label over a quarter-full bar.
  - **The pay-out matrix is where the armor section stops being a copy of the health one.** A health cube must not touch AP and an armor cube must not touch HP; armor caps at `PLAYER.maxArmor` from over and under; a real contact hit has to come off AP and leave HP alone; and `player.reset()` has to zero AP rather than fill it, since it isn't health. Both pools are **written directly** rather than damaged into place, the same thing `player.reset()` does — taking a real hit to set up a partial level would be spent on the armor the next assertion is about to call untouched — and each case carries a combined guard that both pools really were where the case claims.
  - Also: the drop lands at the kill's X/Z but never at its *height* (one kill is staged at y=5.5); a drop carries `kind` pointing at the **face** (`PICKUP.health`), not at the `PICKUP` block the two faces share, since that pointer is what `effects.js` reads the glow off and what `main.js` branches on; the bob stays inside `hoverHeight ± bobAmplitude`, uses most of that band, stays *centered* on it after a full period (Y is written outright, not accumulated), and eight drops spawned together are out of phase; spin is about Y only, since a tumble would hide the icon; the shrink scales the halo with the cube through the parent matrix, because a full-size aura around a vanishing cube reads as the item leaving its glow behind; a drop is neither a bullet stop nor a hit target (an enemy behind one still dies, shooting the cube does nothing); `#notice`'s **text** box is measured with a `Range`, since the element is full-width and a rect on it would be vacuous, and its class has to carry the right tint and only that one; a second collection restarts the animation, which is the check on `hud.notice()`'s reflow; and a drop survives a round change but not a retry.
- `%TEMP%\doomslop-hitmarks.mjs` — 70 assertions on the damage feedback and the two vitals readouts, plus six screenshots. Run it after touching `player.js`, `enemies.js`'s contact checks, the HUD's full-screen layers, or the bottom-center vitals stack.
  - **Nothing in it calls `hud.hitFrom()` directly.** Every directional case stages a *real* contact hit — a floater placed just inside `kind.radius + PLAYER.radius` along a computed bearing, then two frames — so the path under test is `enemies.update()` → `takeDamage(amount, source)` → `onDamage` → `bearingTo()` → the wedge. A driver that called the HUD method with an angle it computed itself would be asserting its own trigonometry.
  - **The wedge is measured in screen space off `getBoundingClientRect()`**, not by reading the inline `rotate()` back. The bearing lives on an outer anchor and the animation's `translateY` on the child, so the placement only exists as a composition of the two — and a string comparison would pass on an indicator pinned at the crosshair. 25 (yaw, bearing) pairs, the same sweep the minimap driver runs and for the same reason.
  - **Both negative cases carry their own vacuity guard.** "A hit at 0 HP raises nothing" and "a kill raises nothing" would pass on a build where nothing ever flashes, so each is preceded by a positive case proving the feedback does fire. The 0-HP one takes damage directly with no frame boundary, because letting that frame run trips `endGame()` and stops the loop every later case needs.
  - **The harness must not top health up through `player.refillHealth()`.** That fires `onHeal`, which flashes the green vignette the baseline was about to assert was absent — it's what broke four checks on the first run. Write `player.health` instead, the same thing `player.reset()` does, and strip the classes *after*. `player.armor` is written the same way and for the same reason, even though `refillArmor()` has no hook: the blue flash is raised by `main.js`'s `onCollect`, so a *collection* staged to set up an armor level would tint the frame the next case measures.
  - The vignette's opacity is read by **seeking** its animation (`getAnimations()[0].pause()`, then `currentTime`) rather than sampling over wall clock, which is what makes the peak and tail figures exact. Both tints are parsed out of the computed `background-image`, taking the **last** `rgba(...)` match — `transparent` computes to `rgba(0, 0, 0, 0)` and is the first stop in the gradient.
  - Also: the pool built from `HITMARK.pool` and recycled round-robin, six wedges up at once from six sides, pitch invariance at ±70°, the boss's cooldown call site as well as the floater's contact one, paint order (the tint under every readout), a heal landing inside a damage flash *replacing* the red, the boss-death refill flashing green (reached the config-derived way), and placement/size checks on both vitals labels measured with a `Range` — including that `HP` and `AP` are **typographic twins** rather than a heading and a footnote (same font size, same weight, same tracking, differing only in color), which is the one thing a stylesheet slip would undo.
  - **Both bars are measured in pixels off `getBoundingClientRect()`, never by reading the fill's inline width back.** A percentage width that never lays out — a fill outside the element it's meant to be filling, an auto-width track — agrees with itself perfectly in the style attribute. Three levels are sampled and the fraction is checked against `health / PLAYER.maxHealth` (and the armor bar's against **`PLAYER.maxArmor`, not `maxHealth`** — the one assertion that catches a copy-pasted divisor), with the *track* asserted to keep its width and the fill to keep its left edge: a build that resized the whole element would pass proportionality and read as the HUD shrinking rather than as health draining. Two traps: the fill carries a **CSS transition**, so a sample has to wait out the 140ms or it measures the animation instead of the level; and every level is reached by writing `player.health` / `player.armor` rather than through the refill methods, for the reason two bullets up. One case lands a **real contact hit** and asserts the bar dropped by `ENEMY.touchDamage`, since the written levels can't show the game drives it.
    - **The absorption order is asserted through the bars, not just through the numbers.** A hit inside the AP pool has to move the armor bar and leave the health bar *and* the HP number exactly where they were; a hit bigger than the pool has to spend it and spill the remainder onto health, with **both** bars moving — which is what proves the overflow was split rather than dropped or double-charged.
    - **The stack's grouping is measured as well as its contents**: the armor pair above the health pair rather than beside it, the two tracks the same width and on one center line, and the seam *between* the pairs wider than the gap inside either one. That last is the whole point of `#armor`'s bottom margin — four rows evenly spaced read as four unrelated readouts instead of two labelled bars.
    - **The killing blow is the last thing in the file, and it has to be.** `endGame()` releases the pointer lock, so nothing after it can measure a live frame — the case asserts that (`isRunning()` false, overlay up) before asserting the bar emptied. It's worth its own case because `hud.update()` runs *outside* main.js's `if (running)`: the bar is written on the death frame, and CSS ignores a negative width outright, so an unclamped fraction would leave it sitting wherever it last was behind `YOU DIED`.

- `%TEMP%\doomslop-pages.mjs` — 12 assertions on the **production build under a path prefix**, which is the only way to catch a wrong Vite `base`. It runs its own static server that serves `dist/` at `/DoomSlop/` and logs a status per request, so a 404 on an asset is reported rather than just showing as a blank screen. Run it after touching `vite.config.js`, `index.html`, `bosses.js`, `sound.js`, or anything about the deploy. When a driver places an enemy by hand, **keep it above the floor.** The arena is solid, so a target buried under `y=0` is legitimately unhittable — a test that positions one there is testing nothing. This is how the gameplay driver used to place its target.

A driver that places a **pickup** by hand has the opposite problem: `pickups.update()` rewrites Y from `PICKUP.hoverHeight` every frame, so a drop parked on the ray for a raycast test has to be fired at in the same `evaluate()`, with no frame boundary in between.

`main.js` exposes `window.__game` (player, enemies, pickups, weapon, effects, sound, hud, minimap, rounds, input, config, score/state getters) behind `import.meta.env.DEV`, which is how the gameplay driver reaches in. Vite strips it from production builds — verified by grepping `dist/`.

Two things the gameplay driver learned the hard way, worth preserving in any replacement:

- **Let real frames elapse after setting player state.** Writing `player.yaw` then immediately calling `weapon.fire()` tests the harness, not the game — `_syncCamera()` hasn't run. Wait ~120ms.
- **Freeze `enemies.spawnTimer` to a huge value** during targeted assertions, or the spawn timer injects an extra enemy mid-check and the count assertions fail spuriously.
- **Read effect buffers after a frame boundary.** `effects.update()` writes `drawRange` and the position buffer later in the same frame as the shot, so reading them synchronously after `fire()` sees stale values. `await` a `requestAnimationFrame` first.
- **`window.__game.config` lets a driver retune live** (the config objects are read at use time). The effects screenshots stretch `tracerLife`/`particleLife` this way, since a 0.07s tracer is otherwise impossible to capture.

Two more assertions worth keeping:

- Read `#health` / `#armor` / `#score` text. They start as literal `HP --` / `AP --` / `SCORE --` in the HTML and are only filled in by `hud.update()`, so `HP 100` proves the loop actually reached the HUD rather than dying at import time. `AP 0` is the useful one for the armor pair — a run starts with no armor, so the placeholder is what distinguishes "empty" from "never written".
- Always check `console --errors` / `pageerror`. A dark scene and a failed scene are hard to tell apart in a screenshot.

Headless Chrome needs `--use-angle=swiftshader --enable-unsafe-swiftshader` or WebGL won't come up at all. Pointer lock *does* work headless, so the click-to-play path is testable.

## Architecture

`src/main.js` owns everything: it constructs the renderer, scene, camera, and each system, then drives them from one `requestAnimationFrame` loop. Systems never call each other's `update()` and never schedule their own frames — if something needs to run per-frame, main.js calls it.

Boundaries that are load-bearing:

- **`config.js` is the only place tunable numbers live.** Speeds, damage, spawn rates, sensitivity. Gameplay code reads from it; it must not hardcode values. Balancing should stay a single-file edit.
  - **`PICKUP` is split into a shared part and two *faces*.** Everything physical about a drop — `size`, `radius`, `hoverHeight`, the bob, the spin, `life`, `shrinkTime`, and both rolls — sits on `PICKUP` itself, because the two items are one cube with a different picture on it and a tunable that differed between them would be a tunable that shouldn't exist. `PICKUP.health` and `PICKUP.armor` hold only what *is* different: three colors and a `glow` block. That's also the block a drop's `kind` points at, so the split is the thing shared code reads through rather than a filing convenience.
    - `dropChance` is "does anything drop" and `armorShare` is "which one" — **two rolls, not one chance per item**, so the overall drop rate stays a single number and a third item would move the split rather than dilute it. Armor is the minority (0.35) on purpose: health gets the player out of trouble they're already in, where armor buffers trouble they haven't met, so the other weighting would mostly hand shields to a player at 20 HP.
  - Two blocks hold **CSS strings rather than `0x` literals**, and for the same reason: their colors are consumed by the Canvas 2D API, not by three. `MINIMAP`'s are drawn on the radar canvas; each `PICKUP` face's `bodyColor`/`iconColor`/`edgeColor` are drawn into that face's generated texture. `iconColor` is named for the job rather than the shape — one field paints the health cross and the armor shield — and a face's `glow.color` is a `0x` literal, because that one goes to a three light and material, so the one block carries both conventions on purpose.
  - **`HITMARK` holds exactly one field, `pool`, and that's the whole split.** `hud.js` reads the count to build the wedges, so it's a number something in the game consumes; the wedges' size, their distance from the reticle, their color and their lifetime are pure appearance and live in `style.css`. Same division `POPUP` makes, in the same direction — and the distance in particular is a *tuning* number that was got wrong once and fixed by looking at a screenshot, not by reading a config file.
  - `PICKUP.health.glow.intensity` (9) is less than half `ENEMY.glow.intensity` (20) even though the drop reads as the brighter effect, and that's geometry rather than taste: intensity is candela at 1/d², and a cube at `PICKUP.hoverHeight` 1 lights a floor `(1/1.6)² ≈ 0.39` as far away as a floater's at 1.6. Same reasoning as `BOSS.glow` in the other direction, where a radius-3 orb needs 120 because nothing it lights is nearer than 3 units.
    - **The armor cube's 11 against the health cube's 9 is the one number here set by the eye rather than by geometry**, since the two hover at the same height and light the same floor. Blue at equal candela reads dimmer than green against a dark floor, and what the two drops should match is how *present* they look from across the arena, not what the number says. Both `haloScale`s are the 2.2 everything glowing in the game holds — see `BOSS.glow`.
  - `MINIMAP`'s two drop blips are `healthColor`/`healthArm`/`healthThickness` and `armorColor`/`armorArm`, rather than the `…Color`/`…Radius` pair the two dots use, because neither is a dot: `arm` is the half-length of a cross stroke (and of the shield's width), `thickness` the stroke's width. Naming either one `…Radius` would invite someone to draw it with `arc()`. The shield needs no `thickness` because it's a filled silhouette, and its `armorArm` is a touch under the cross's for that reason — matching their extents would leave the filled shape much the heavier of the two. **Both glyphs' proportions live in `minimap.js`, not here**, alongside the cube icons' in `pickups.js`: which marks make a shield is the shape, not a tunable.
- **`input.js` reports hardware, not intent.** Held keys, accumulated mouse delta, whether the trigger is down. It has no notion of "forward" or "shoot" — `player.js` and `weapon.js` interpret. Keep gameplay meaning out of it.
  - `consumeMouseDelta()` is destructive: it returns the accumulated delta and zeroes it. Exactly one caller per frame, or look input gets eaten.
  - **`presses` / `consumePress(code)` is the edge, `keys` / `isDown(code)` is the held state.** Anything that should happen once per tap — the `~` skip, any future toggle — has to use the former: `isDown()` in the frame loop is true every frame the key is down, so one tap on a 60fps display fires sixty times. `consumePress()` is destructive for the same reason `consumeMouseDelta()` is, and one physical tap therefore reads true for exactly one caller. `keydown` filters `e.repeat` so the OS auto-repeat isn't a stream of presses, and it records `e.code` rather than `e.key` because `~` only arrives as a key with Shift held while `Backquote` is the physical key either way.
  - Losing pointer lock clears held keys and the trigger, so nothing sticks after Esc or alt-tab. It clears unread `presses` too, alongside the mouse delta and for the same reason — main.js only drains them while running, so a tap during a pause would otherwise fire on the frame after resume.
  - **Two guards in here exist because the camera used to jump to a random heading. Both are load-bearing and neither is obvious from reading the happy path.**
    - **A mousemove whose `movementX`/`movementY` exceeds `INPUT.maxLookDelta` is discarded whole.** Under pointer lock the browser can report half a screen width of movement in one event when the underlying cursor gets warped; at `PLAYER.lookSensitivity` a 960px reading is a 121° teleport, which is exactly what the bug looked like. The event is dropped rather than clamped — a spike is a bad *reading*, so the honest response is to have seen nothing, where clamping still swings the view 50° on invented data. Both axes go together: a reading wrong on X isn't trustworthy on Y.
      - **This has to live here, not in `player.js`.** It's only decidable per-event; by the time `_look()` reads the accumulator the events are summed and a single 960px spike is indistinguishable from legitimate fast movement across a slow frame. That's also why the cap is a per-*event* ceiling and must never become a per-frame one — a real flick arrives as several events and has to add up.
      - The threshold sits in its own `INPUT` block rather than next to `PLAYER.lookSensitivity`, because sensitivity is interpretation (`player.js`'s job) and this is noise rejection (`input.js`'s job).
    - **`pointerlockchange` zeroes the accumulator, in both directions.** `player.js` only consumes it while the game is running, so movement landing after a session's final `update()` — a flick that ends in the same breath as Esc — used to sit there through the whole pause and get applied as one jump on resume. Same path on death, where it would rotate a view `player.reset()` had just zeroed. The `if (!this.locked)` block below it handles keys and the trigger; this is deliberately outside it.
- **The camera *is* the player.** No body mesh — nothing renders from another viewpoint. `player.js` keeps `yaw`/`pitch` separately from `camera.rotation` and applies them via `YXZ` Euler order so pitch can be clamped without gimbal problems. Mutate `player.position`/`yaw`/`pitch`, then let `_syncCamera()` push to the camera.
  - **`_jump()` owns Y and nothing else does.** `velocityY` is the only piece of motion state carried between frames — walking is positional, with no acceleration or inertia — and `_clampToArena()` deliberately touches X/Z only, since there's no ceiling. `PLAYER.eyeHeight` doubles as the ground.
    - **Grounded is a height test, not a flag.** The floor is flat and at a known height, so there's no landing event to detect and no second piece of state that can drift out of step with the position. The early return while resting is what stops gravity accumulating a growing downward velocity while standing still — harmless against the landing snap, but it would fire the player through the floor the first time that snap was loosened.
    - **`grounded && consumePress('Space')` short-circuits in that order, and the order is the feature.** `consumePress()` is destructive, so testing `grounded` first leaves a mid-air press *queued* rather than eating it: a tap a few frames before touchdown fires on landing instead of being silently dropped. The same property is what makes double-jumping impossible — nothing reads the press until the player is back on the floor. Swapping the operands loses jump buffering and gains nothing.
    - **Jumping is not a dodge, and that's structural.** `enemies.js` measures steering and contact on the XZ plane only, so height buys nothing defensively at any `jumpSpeed`. Nothing needs to enforce it — but making that distance check 3D would silently turn jump into invulnerability, which is why the jump driver asserts a hit still lands mid-air.
    - `PLAYER.jumpSpeed`/`gravity` fully determine the arc: apex `jumpSpeed² / (2 * gravity)`, airtime `2 * jumpSpeed / gravity`. `eyeHeight` plus that apex has to stay under `WORLD.wallHeight` or a jump sees out over the arena — a balance constraint noted in `config.js`, not a clamp in code, same as the uncapped `speedStep` ladder.
  - **`player.js` holds two health pools, and `takeDamage()` is the only thing that knows they're ordered.** `armor` soaks first and only the remainder reaches `health`, so a 25-point hit against 10 AP spends those 10 and puts 15 on the bar — not one pool absorbing the whole thing. Health is floored at 0; armor needs no floor because it never absorbs more than it has. Nothing else in the game distinguishes the two: `enemies.js` and the boss both just call `takeDamage()`, and `isDead()` is still `health <= 0`.
    - **`onDamage`'s "only a real loss" guard is measured across *both* pools** (`health + armor` before against after), not against health alone. A hit soaked entirely by armor cost the player something real, so the sound and the wedge still have to fire — a guard on health would have gone silent for exactly the hits armor exists to take.
    - **Armor is filled only by `refillArmor()`, and `refillHealth()` deliberately doesn't touch it.** That's the spec — recoverable from an armor drop and nothing else — which is also why a boss dying tops health up and leaves AP where it was, and why `reset()` zeroes armor rather than filling it: a new run starts with whatever the last one earned, which is nothing.
    - **There is no `onArmor` hook to match `onHeal`, and that asymmetry is the rule working rather than an omission.** `onHeal` exists because *two* unrelated callers heal (a medkit and a boss going down) and neither should have to know the HUD exists. Armor has one source, so `main.js`'s `onCollect` raises the blue flash at the one call site — a hook would be a seam with nothing on the other side of it.
  - **`player.js` owns the two feedback hooks for health changing, and both exist because nothing else can see the change happen.** `onDamage(amount, source)` fires from `takeDamage()` — `enemies.js` calls that directly and main.js never sees it — and `onHeal()` fires from `refillHealth()`. `main.js` attaches the sound, the vignette and the hit indicator to them.
    - **`onHeal` hangs off `refillHealth()` rather than off the two things that call it, and that placement is the feature.** A medkit (`pickups.onCollect` in main.js) and a boss going down (`rounds.js`) have nothing in common except that method, so one line there covers both — and it's what lets `rounds.js` flash the HUD green while still having no DOM access and no HUD reference. Duplicating `hud.vignette('heal')` at both call sites is the easy wrong move.
    - **It reports unconditionally, where `onDamage` guards on health actually dropping.** A refill at full health is still something the player earned, and the `HP RESTORED` notice and the choir already fire there. `onDamage`'s guard is about one degenerate case — a hit landing on the death frame, over the top of `YOU DIED`.
    - **`source` is the attacker's live position vector, not a copy.** A floater is removed from the scene on the line after it lands its hit, so a handler has to read it synchronously — the same rule `hud.scorePopup`'s position argument follows, and the same rule the shot object's scratch vectors follow.
  - **`bearingTo(point)` is the seam between the player and the hit indicator.** An on-screen bearing is a screen-space angle, but deriving it needs `yaw` and `position`, so the angle is computed here and the drawing is `hud.js`'s. XZ-planar and **deliberately free of `pitch`** — looking up shouldn't swing the wedges, and flattening the camera's world direction instead (the obvious alternative) degenerates when looking straight up. It's the same rotation `minimap.js` applies, for the same reason it comes out clockwise-from-up; the sign is easy to talk yourself into, which is why the hit driver sweeps (yaw, bearing) pairs instead.
- **Pointer lock drives pause.** Locked means running; unlocked means paused. `running` is derived from the lock state via `input.onLockChange`, not tracked independently. Game over calls `document.exitPointerLock()`, and the overlay doubles as the pause and death screen.
- **Damage and heal feedback is wired in main.js off `player.onDamage` / `player.onHeal`**, the same shape as `enemies.onDefeat` and `pickups.onCollect`: the system reports, main.js decides what it means. `onDamage` plays the hit sound, flashes the red vignette, and turns the attacker's position into a bearing for the wedge. `onHeal` flashes the green one — and because it hangs off `refillHealth()` rather than off its callers, that one line covers both a medkit and a boss going down. The blue armor flash is the exception, raised from `pickups.onCollect` itself, because an armor cube is its only source.
- **Score flows weapon → main via callback.** `Weapon` takes an `onKill(score)` and doesn't own the tally; `EnemyManager.damage()` returns points earned and the weapon forwards them. Enemies and the weapon stay ignorant of the score.
- **Enemies share one geometry and one material** at module scope in `enemies.js`. At this fidelity per-enemy assets are pure waste. Iterate the enemy array backwards when removing mid-loop. The boss gets its own module-scope pair rather than a scaled-up floater — at radius 3 a 20-facet icosahedron reads as a few flat slabs, and the different hue is what makes it legible as a different tier of thing.
  - **Every enemy carries `kind`, a pointer at the config block it was spawned from** (`ENEMY` or `BOSS`), and `update()` reads speed/radius/damage/spin off that rather than off an import. So a new per-enemy tunable has to be added to *both* blocks — one of them missing it is an `undefined` that silently means "0" or "NaN", not an error.
  - **Enemies spawn somewhere in a height band and *level out* to `kind.hoverHeight` as they close**, so a wave arrives at mixed heights instead of all on one plane. Two halves, and the second is what makes the first safe.
    - **The settle is a slope against the horizontal step, not a rate against `dt`.** `levelSlope` is frozen at spawn as `|y - hoverHeight| / spawnDistance` — vertical units to shed per horizontal unit travelled — and `update()` multiplies it by the same `step` that already carries `speedScale`. So the descent finishes on arrival at *any* round: a round-8 floater crosses the arena four times faster and comes down four times faster with it. A per-second rate would look identical in round 1 and leave enemies attacking from overhead in round 8, which is why the driver measures the same flight at two speed scales rather than reading `levelSlope` back.
  - **Both `takeDamage()` call sites pass the attacker's `mesh.position`** — the floater's contact death and the boss's cooldown hit — so the HUD can point at where the hit came from. Passed, not copied: `remove()` takes the mesh out of the scene on the very next line, so the hook reads it synchronously (see `player.js`).
    - **That convergence is what keeps the XZ-planar contact check honest.** `update()` steers and measures contact on the plane only (which is also why jumping isn't a dodge — see `player.js`), so something still 6 units overhead landing a hit would read as damage out of nowhere. Height is deliberately *not* part of the pursuit: enemies never dive at the camera. The one way to meet one before it has come down is to charge a fresh high spawn, and that's the player's doing. **Don't "fix" this by making the contact check 3D** — it would silently turn jump into invulnerability, which the jump driver asserts against.
    - `Math.sign(remaining)` handles both directions and the step is clamped to `Math.abs(remaining)`, so it stops exactly level rather than oscillating across the target on a long frame. The clamp is the only thing stopping a fast round from overshooting, and the driver checks both signs for it.
    - **The boss opts out by setting both ends of its band to its hover height**, which makes the settle a no-op for that tier — its entrance is staged, and a radius-3 orb arriving at a random altitude reads as a glitch rather than as variety. The fields are *present* rather than omitted, per the `kind` rule above: a missing one is a NaN, not an error. `config.js` holds the shared number in a module-local `const` so it isn't written three times.
  - **Every enemy carries a halo sprite from `_halo()`** — the aura burning around the body, the other half of the glow whose point light lives in `effects.js`. The light is what the enemy throws on the floor; the halo is what the enemy looks like. **Both read the same `kind.glow.color`**, which is the whole reason those fields live in one block: let them drift and the pair stops reading as one glow.
    - **What makes it a halo rather than a blob painted over the enemy is depth testing against the body it's centered on.** The near facets hide the middle of the quad, so all that's left is the overhang past the silhouette — which is why `haloScale` has to be over 1, and why the gradient in `HALO_TEXTURE` puts its brightness in the outer half. This is the opposite call from the boss portrait below, which turns depth testing *off*; the contrast is deliberate, and `depthWrite` is off on both so overlapping sprites don't punch holes in each other.
    - **The silhouette's edge lands at `1/haloScale` of the gradient's radius, so that ratio is what decides how the aura reads — not its world size.** Every glowing thing in the game therefore holds the same `haloScale` of 2.2 — both enemy tiers and `PICKUP` (see `BOSS.glow` in `config.js`): the boss shipped at a smaller one first, on the reasonable-sounding grounds that a multiple of a radius-3 body is already big, and ended up with a fainter aura than the floaters it towers over. A wider aura is *not* the fix for a weak one — past ~2.6 it stops belonging to the body and just tints the wall behind it. Opacity is.
    - The texture is one `CanvasTexture` built at import time, shared by both tiers, with the per-tier color as the sprite material's tint over white — asset-free for the same reason `sound.js` synthesizes its effects. One material per tier, like the shared geometry. **Those materials read `config.js` at import time**, unlike the light, which reads it per frame, so a driver retuning `glow.color` live moves the light and not the halo.
    - **The halo is parented first and the portrait second, and the order is load-bearing.** Both sit at the orb's centre, so they tie on depth and the transparent sort leaves them in scene-graph order; with the additive halo drawn second it paints over the face and washes the portrait purple. The rounds driver asserts the ordering.
  - **The boss's portrait is a `Sprite` parented to its orb**, built in `_portrait()` from the material on the `bosses.js` entry it was spawned with. A sprite because it billboards — the face turns toward the player with nothing per-frame driving it — and parented rather than tracked so it rides the orb and vanishes with it. The orb's cosmetic tumble can't spin it: a sprite takes only position and scale off its world matrix. It's added *before* the `updateMatrixWorld()` in `_add()`, which recurses.
    - **It is never a hit target, and `weapon.js`'s non-recursive `intersectObjects(TARGETS, false)` is what guarantees that.** Flip that flag and a shot to the face returns the sprite, which misses `damage()`'s `e.mesh === mesh` lookup — leaving the boss unkillable from the front, which is the only side you ever see. The rounds driver fires one shot dead into the portrait for exactly this, and the lighting driver does the same through a floater's halo — **every** enemy has a sprite over it now, so that flag stopped being a boss-only concern.
  - **`BOSS.spawnDistance` must stay below `arenaSize/2 - BOSS.radius`.** `_spawnPoint()` rejects bearings that land out of bounds; if the distance exceeds the limit then *every* bearing is out of bounds and it falls through to its center-ward fallback on every attempt, so the boss always arrives from the same spot.

- **`glow.js` holds the halo machinery, and it exists because two unrelated modules need the *same* texture.** `enemies.js` and `pickups.js` both put an aura on their meshes, and neither should import from the other — exporting `HALO_TEXTURE` from `enemies.js` would make the drop system depend on the enemy system for a canvas gradient. So the texture and the two tiny builders (`haloMaterial(glow)`, `haloSprite(material, diameter, haloScale)`) live here and both callers import down into them.
  - **One `CanvasTexture` for every halo in the game, built at import time**, with the per-thing color as the sprite material's tint over white — asset-free for the same reason `sound.js` synthesizes its effects. Four materials over it now (two enemy tiers, two pickup faces); the pickups driver asserts `pickupHalo.material.map === enemyHalo.material.map`, which is the single check that justifies this file.
  - **`haloMaterial()` takes a `glow` block, not a `kind`.** A `kind` is a whole enemy tier and a pickup face isn't one; the block (`{ color, intensity, distance, haloScale, haloOpacity }`) is the actual shared shape, and it's the same block `effects.js` reads the point light off. Materials are still **one per kind of thing**, like the shared geometry — and they read `config.js` at *import* time, unlike the light, which reads it per frame. A driver retuning `glow.color` live therefore moves the light and not the halo.
  - The rest of why a halo reads the way it does — depth testing against the body, `haloScale` over 1, brightness in the gradient's outer half — is under `enemies.js` above, since that's where the tuning constraints bite.

- **`pickups.js` owns drops, and it's one system for two items that are one cube with a different picture on it.** `PickupManager` holds the items, floats and spins them, expires them, and reports a collection out through `onCollect` — it does not know what being collected *means*. main.js decides that (`player.refillHealth()` / `player.refillArmor()`, `sound.itemPickup()`, `hud.notice()`), which is the same shape as `enemies.onDefeat`: the manager reports, main.js interprets. **The armor cube is what that promise was written against, and it cost what it said it would**: a `config.js` face, a branch in `onCollect`, and an icon to draw — no second manager, no type field, and nothing in this module that knows what either item does.
  - **The drop roll hangs off `enemies.onDefeat`, and that hook is what gives it the right rules for free.** `onDefeat` fires only from `damage()` — never `remove()` (contact deaths) or `removeAll()` (round sweeps) — so a floater that suicides into the player and a field wiped between rounds leave nothing behind. You have to actually kill them, the same rule the score and the round count already follow. Don't move the roll to `remove()` to "catch every death"; that's the bug, not the fix.
  - **Every drop carries `kind`, pointing at the *face* it was made from — `PICKUP.health` or `PICKUP.armor`, not the `PICKUP` block they share** — exactly as an enemy points at `ENEMY`/`BOSS`. That's what lets `effects.js` read a drop's glow through the same `item.kind.glow` path it reads an enemy's, with no branch for which it got, so `_assignGlows()` is one function over two arrays; it's what `minimap.js` compares to pick a glyph; and it's what `main.js` branches on to decide what collecting one means. A `type: 'armor'` string would have needed all three of those places to learn a vocabulary.
  - **The per-face three.js objects live in an `ASSETS` `Map` keyed by the face block**, built at import time — one `MeshLambertMaterial` over one generated `CanvasTexture` and one halo material per face, the same "one per kind of thing" rule the enemy tiers follow, with the halo *texture* still the single shared one from `glow.js`. A `Map` rather than fields hung on the config blocks, which would make `config.js` a place that holds three.js objects; built eagerly rather than on first drop because there are two of them and a decode landing mid-fight stutters.
    - `faceTexture(face, drawIcon)` is the shared half and `drawCross` / `drawShield` are the difference. The icon comes in as a **callback rather than a shape name in `config.js`**, because which marks make a cross or a shield is the drawing's business — which is the same split that leaves both glyphs' proportions hardcoded in this file while their three colors live in config.
    - **`drawShield()`'s Bézier control point sits *above* the bottom edge, and that one number is the whole read of the icon.** A quadratic's end tangent points from the control at the endpoint, so a control level with the bottom corner brings both sides in horizontally and they meet in a flat curve — which at the ~50px this is seen at reads as a *cup*. Pulled up, they converge at about 45° and come to a point. The minimap blip draws the same construction a tenth the size and repeats the same pull for the same reason.
  - **Collection is an XZ-plane distance test, like enemy contact, and here it's load-bearing even standing still.** The cube hovers at `PICKUP.hoverHeight` 1 while the eye is at `PLAYER.eyeHeight` 1.7, so a 3D test against the same `PICKUP.radius + PLAYER.radius` reach would miss a drop the player is standing right next to — never mind mid-jump. Same reason jumping isn't a dodge; same warning against "fixing" it.
  - **The Y position is written outright every frame, not accumulated.** `hoverHeight + sin(phase + age * bobSpeed) * bobAmplitude`, off a per-drop random `phase` so a handful spawned together don't bob in lockstep. Accumulating would let a long life walk the item off its hover height, which is also the height the collection reach was chosen against.
  - **A drop is not in `weapon.js`'s `TARGETS` at all, so it neither stops a bullet nor can be shot.** That's by omission rather than by a guard, and it's the right call: the arena's `solids` are what bullets hit, and adding drops to either list would mean a medkit between you and a floater absorbed your shots. Don't "fix" the fact that you can shoot through one.
  - **The icon is a generated `CanvasTexture` on the cube, not a sprite.** A sprite billboards, which is right for a boss's face and wrong here: the cube *rotates*, and a face that stayed square to the camera while the body turned under it would destroy the read. Spin is `rotation.y` only for the same reason — a tumble hides the icon half the time.
  - **Drops expire (`PICKUP.life`), shrinking away over the last `shrinkTime`.** Not asked for, and a judgment call: at ~3.5 drops a round with no expiry the arena silently fills with medkits and the health bar stops mattering. The shrink is `mesh.scale`, which scales the halo for free through the parent's world matrix — a full-size aura around a vanishing cube would read as the item leaving its glow behind. The point light is the one part that doesn't follow, and it's gone within a frame.
  - **`pickups.update(dt)` sits between `weapon.update()` and the `player.isDead()` check, and both edges are deliberate.** After the weapon, so a drop rolled by a kill *this* frame is already bobbing at its hover height before it's ever drawn — spawned at the kill's raw X/Z, it would otherwise paint one frame unmoved. Before the death check, so walking onto a medkit on the same frame a floater lands its hit still saves you.
  - **`clear()` has exactly one caller, `restart()`.** Drops deliberately survive round changes — one left over at the end of a round is still there to use in the boss fight, which is the point of a drop you can save. That's also why `rounds.js` holds no reference to the manager: a round change must not be able to sweep the floor.

- **`bosses.js` is the boss roster: an enum of the portraits in `assets/images/`, keyed by name.** The only module that imports an asset file. Each entry is `{ name, material }`, and the enum keys double as the displayed names so there's no second list to keep in step — add an image to `PORTRAITS` and that's the whole change.
  - **The `SpriteMaterial`s are built at import time, which is the point.** Reaching a boss takes `ROUNDS.killsPerRound` kills, so every texture is decoded long before one is needed and there's no lazy-load path to get wrong. One shared material per boss, same reasoning as the shared geometry in `enemies.js`.
  - **`depthTest: false` on those materials is load-bearing and arena-specific.** The sprite sits at the orb's center, where the near facets of a radius-3 icosahedron would hide nearly all of it. It's safe here only because the arena is one open box with nothing standing in it and floater spawning is off for the boss fight, so nothing can legitimately occlude a boss. Add cover to the level and this becomes wrong.
  - `randomBoss()` is a uniform pick with no memory, so the same boss can turn up twice running. At this roster size that's an occasional repeat, not something worth tracking state to avoid. Adding a face is an image in `assets/images/`, an import, and a line in `PORTRAITS` — plus the two drivers that pin the roster by hand (`-rounds.mjs`, `-pages.mjs`), which is the point of their hardcoding it.

- **`rounds.js` owns the phase machine, and it's the only module that knows what a "round" is.** `fighting → incoming → boss → breather → fighting`. It drives `EnemyManager` (wiping the field, gating spawns, summoning the boss) and reports announcements out through a callback, so it needs the manager but nothing needs it. It has no DOM access, like every other system here.
  - **Kills are tallied in `enemyDefeated()` but every phase change happens in `update()`.** The kill is reported from inside `EnemyManager.damage()`, so acting on it immediately would call `removeAll()`/`spawnBoss()` re-entrantly — mutating the enemy array from inside a method that's iterating it. Deferring to the next frame boundary is the cheap fix; don't "simplify" it back.
  - **`rounds.js` draws which boss is coming, and it does it at the field wipe rather than at the spawn a beat later** — because the `BOSS ROUND` flash is what names it, and that flash fires `ROUNDS.bossDelay` before the orb walks in. The pick is held in `rounds.bossIdentity` and handed to `enemies.spawnBoss()`, so the face on the orb is the name that was announced. `reset()` nulls it, or a retry would carry the dead run's boss into the next flash. `spawnBoss()` defaults the argument to a fresh `randomBoss()` so a bare call still works.
  - **`skip()` is the `~` cheat, and it's one implementation for all four phases.** It wipes and gates spawning unconditionally: from `fighting` that clears a live field, and from the other three it's a no-op on an already-empty arena. Two things it deliberately doesn't do, both of which existing boundaries hand over for free — **no score or kill credit**, because the sweep goes through `removeAll()`, which never fires `onDefeat`, so skipping past a live boss can't pay out its 5000; and **no heal**, because `refillHealth()` is the boss-death transition's payment for actually killing it, and a skip that healed would double as a medkit. It routes through `_startRound()` rather than repeating its two steps, so a skip can't drift from a real round start — skipping to round 5 and fighting round 1's floaters is exactly the drift that method exists to prevent. main.js reads the keypress and calls this; `input.js` never learns what `~` means.
  - **`rounds.js` formats its own readout strings** — `label` (`ROUND 3`, `ROUND 3 BOSS`) and `progress` (`KILLS 12/25`) — plus `speedLabel` (`ENEMY SPEED: 1.32x`) for the flash's second line, and `hud.update()` just writes them. `_pending` is therefore a `{ text, sub }` object rather than a string, and the flush passes both to `onAnnounce`. `progress` returns **null during the boss fight**, which the HUD treats as "hide the field": a frozen `25/25` sitting there looks like it's still counting. Because null is a real value, the HUD's change-cache for it starts as `undefined`, not null.
  - **Announcements are queued in `_pending` and flushed at the top of `update()`**, which main.js only calls while running. That's what keeps `reset()` from flashing `ROUND 1` behind the click-to-start overlay, and it's why the inter-round timers pause with the game.
  - **`removeAll()` vs `clear()` is load-bearing.** `clear()` also calls `reset()`, which zeroes `elapsed` — using it for the between-rounds wipe would restart the difficulty ramp every round and the game would never get harder. The round wipe uses `removeAll()`; only a player restart uses `clear()`.
  - **`onDefeat` fires only from `damage()`, never from `remove()` or `removeAll()`.** Contact deaths and between-round sweeps stay silent, so floaters suiciding into the player can't advance the round and a restart can't credit a kill for every enemy it swept. Same rule the score already follows: you have to actually kill them.
  - **`rounds.js` owns the per-round speed growth, and `EnemyManager` just holds the number.** `speedScale` is a getter over `1 + ROUNDS.speedStep * (round - 1)` — a step **added** to round 1's speed, not a rate compounded on the previous round, which is why the field is `speedStep` rather than `speedGrowth`; and derived from the round rather than accumulated in a field, so it can't drift out of step with it. `_startRound()` pushes it via `enemies.setSpeedScale()`. `EnemyManager.update()` multiplies `kind.speed` by it, which covers the boss for free since both tiers read speed off `kind`.
    - **The same multiplier scales the spawn *rate*, so `currentSpawnInterval()` divides by it** rather than scaling `ENEMY.spawnInterval` alone. Dividing the already-ramped interval moves both ends of the ramp together; scaling only the starting interval would flatten it against a fixed `spawnIntervalMin` and every late round would converge on the same pressure. Rate is the reciprocal of interval, so a 1.15× rate is a division, not a multiplication — the sign of that is easy to get backwards and the driver measures spawns per second rather than reading the interval.
    - **Push the scale *before* `setSpawning(true)`.** `setSpawning()` re-derives `spawnTimer` from `currentSpawnInterval()`, so the order is load-bearing in `rounds.reset()` — `_startRound()` first, then `setSpawning()`. Reversed, a retry after dying on round 7 opens with the dead run's compressed interval.
    - `EnemyManager.reset()` deliberately leaves `speedScale` alone. `rounds.reset()` is the only writer, and it runs right after `clear()` on a restart.
    - The ladder has no ceiling, so it eventually passes `PLAYER.moveSpeed` (round 6 for floaters, 10 for the boss at the shipped 0.5) and enemies stop being outrunnable; the spawn interval likewise shrinks past `spawnIntervalMin` with no floor under it. Both are balance calls to make in `config.js`, not bugs to fix in `enemies.js`.
  - **The boss dying refills the player to full**, via `player.refillHealth()` at the `boss → breather` transition. That's why `Rounds` takes a `player`: it's the second gameplay system to hold one and move health, after `EnemyManager`. Two placements that look equivalent and aren't — hanging it off `onDefeat` heals on every floater, and putting it in `reset()` is dead code, since a restart goes through `player.reset()`, which is already full health.
  - **The boss is not consumed on contact.** Floaters are removed when they touch the player; the boss sits on them and hits on an `attackInterval` cooldown instead. Removing it on touch would let a 50-shot enemy be beaten by walking into it, and with no cooldown it would land a hit every frame and erase a full health bar in a fraction of a second.
- **`hud.js` anchors two things to world points, both DOM, both through `_place()`:** the boss health bar and the floating `+points` score popups. `_place()` projects, converts NDC to CSS pixels, and returns false for anything behind the camera — `project()` mirrors x/y through the origin there and would put the element somewhere plausible-looking but wrong. Off to the sides needs no such check; it clips at the viewport edge. Keep both callers on that one helper rather than reimplementing the `z >= 1` rule.
  - **`#announce` is a wrapper, not the text.** It holds `#announce-title` (`ROUND 3`, `BOSS ROUND`) and `#announce-sub`, and the `flash` class plus the `opacity: 0` base live on the *wrapper* so both lines fade as one thing. The second line is in normal flow under the first rather than pinned to its own `top`, so the title's font size can change without re-deriving an offset. **`#announce-sub` carries two unrelated things** — the round's enemy speed (`ENEMY SPEED: 1.32x`) on a round flash, and the boss's name (`KYLE`) on `BOSS ROUND` — hence the generic id; it was `#announce-speed` before the bosses got names. `hud.announce(text, sub)` writes both children and empties the sub for any announcement that doesn't have one. **Anything reading the announcement out of the DOM must read `#announce-title`** — the wrapper's `textContent` concatenates both lines plus the whitespace between them, so it is never `''`.
  - **`#notice` (lower center) is `hud.notice(text, kind)`, and it is deliberately not a third argument to `announce()`.** `HP RESTORED` or `AP RESTORED` when a drop is taken, where `kind` (`'heal'` / `'armor'`) doubles as the CSS class that tints it — exactly as `vignette()`'s argument does, so there's no mapping table here to keep in step with the stylesheet. It's tinted rather than left one color because the vignette going up with it is the item's color, and a green message under a blue flash reads as two unrelated events; the retrigger strips the tint with the `flash` class, so back-to-back drops of different kinds can't leave one message wearing the other's color. Two reasons they're separate: `#announce` owns the center of the screen and is *timed against* — `ROUNDS.bossDelay`/`roundDelay` have to stay longer than its 1.2s by hand — while nothing waits on this one, so its whole duration lives in `style.css` and it needs no config number at all. And they can be on screen together: a drop from the last kill of a round is collected while `ROUND 4` is still flashing, so one has to be above the crosshair and one below. Same remove-reflow-add retrigger as `announce()` and the muzzle flash.
  - **Score popups are pooled**, like everything in `effects.js` — a fixed set of divs built in `_buildPopups()` from `POPUP.pool`, with a kill on a full pool recycling the one closest to expiring. Kills come several a second, so creating and dropping DOM nodes per kill would give the GC steady work.
  - **`hud.updatePopups(dt)` must run after `weapon.update()` in the frame.** A popup spawned by a kill this frame is placed by that call; run it earlier and a fresh popup paints one frame at the top-left corner before jumping to the kill.
  - **The popup's rise and fade are driven in JS, not by a CSS animation**, so `POPUP.life` is the single source of truth. `#announce` does it the other way — its 1.2s is in `style.css` and `ROUNDS.bossDelay`/`roundDelay` have to be kept longer by hand. That coupling is tolerable for one number; don't add a second. The popup's *color and font* are still CSS, like the rest of the HUD.
  - The popup's number comes from `enemy.kind.scoreValue` via `enemies.onDefeat`, while the score tally comes from `damage()`'s **return value** forwarded through the weapon's `onKill`. Same number, two hooks — safe only because `damage()` has exactly one real caller. A second caller would make the popup and the readout disagree.
  - **`#vignette` and `#hitmarks` are the damage feedback, and `hud.vignette(kind)` / `hud.hitFrom(bearing)` are the whole interface.** Neither knows what hit the player; main.js works that out from `player.onDamage` / `player.onHeal`.
    - **`#vignette` is one element, one gradient and one keyframe serving all three colors.** The class (`damage` / `heal` / `armor`) supplies a `--tint` custom property that the `radial-gradient()` reads, so red, green and blue can't drift into three different fades — they're the same event shape ("what you can survive just changed, look at the bars") pointing in different directions. It's **first inside `#hud`** — later siblings paint over earlier ones, so a full-screen tint has to sit under every readout, or it dims the numbers you read through it. Its duration lives in `style.css` like `#notice`'s, since nothing waits on it. `vignette()` strips *every* tint class before re-adding one: a heal landing inside a damage flash has to replace the red, not stack on it.
    - **A wedge is two nested divs, and the nesting is not decoration.** A CSS animation on `transform` overwrites an inline `transform`, so the bearing `rotate()` lives on a zero-size outer anchor pinned at the screen center and the keyframes live on the child. That also makes the child's `translateY` radial at every bearing for free, since it runs in the parent's already-rotated frame. `rotate()` takes radians and is clockwise for positive angles, which is exactly what `player.bearingTo()` returns — no conversion.
    - **The wedge pool is walked round-robin, not searched for a free slot like the popups'.** `hud.js` holds no lifetime for these — the CSS animation *is* the duration — so there's nothing to search on. `HITMARK.pool` is 6 because floaters arrive in a swarm and several can land in the same second.
  - **`#vitals` is the bottom-center stack, and it is deliberately no longer part of `#readout`.** Two pairs — `#armorbar` over `#armor` above `#healthbar` over `#health` — because these are the readouts that change what the player should do next, and at 18px in the bottom-left corner health was being missed until the screen went red. Only the wrapper is positioned; everything inside it is in normal flow, so any label's font size is free to change without re-deriving an offset — the same arrangement `#announce-sub` has under `#announce-title`. It sits after `#muzzle` in the source so the flash glows behind the numbers rather than over them. Anything reading the HUD's layout has to know these are out of the `#readout` flex block — the rounds driver's field-order assertion had to be corrected for exactly that.
    - **Each bar is the *redundant* half of its pair on purpose**: a number has to be read, where a length is taken in by the eye that's already on the crosshair. Armor sits above health rather than beside it because it's the pool that gets spent first — the two read top-down in the order damage comes off them.
    - **`_vital(labelEl, fillEl, label, value, max)` is one helper for both pools, and the number and the fill are written together inside it**, off the caller's single change check (`if (health !== this._health)` / `if (armor !== this._armor)`). The two are views of one value and must not be able to disagree, which is also why neither tracks its own cache. A third pool would be a third call, not more code here.
    - The fraction is clamped to `[0, 1]` even though `takeDamage()` already floors both pools at 0: they're also written directly (`player.reset()`, the drivers), and CSS ignores a negative width outright, so a bar would sit at its last value on the death frame rather than emptying.
    - **`max` is passed in rather than read here, which is the one thing that keeps the armor bar off `PLAYER.maxHealth`.** A copy-pasted divisor is the natural bug in a second pair, and it would read as a bar that only ever fills halfway; the hitmarks driver asserts the armor fraction against `maxArmor` specifically for it.
    - Sizes and colors are `style.css` — nothing in the game reads them, the same split `HITMARK` and `POPUP` make. The two numbers it needs, `PLAYER.maxHealth` and `PLAYER.maxArmor`, are already tunables gameplay reads, so `hud.js` divides by them rather than gaining a config block of its own. **HP and AP are typographic twins there** (one shared rule for size, weight and tracking; only the color differs), so neither reads as a footnote to the other; the gap *between* the pairs is wider than the gap inside one, or four evenly spaced rows read as four unrelated readouts. Both fills carry a `transition`, and any driver measuring a bar has to wait it out.
  - **`#controls` (top left) is static text like `#build`** — no JS touches it. It's in the one corner nothing else occupies, which is the reason it can be absolutely positioned at a flat `top`/`left` with no coordination: the radar's `MINIMAP.size` and the readout's length both move things it isn't next to. It's a two-column grid so the actions line up against keys that run 1 to 5 characters, both columns left-aligned so the panel's left edge stays flush with the screen edge it's anchored to. **It's the only list of the controls anywhere.** The overlay used to repeat the movement keys in a second `<p>`; that's gone, so there's one copy to keep current. It stays drawn behind the pause overlay like the rest of the HUD, which is what lets it cover the start screen too — dim there, but legible. Note the removal left `hud.showOverlay()`'s `querySelector('p')` matching exactly one element, and re-adding a paragraph above the subtitle would silently turn it into the pause message.
  - **`#build` (bottom right) is the one HUD element `hud.js` doesn't own.** The build number is a literal in `index.html` — no JS reads or writes it, and it is deliberately not in `config.js` (tunables are numbers gameplay reads; nothing reads this) nor derived from `package.json`'s `version`, git, or a build timestamp. It's bumped by hand, so the value lives next to the element that shows it and changing it is a one-line HTML edit. The pages driver asserts the *shape* (`/^BUILD \d+\.\d+$/`), not the value, so bumping it doesn't break a test — but emptying the element, or "tidying" it into `hud.update()` and leaving it unwritten like `HP --`, still fails.
- **`effects.js` draws; `weapon.js` doesn't.** The weapon has no scene access — it reports `{ muzzle, endpoint, direction, hit }` through `onShot` and main.js turns that into tracers and sparks. Keep it that way; handing `Weapon` a scene reference is the easy wrong move.
  - The vectors in that shot object are **module-scope scratch**, overwritten on the next shot. Handlers must consume them synchronously, never retain them.
  - Everything in `effects.js` is preallocated: a fixed tracer pool and a particle pool with a contiguous `[0, live)` active prefix, dead particles swapped with the last live one so `drawRange` stays valid. Effects fire several times a second, so per-shot allocation would give the GC steady work during play.
  - Ray origin is the **eye** (so aim matches the crosshair exactly), but the tracer is drawn from an offset **muzzle**. These are deliberately different points.
  - **The arena is solid.** `createWorld` returns a `solids` array (floor + four walls) and `weapon.fire()` raycasts it in the *same* cast as the enemy hitboxes, so the nearest surface wins. Don't split this into two casts — an enemy behind a wall would become hittable through it. The floor grid is deliberately excluded from `solids`: it's `LineSegments` 1cm above the floor, and raycasting it would scatter sparks off invisible wires.
  - **`shot.hitEnemy` is what gates gameplay, not `shot.hit`.** Scenery stops bullets and throws sparks but deals no damage, awards no score, and must not flash the crosshair hitmarker — otherwise the marker fires on every shot and stops meaning anything.
  - `shot.normal` is the **world-space** surface normal, already flipped to face back toward the shooter. `face.normal` is object-local and enemies tumble, so it has to be run through a normal matrix; `_impactNormal()` does that and falls back to the reversed shot direction if a hit carries no face data.
  - **`WEAPON.muzzleOffset` is specified in screen space, not world units** — `screenX`/`screenY` are normalized device coords (`0,0` is the crosshair, `-1` is the bottom/left edge) and `forward` only sets depth. `weapon.fire()` converts them using the live `camera.fov`/`aspect`, so the muzzle holds its on-screen spot when the FOV or window changes. Expressing it as a world offset instead looks right at one FOV and drifts at every other.
  - That offset puts the muzzle ~1.3 units *below* the eye, which swings it under the floor past ~15° of downward pitch and lets the floor clip the start of the tracer. `muzzleOffset.minHeight` clamps world Y to stop that. Don't remove it without re-running the pitch sweep in the effects driver.
  - **`effects.js` also owns the scene's dynamic lights** — the red glow riding each enemy and the flash when the player shoots — for the same reason it owns the particles: they're pooled, and the pool has a harder constraint than the others.
    - **The light count in the scene must never change, and that is what makes the glows a fixed pool rather than one light per enemy.** Three bakes the number of lights into every material's shader program, so adding a light, removing one, *or setting `visible = false`* makes it rebuild all of them — and it would happen on every spawn and every kill. An unused slot therefore idles at `intensity = 0` and stays in the scene; `clear()` dims them rather than removing them. `EFFECTS.glowPool` is the budget, and the nearest `glowPool` enemies win it.
      - Nearest rather than first-come: the pool is smaller than a late round's field, and a distant enemy holding a light while one in the player's face has none is the single arrangement that would be obvious. The pick is redone every frame by insertion into a preallocated window, so it survives spawns and kills without allocating.
      - The cost is **fill rate**, not light count as such: under swiftshader at 1280×800 the seven lights push the frame from the 72fps bucket into the 48fps one, while at 480×300 they are free. That's a software rasterizer's per-fragment shading, i.e. the one thing a real GPU is built for — but it's also why the budget exists and why `glowPool` is the knob to turn if a machine struggles.
      - **There are two glow pools, not one: `glowPool` for enemies and `pickupGlowPool` for drops.** Deliberately separate budgets rather than one shared nearest-wins window, because the two have opposite lifetimes — a drop lies on the floor for the whole of `PICKUP.life`, so on a shared pool a couple of them near the player would sit there holding lights that closing enemies need. That is exactly the arrangement nearest-wins exists to prevent, and it's why the pickups driver lights six crowding enemies and a distant drop in the same frame.
      - **`updateGlows(enemies, pickups, viewpoint)` is a dispatcher over `_assignGlows()`**, which runs the nearest-wins insertion for one array into one pool. It works on both because a drop carries `kind` pointing at a `PICKUP` *face* just as an enemy points at `ENEMY`/`BOSS`, so `item.kind.glow` is the only thing it reads — which is also why a green health cube and a blue armor cube need no branch anywhere in this file — there is no branch for which kind of thing it got. Two arrays rather than one concatenated, since joining them would allocate every frame.
    - **Glow color, intensity, and reach come off `kind`**, like speed and radius, so `ENEMY` and `BOSS` each carry a `glow` block and the boss's orb glows purple while floaters glow red. The boss's intensity is several times a floater's, and that part is geometry rather than taste: intensity is candela at 1/d², and nothing a radius-3 orb lights is nearer than 3 units where a floater's light works at 1.6.
    - **The glow lights the floor, not the enemy.** A point light at a mesh's center is inside it, and the arena renders front faces only, so what reads is the pool of colored light under each enemy. That is the effect, and it's also why intensity has to be read against `hoverHeight` — the numbers were chosen by looking, not derived.
    - `effects.updateGlows()` is called from main.js **outside** the `if (running)` check, alongside `minimap.draw()`, so the arena keeps its glows behind the pause overlay instead of going flat. It takes `enemies.enemies` raw for the same reason the minimap does: `hitboxes()` allocates.
    - The flash is **one light, not a pool** — `EFFECTS.muzzleFlash.life` is shorter than `WEAPON.fireInterval`, so two can't be alight at once and retriggering just restarts the decay. It gets the same **grace frame** as a tracer (`flashBorn`), because `update()` runs after the shot that armed it and the flash is shorter than a clamped worst-case frame. Its `decay` is deliberately below the physical 2: the muzzle sits ~0.4 units off the floor and is clamped nearly onto it when aiming down, where inverse-square is a blown-out spot at the barrel and nothing beyond it.

- **`sound.js` synthesizes every *effect*; `assets/audio/doom.mp3` is the one audio file.** Oscillators plus one shared noise buffer, via the Web Audio API — a deliberate match for the flat-color visuals. The music is the exception because a minute and a half of it isn't something oscillators produce; that's not licence to add samples for the effects.
  - **The `AudioContext` is built lazily, inside `resume()`.** Constructing one at import time leaves it suspended and logs an autoplay warning, and the drivers treat console warnings as failures. `resume()` is called from the overlay click, which is the one gesture every path (start, resume, retry) passes through.
  - `OscillatorNode`/`AudioBufferSourceNode` are single-use by spec — they can't be restarted, so each sound builds fresh ones. Unlike the effects pools, there is nothing poolable here; that is not an oversight.
  - **The music is a looped segment, and that's why it's an `AudioBufferSourceNode` rather than an `<audio>` element.** `loopStart`/`loopEnd` are sample-accurate and gapless; seeking an element from a `timeupdate` handler is quantized to ~250ms and audibly stutters at the seam. The cost is decoding the whole 2.4MB file on one click, once. `src.start(t, loopStart)` also offsets the *first* pass, so the trimmed lead-in never plays at all.
    - A `loopEnd` past the end of the buffer is **not an error** — the spec treats it as the buffer's end — so an over-long window's symptom is the loop running long, not a failure. `_startMusic()` clamps it and the sound driver asserts the clamp didn't fire.
  - **It plays through pause, round changes, death and retry because nothing can reach it.** `_startMusic()` is called once, guarded, and there is deliberately **no stop, no restart and no seek anywhere in the codebase** — that absence *is* the feature. Pausing only stops main.js's frame loop, which the `AudioContext`'s own clock doesn't depend on. Adding audio teardown to any reset path breaks it.
    - **The guard is set before the `await`, not after.** Two clicks in quick succession both land while the decode is in flight, and the second source wouldn't replace the first — a single-use node means it would start a second copy of the track playing over the top of it.
  - **The music has its own gain node straight to the destination, not through `master`.** Two reasons: `masterVolume` is headroom for several *effects* stacking, which one sustained bed doesn't participate in; and the sound driver taps `master` to measure whether each effect generates signal, which music underneath would swamp. So `SOUND.music.gain` is an **absolute** level and has to be read against an effect's *effective* peak (`masterVolume` × that effect's gain), not against the other gains in the block.
  - **`_voice()` is the counterpart to `_tone()`, and the pickup choir is the only caller.** It's `itemPickup()`, not a sound per item: both drops are the same event ("you picked something up") and the vignette, the notice and the bars already say which — a second chord would be a fourth thing saying it, and the name is deliberately generic so a third item doesn't invite one. `_tone()` is percussive: it opens at full level and sweeps down. `_voice()` holds a pitch and *fades in* — a linear attack from an epsilon, then an exponential release — which is what makes a sine sound like a voice rather than a blip. The choir is `SOUND.pickup.ratios` (a major triad plus the octave) sounded as **detuned pairs**: two oscillators ±`detune` cents apart beat against each other, which is the cheapest thing that reads as a section rather than one singer. `stagger` brings them in low-to-high so the chord blooms upward.
    - `gain` in that block is **per voice**, not for the chord — eight of them sound at once, so the effective ceiling is `masterVolume × gain × 8`. It's the one place `masterVolume`'s headroom is actually spent, and it's why the sound driver gives the choir its own clipping check.
    - The exponential release means the tail is ~-26dB by 70% of `duration`. That's by design (it's a short sound, as asked), and it's why the driver asserts the *shape* of the decay rather than a level late in it.
  - **Damage feedback hangs off `player.onDamage`.** `enemies.js` calls `player.takeDamage()` directly and main.js never sees it, so without that hook there is nowhere to attach a hit sound. `takeDamage` only fires it when health actually drops, so a hit landing at 0 HP stays silent.
  - Death releases the pointer lock, which would otherwise fire the pause click on top of dying. `onLockChange` gates the click on `!gameOver` for that reason.

- **`minimap.js` is a 2D canvas, not three.js.** It's part of the HUD layer, drawn with the Canvas 2D API on its own `<canvas id="minimap">`; the scene never contains it and the WebGL renderer never touches it. Same reasoning as the rest of the HUD — cheaper and far easier to style than in-scene geometry. Consequently `MINIMAP` colors in `config.js` are **CSS strings**, not the `0x` literals everything else uses.
  - **The map rotates; the player doesn't.** The player sits pinned at the center pointing up and the world spins around them, so map-up is always straight ahead. That's why the view cone is drawn *fixed*, pointing up, rather than swung around by the yaw — swinging it would be the non-rotating (north-up) convention, and doing both at once is the classic way to get a radar that's subtly wrong.
  - The whole rotation is one `ctx.rotate(player.yaw)` before plotting enemies at their raw world `(dx, dz)` offsets. Positive `yaw` is the right amount in the right direction only because world `+X/+Z` map to canvas `+x/+y` and canvas rotation is clockwise; flipping either convention needs `-yaw`. Verify with the minimap driver rather than by reasoning — this sign is easy to talk yourself into.
  - Cone half-angle is the **horizontal** FOV, `atan(tan(vFov/2) * aspect)`, read from the live camera. `camera.fov` is vertical, so using it directly draws a cone narrower than what the player actually sees.
  - **Drops are drawn too, as small upright glyphs rather than a third and fourth color of dot** — a cross for health, a shield for armor. Both dots on the radar are things trying to kill you; the things on it that aren't shouldn't be told apart from them by hue alone. Each is the same symbol painted on its own cube, which is what ties a blip to the thing you walk over to collect.
    - **Which glyph is chosen by comparing `item.kind` against `PICKUP.armor`**, not by a shape name stored in the config block. How a shield is drawn belongs to the thing drawing it; `config.js` holds the color and the size.
    - **Each glyph is counter-rotated by `-player.yaw` inside the rotated frame**, so it stays square to the screen while the map turns. The dots don't need this because a circle is rotation-invariant; a cross left in the rotated frame leans into an X at most headings, and a shield hangs sideways and stops reading as a shield at all. Positioning is still the one shared `ctx.rotate(player.yaw)` with raw world offsets plotted into it — that part is identical to the enemies' and is what the driver measures.
    - Drawn **under** the enemy dots on purpose: drops don't move, so one briefly covered costs nothing, where a closing threat hidden under a medkit is the arrangement that gets the player killed.
    - The cross is two arms as overlapping `fillRect`s rather than a stroked path — at a couple of pixels wide a `lineWidth` lands between device pixels and comes out grey. The shield is a **filled** silhouette for the mirror-image reason: at 6 pixels across an outline closes up into a smudge. It's taller than it is wide, which is what separates it from the round dots at a glance before the color does, and its two quadratics take the same above-the-edge control point `drawShield()` uses in `pickups.js` — level with the bottom, the sides meet in a flat curve and it reads as a cup.
  - main.js passes `enemies.enemies` (the raw `{mesh, health}[]`), not `hitboxes()` — the latter allocates a new array via `.map()` and this runs every frame. `draw(player, enemies, pickups)` takes the two arrays separately for the same reason `effects.updateGlows()` does: joining them would allocate here too, and they're drawn differently anyway.
  - `draw()` is called **outside** the `if (running)` check, alongside `hud.update()`, so the radar stays visible behind the pause overlay instead of going blank.
  - The circular mask is CSS `border-radius: 50%` *and* a `ctx.clip()` arc. Both, deliberately: the CSS handles the rim border, the clip keeps a dot near the rim from being drawn into the square's corners. Note that a clip region survives until `restore()`, hence the `save()`/`restore()` around the whole frame.

## The matrixWorld invariant (read this before touching hit detection)

`Raycaster` reads `object.matrixWorld` and **never refreshes it**, and three only recomputes world matrices inside `renderer.render()` — which runs *after* every system's `update()` in a frame. So anything that mutates a transform and is then raycast in the same frame must call `updateMatrixWorld()` itself.

Three places depend on this, and dropping any of them produces a silent aiming bug rather than an error:

- `Player._syncCamera()` — without it, `weapon.fire()` aims along the *previous* frame's rotation and aiming lags the mouse by a frame.
- `EnemyManager.update()` after moving each mesh — without it, shots test against last frame's enemy positions.
- `EnemyManager.spawn()` — most severe. A new mesh has an identity `matrixWorld`, so until the next render a raycast treats it as sitting at the **world origin**, not where it spawned.

If shots visibly pass through enemies, suspect a missing `updateMatrixWorld()` before suspecting the raycaster.

## three.js notes

- **Use `THREE.Timer`, not `THREE.Clock`.** Clock is deprecated in the pinned version and warns. Timer is exported from core; `timer.connect(document)` wires up the Page Visibility API so a backgrounded tab resumes with a sane delta. Call `timer.update()` once per frame before `getDelta()`.
- The per-frame delta is additionally clamped to `0.1s` so a GC pause can't tunnel anything through a wall.
- `require('three/package.json')` throws — three doesn't export it. Use `npm ls` to check the installed version.
- Graphics are intentionally minimal: flat colors, `MeshLambertMaterial`, no textures, no shadows. Match that when adding visuals.
- **A scene's light count is compiled into every material's shader program.** Changing it — adding a light, removing one, or hiding one with `visible = false` — makes three rebuild all of them. That's why the enemy glows are a fixed pool that dims to `intensity = 0` instead of a light per enemy; see `effects.js`. Point-light `intensity` is also candela falling off as 1/d² in the pinned version, so a glow's number only means anything read against how far its surfaces are.
- **`PointsMaterial` uses `sizeAttenuation: false`** in `effects.js`, making `EFFECTS.particleSize` a **pixel** value rather than world units. With the default world-space attenuation, muzzle sparks spawning ~0.5 units from the camera rendered as screen-filling squares. Don't "fix" this back.
- `LineBasicMaterial.linewidth` is ignored by the WebGL renderer — tracers are always 1px. That suits the look, so there's nothing to work around.
- `PointsMaterial` has no per-particle alpha, so particle fade-out is done by scaling vertex color toward black under `AdditiveBlending`. That only reads as a fade against a dark background; it would look wrong on a light one.

## Conventions

Plain ES modules, no TypeScript, no JSX, no build step beyond Vite. The HUD is DOM on top of the canvas (`hud.js`, `minimap.js`, `style.css`), not drawn in the scene — cheaper and easier to style. Comments explain *why* a boundary exists, not what a line does; match that density.
