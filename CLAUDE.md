# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state: playable

The full loop works — look, move, jump, shoot, enemies spawn and close in, contact damage, death, restart. There are no `TODO` stubs left. Difficulty ramps by shortening the spawn interval from `ENEMY.spawnInterval` to `ENEMY.spawnIntervalMin` over `ENEMY.rampDuration`.

On top of that, `rounds.js` runs the round structure: clear `ROUNDS.killsPerRound` floaters, fight a boss alone in an empty arena, next round. There are two enemy tiers (floater and boss) and no more planned — the bosses in `bosses.js` are one tier wearing a handful of faces, not a tier each.

Kills also roll for a drop. `pickups.js` runs that: a `PICKUP.dropChance` roll off every shot kill, then a second roll for which of three items it is — a health cube that refills the bar, an armor cube that fills the `PLAYER.maxArmor` pool that soaks damage ahead of health, or SUPER BOOTS that triple move speed and jump height for `PICKUP.boots.duration` seconds. The armor cube cost a config block, a branch in `main.js`'s `onCollect` and an icon to draw, which is what the system was shaped for. **The boots are the one that shows where that promise stops**: the drop half of them cost exactly that again and nothing else, but being a *timed effect* rather than a pool, they also needed state and a countdown on `player.js`, a √ where the config number is interpreted, and a third HUD row. A fourth *resource* would be free; a fourth kind of effect wouldn't.

`portals.js` is the only thing in the arena that isn't an enemy or a drop: two glowing squares in two different walls, re-placed at the start of every round, that swap the player between them, showing a perspective preview of the far side. It's the only system that moves the player — **the arena is otherwise still a bare box**, which is what makes the portals cheap in every direction: `depthTest: false` on the boss portraits, a doorway that stops no bullets, and a planar trigger all lean on there being nothing standing in the level, and the preview leans on it hardest of all. Showing only the walls is what keeps it to one extra scene with no lights in it; a level with cover would need the real one, and then the two renders stop being affordable.

Not implemented (deliberately, not oversights): weapon variety, persistent high score, mobile/touch controls. **`ROUNDS.speedStep` is the only thing that scales with the round** — a flat +0.5 per round (1.0x, 1.5x, 2.0x, …) on floater speed, boss speed, *and* the floater spawn rate, so one number covers both how fast they come and how many. Boss health and `killsPerRound` deliberately don't scale, so every round is the same length and the boss takes the same 50 shots; that's a balance decision, not a missing feature.

## Commands

```bash
./start.sh       # install if needed, start the dev server, open a browser on it
npm run dev      # Vite dev server on http://localhost:5173/, hot reload
npm run build    # production bundle into dist/
npm run preview  # serve the built bundle
```

**`start.sh` is a wrapper around `npm run dev`, and the three things it adds are the three ways starting the game fails.** It applies the PATH fix below rather than leaving it to be remembered; it runs `npm install` only when `node_modules` is absent; and it passes `--strict-port`, so a taken 5173 is an error instead of Vite quietly moving to 5174 — where the game runs fine and every driver here, all of which hardcode 5173, is left talking to nothing. It also exits early when something is already serving the port, since that's the one case where doing nothing is right. `exec`s the server so Ctrl-C reaches Vite, and takes `--no-open` to skip the browser. Note it passes no `base`: the dev server has to stay at the root (see below).

`assets/` holds every asset file in the repo: `images/` the boss portraits (one per `bosses.js` roster entry), `audio/doom.mp3` the music bed. They're reached with ES imports from `bosses.js` and `sound.js`, never literal paths, so Vite emits them into the bundle and rewrites the URLs against the base. That's why they don't need to live in `public/`, and it's the whole reason the deploy still works with assets in play.

**`vite.config.js` exists only to set `base: './'`, and that line is load-bearing for the deploy.** GitHub Pages serves the game from a `/DoomSlop/` subpath; Vite's default base of `/` emits `/assets/index-xxx.js`, which resolves above the project and 404s. Relative is used rather than a hardcoded `/DoomSlop/` so the base survives a repo rename and — more importantly here — so the dev server stays at the root, where every headless driver navigates. Don't "tidy" it to an absolute base: `npm run dev` and `npm run preview` both serve from the root, so the failure is invisible locally and only shows up on the live site.

**There is no test suite, linter, or formatter configured.** Don't invent `npm test` — it will fail. Verification is done by running the app (see below).

### Node on PATH

Node 24 LTS lives at `C:\Program Files\nodejs`, but an agent shell's environment may predate the install and not have it on PATH. If `node: command not found`, prefix it:

```bash
export PATH="/c/Program Files/nodejs:$PATH"
```

## Verifying changes

`npm run build` catches import/syntax breakage cheaply (it transforms every module). But a clean build proves nothing about rendering — WebGL failures are runtime-only and silent.

To actually check the game runs, drive headless Chrome. `playwright-core` is installed **globally** (deliberately not a project dependency), and two driver scripts live outside the repo:

- `%TEMP%\doomslop-preview.mjs` — navigates, screenshots, dumps console errors.
- `%TEMP%\doomslop-gameplay.mjs` — 20 assertions covering look/move/bounds/spawn/steering/shooting/damage/death/restart. Run it after any gameplay change. Its two height assertions read the band out of `config` rather than hardcoding a number, because this one watches a *timer*-spawned enemy and so gets whatever height the band allows; `doomslop-spawnheight.mjs` owns the detail.
- `%TEMP%\doomslop-effects.mjs` — 33 assertions on tracer origin/endpoints/lifetime, hitsparks on each surface type, and particle spawn/decay/pool-ceiling, plus effect screenshots. The muzzle assertions project the tracer's start point to NDC and sweep the pitch range, since "bottom center of the screen" is only checkable in screen space.
- `%TEMP%\doomslop-hitsparks.mjs` — screenshots of a floor hit and a wall hit. Assertions can't tell whether sparks *read*; two bugs this project has already had (screen-filling muzzle sparks, a long diagonal tracer) passed every assertion and were only caught by looking.
- `%TEMP%\doomslop-minimap.mjs` — 33 assertions on the minimap, plus a full-screen and a close-up screenshot. It reads pixels back off the minimap canvas with `getImageData` and finds the centroid of the enemy dot, then sweeps 25 (yaw, bearing) pairs asserting each dot lands at the right *bearing* clockwise from straight up. Numbers, not eyeballs: a mirrored or quarter-turn-off radar looks entirely plausible in a screenshot. Filter Chrome's `willReadFrequently` warning in any replacement — the driver's own readback triggers it, not the game. The full-screen shot is the best check of all: with enemies at known bearings, the dots inside the cone and the enemies visible in the 3D view have to be on the same sides, which no amount of self-consistent minimap math can fake.
  - **The drop blips get the same (yaw, bearing) sweep the enemy dots do, not a single "it's drawn" check, and both kinds get it separately.** They're plotted by the same `ctx.rotate(player.yaw)`, so a copy-pasted sign error is exactly the failure that would land on one of them and not the others. The readback picks them out by hue (`healthColor` green and `armorColor` blue against the enemy red and the white player), and one case puts an enemy, a health drop and an armor drop on three sides of the same frame, which is what proves they're told apart rather than one filter catching two of them. **Test cyan before blue before green, and each step of that order is load-bearing.** The armor color is green enough in its own right to pass a loose green test, so the blue filter has to run before the green one and the green case needs a `greenPixels === 0` guard to be worth anything. The portal segments then have to be claimed before *both* — and what separates their cyan from the armor blue is the **gap** between the two channels (`b - gr`, 31 for cyan against 87 for the shield), not either level. A threshold on green alone can't do it, because the anti-aliased fringe of a cyan stroke fading into the dark background walks green down through the shield's own value while blue is still over 200. That is exactly how two portals on opposite walls came out as one 74px-wide "shield" when the segments were added, against a filter order that had been correct for every blip before them. The boots blip is deliberately **not** in this driver — it's swept the same way in `doomslop-boots.mjs` — and if it's ever moved here its yellow filter has to run before all three, since yellow is greener than the armor blue is.
  - **Both of the glyphs it covers are asserted as *shapes*, which is the whole reason none of them is just another color of dot.** Each must stay square to the screen across six yaws — left in the rotated frame a cross leans into an X and a shield hangs sideways, and both stop being the symbol painted on the cube. The cross's lit pixels must also come to well under the area of its bounding box, since a filled dot of the same extent would be ~79% of it; the shield is checked as taller than it is wide instead, which is what separates it from the dots before the color does. None of that is visible in a screenshot at 148px. The close-up is still worth looking at: it's the only thing that says whether a 7px cross and a 6px shield read as things to go and get when they're sitting next to an enemy dot, which is how the shot stages it.
  - **The walls are checked as a *ray*, not as a sample: a wall is a 1.5px line at one exact radius, so a single reading can fall beside it.** `rayMax(bearing, fromU, toU)` takes the brightest pixel over a stretch of a bearing and each case pairs "lit out at the arena distance" with "dark just inside it" — plus, for each of four bearings, the *opposite* bearing being dark from a player standing off-center, which is what fails on a box drawn centered on the map instead of at the player's own distance from each wall. The cone has to be switched off through `config.MINIMAP.coneColor` (restored afterwards) for any of it to mean anything, because the inside-the-wall control samples are exactly where the cone lands.
  - **The portal segments get the same (yaw, bearing) sweep, with the *other* portal parked past the rim so the centroid is one segment's.** `stagePortals(wall, step, u0, u1)` gets there by inverting the four `Math.random()` draws `place()` makes and stubbing them, so the placement is the real one — a driver that assigned `portal.center` and `portal.wall` itself would be testing its own arithmetic. A portal at the maximum offset on a wall 30u out is 39u from the arena center, past `MINIMAP.range` 32, which is what makes hiding one free. Two assertions are the inverse of the glyph checks above: the segment's bounding box has to **rotate** with the map (8×3px at yaw 0, 3×8px at yaw 90) rather than staying square to the screen, because a segment's *direction* is information, and its extents have to match `PORTAL.size` × `portalThickness` read from config rather than a measured constant.
- `%TEMP%\doomslop-rounds.mjs` — 71 assertions on the round loop: announcement order and that nothing flashes behind the click-to-start overlay, the field wipe at `killsPerRound`, the boss's size/health/score/identity, the health bar's screen position relative to the boss's head, boss contact damage arriving on a cooldown rather than every frame, the `KILLS n/25` progress field (counts shot kills, ignores contact deaths, hidden for the boss fight, back to zero next round), the health refill (a damaged player is carried through the wipe and the whole boss fight, and only topped up by the killing blow — plus a floater kill that must *not* heal), the per-round speed and spawn-rate growth, and that a retry returns to round 1.
  - The boss-identity checks tie the flash to the orb: the `#announce-sub` name must equal `rounds.bossIdentity`, and the sprite's **texture URL** must contain that same name — the one thing that catches an announcement and a face drifting apart. It also asserts the sprite's scale sits between half the orb's diameter and all of it, `depthTest === false`, and that **a shot dead into the portrait still damages the boss**, which is the guard on `weapon.js`'s non-recursive raycast. The roster is hardcoded in the driver rather than read out of the game, so a dropped or renamed image fails instead of being agreed with, and 80 `spawnBoss()` draws have to produce every name on it and nothing else.
    - **It finds the portrait by `boss.identity.material`, never by child index.** The orb carries two sprites and the glow halo is parented first, so `children[0]` is the halo — whose map is a generated canvas with no `.complete`, which means an index here doesn't fail loudly, it hangs the `waitForFunction` for its full 30s timeout. That is exactly how it broke when the halo was added. It now also asserts the portrait is the *last* child, which is what stops the additive halo painting over the face.
  - Two screenshots for the parts assertions can't judge: the `BOSS ROUND` flash with a name under it, and a close-up of the orb. Whether the ring of purple left around the face still reads as the boss underneath is the entire justification for `BOSS.portraitScale` being under 1, and no number tells you that. Note `rounds.bossIdentity` is null by the time the screenshot section runs — the retry test reset it — so the flash shot draws its own name through `spawnBoss()`.
  - The speed checks **measure displacement** — a lone enemy's position over ~450ms of real frames, timed off the rAF timestamp — rather than reading `speedScale` back. Asserting the multiplier is 1.5 proves nothing about whether `update()` multiplies by it. One frame of travel is 2-3% of that window, so they compare against a percentage band, and the *measured* case uses round 5 (3.0x) where the bands can't overlap; round 2's exact `1 + speedStep` is checked as a pushed value and as flash text instead. It also measures the boss, since one multiplier serving both tiers is the thing that could silently regress.
  - The ladder is checked as **equal differences, not equal ratios**, plus one assertion that round 3 is `1 + 2 * step` and *below* what compounding would give. Round 2 is identical under both formulas, so it's round 3 where a reintroduced `**` would show, and nothing else in the suite would notice.
  - The spawn-rate check **counts real spawns** — it times how long a fixed 12 take at scale 1 and again at round 5 — because `currentSpawnInterval()` returning the right number proves nothing about whether the spawn timer is actually fed from it. Two things make that measurable: it flattens the within-round ramp by setting `ENEMY.spawnInterval = spawnIntervalMin` through `__game.config` (restored afterwards), or `elapsed` advancing between the two runs moves the interval underneath the comparison; and it keeps that flat interval **well above a frame time** (0.4s), because the spawn timer is decremented once per frame and reset to a whole interval, so each spawn really takes `ceil(interval / dt)` frames. At 0.1s and ~95fps that rounding alone costs 5% of the rate at 1x and 13% at 3x, which reads as the scaling being weaker than it is — it's what made the ratio come out 2.63 against an expected 3.00. Timing a fixed count also avoids the ±1 discretization a fixed window leaves on the slower run. The reset ordering has its own assertion in the restart section: after dying in round 2 and clicking retry, `spawnTimer` has to be a full `ENEMY.spawnInterval`. The wrong order leaves it a third short — invisible unless measured, and that one check is the only thing that catches it.
  - The layout of the two-line flash is checked with `getBoundingClientRect()`: the speed line below the title, centered on it, smaller than it, and above the crosshair. A stylesheet slip that stacks the lines or hides one behind the other is invisible to a text assertion. It also screenshots the readout mid-round, since four fields on one line can crowd or wrap and no assertion would notice. Three traps it encodes: **score assertions must be relative** (the driver has already banked floater kills by the time it reaches the boss, so asserting an absolute total is asserting the driver's own history), and **the opening announcement is a race** — `isRunning()` flips inside the pointer-lock handler, which can land before the frame that flushes the announcement, so wait on it rather than sampling once. Third: **anything that sets `rounds.kills` by hand must derive the number from `ROUNDS.killsPerRound`.** A hardcoded tally that was safely mid-round under the old quota sits *above* a retuned one, and the next `update()` quietly starts a second boss round underneath every assertion that follows — which is how the readout screenshot's `kills = 37` broke when `killsPerRound` came down to 30. Its announcement screenshot uses a stretched `animationDuration` *plus* a negative `animationDelay` to park the flash on its opaque plateau; stretching alone lands inside the fade-in and looks worse than doing nothing.
- `%TEMP%\doomslop-popups.mjs` — 27 assertions on the score popups, plus a screenshot. The placement checks re-derive the expected pixel from raw trigonometry (`fov`, `aspect`, distance) instead of three's projection, so they can't agree with `hud.js` by sharing its bug, and one case kills on each side of the crosshair — a popup pinned to the screen center passes every "dead ahead" check. **Sample animation over wall-clock fractions of the configured life, not a frame count:** headless Chrome runs uncapped here (~95fps), so counting frames covers a much smaller and less predictable slice than you'd expect, which shows up as "it never fades" and "the ease-out looks linear" — any easing curve is nearly straight over a short enough early window. Its screenshot kills one of two floaters placed symmetrically about the crosshair, so the popup landing opposite the survivor is visible rather than argued.
- `%TEMP%\doomslop-look.mjs` — 16 assertions on the look-input path, guarding the camera-jump bug. It drives the real `document` mousemove listener with synthetic `MouseEvent`s, since Chrome honours `movementX` from the init dict — and asserts that first, because every check below it is vacuous otherwise. Covers the per-event spike cap (at the cap, one pixel over, one axis taking the whole event with it, and a spike mid-flick costing only itself), that the cap does **not** become a per-frame cap (four near-cap events in one frame must add up to four times the ceiling), and that no unread delta survives losing pointer lock — through a pause *and* through death and retry. Run it after touching `input.js` or `player._look()`.
- `%TEMP%\doomslop-cheat.mjs` — 31 assertions on the `~` skip cheat and the top-left controls panel, plus a screenshot. Synthetic `KeyboardEvent`s carrying `code` drive the real `input.js` listener (asserted first, or the rest is vacuous). The round number going up is the easy part; what it's really there for is the three things a skip must *not* do: **pay out a boss it never killed** (it reaches a real boss the config-derived way, then checks the score is unmoved against `BOSS.scoreValue`), **heal** (skips at 37 HP, asserts 37, then trips the real boss-death transition on the same damaged player and asserts 100 — the contrast is the point, since asserting only the first would pass on a build where nothing heals at all), and **fire once per frame** (a press plus 40 auto-repeats over 20 frames must advance exactly one round, which is the bug an `isDown()` implementation has). Also that `~` at the pause screen neither acts nor banks, that the breather resumes into a real fight with floaters actually spawning, and that the additive speed ladder survives being skipped up. The panel checks measure the corner with `getBoundingClientRect()` — top left, clear of both the minimap and the readout, and the minimap still pinned top-right — and pair up the key/action spans, so a row added or dropped moves the count. The `M` row is asserted as `MUSIC ON|OFF` rather than as a literal, since it's the one row carrying live state; `MUSIC --` there means the frame loop never wrote it, the same tell `HP --` gives. The toggle itself is `doomslop-music.mjs`'s. Run it after touching `rounds.js`, `input.js`, or the HUD corners.
- `%TEMP%\doomslop-jump.mjs` — 23 assertions on the space-bar jump, plus a **pair** of screenshots. The arc is *measured*, not read back: player and camera Y are sampled every frame off a rAF loop and compared against the closed form, since asserting `velocityY === jumpSpeed` after a tap passes on a build that teleports the view up and leaves it there. Four traps it encodes:
  - **The apex band is derived from the measured frame time, not picked.** Explicit Euler steps velocity before position, so a *correct* implementation undershoots `jumpSpeed²/(2·gravity)` by `jumpSpeed · dt / 2` — 3% of the hop at 95fps and 5% at 60fps. A flat 4% band would fail on a slower machine; predicting the undershoot from the sampled `dt` is tight at any frame rate (measured 1.020u against a predicted 1.021u). Airtime carries a few frames of slack on top of its percentage because it's quantized at both ends.
  - **A launch is a grounded → airborne transition, so the recorder has to start before the tap.** Tapping first and recording afterwards misses the transition and reads as *zero* jumps — which is how the held-key check first failed against a working build. Each case banks a grounded sample first and asserts it was grounded, or the count is vacuous.
  - **Cases have to start from a known *input* state, not just a known position, and with held-state input that means dispatching `keyup`.** A case that only sends `keydown` leaves Space down for every case after it, which reads as the player pogoing through their measurements. `quiet()` releases the key and clears `input.presses`; `tap()` is down, three frames, up — the hold is not padding, since the game polls the held state once per frame and a press that begins and ends between two frames never happened.
  - **The bounce is checked as a *period*, not a count.** Holding Space for three airtimes has to produce launches spaced one airtime apart; a bare "3 or more launches" would be satisfied both by a build that relaunches in mid-air (short gaps) and by one firing every frame (dozens). The gaps are what say "as soon as you hit the ground" and nothing sooner.
  - Behaviour covered: resting flat with no accumulated gravity, the camera following the arc rather than just `player.position` (only `_syncCamera()` connects them), a held key bouncing at the arc period and coming to rest once released, a mid-air tap neither double-jumping nor being banked for the landing (**one** launch over two airtimes), the other side of that — a press made in the air and *still held* at touchdown launching again (**two**, so it can't pass on a build where nothing fires), air control and the X/Z clamp still applying mid-flight, Space doing nothing while paused and not surviving the resume in either form, and a retry after dying mid-jump starting flat. Plus the one that guards a boundary in another file: **a floater reaching the player mid-jump still lands its hit**, which is what catches anyone making `enemies.js`'s contact check 3D.
    - The two mid-air cases differ only in the window they record: the held-through one stops just past the second landing, because the key is still down and a longer window would catch a third hop and fail an assertion that is counting landings. Repeating is the held-key case's subject, not this one's.
  - The screenshots are a matched pair — the same frame grounded and at the apex, enemies pinned at fixed points so height is the only difference. One shot alone can't be judged: a 1-unit rise on a 1.7-unit eye height is subtle, and "the view lifted" and "the floor dropped away" look identical in isolation.
- `%TEMP%\doomslop-roll.mjs` — 25 assertions on the strafe lean, plus three screenshots of the horizon (level, and leaning each way). Run it after touching `player._roll()`, `_syncCamera()`, or `PLAYER.strafeRoll`. Four things it encodes:
  - **The easing is sampled on wall clock, not after a frame**, like the popups and flash drivers: the frame straddling an `evaluate()` boundary carries a fat dt, and a frame count says nothing about where on a curve a given moment falls. 40ms is ~27% of the way at `strafeRollSpeed` 8; it first failed against a *working* build for exactly this. The check is that 40ms in it's a long way short of the target, which is what fails on a build that assigns the angle outright. **The recovery half of that had to be taught the same lesson twice**: it sampled after `frames(1)` against a fixed fraction, and started failing against an unchanged, correct build when the portals added two permanent point lights and frames got ~5ms longer — at `strafeRollSpeed` 8 a 28ms frame is 22% of the way back where a 57ms one is 45%. It's now 40ms of wall clock inside a two-sided band.
  - **The lean has to be driven by the keys, so two cases take the movement away**: strafing into a wall (with its own assertion that the wall really stopped the player, or the case proved nothing) and strafing with `PLAYER.moveSpeed` forced to 0. Both must still lean.
  - **The one check that isn't about looks: a shot from a rolled camera still hits.** An enemy placed along the *real* camera forward after the roll has settled, so it tests the aim path rather than the driver's trigonometry. That's the guard on roll being innermost in the `YXZ` composition.
  - **Cases start from a known *input* state, not just a known angle** — `quiet()` dispatches `keyup` for all five keys and clears `input.presses`, or a case that only sent `keydown` leaves the key held for every case after it. Same rule the jump driver learned.
- `%TEMP%\doomslop-spawnheight.mjs` — 23 assertions on the spawn-height band and the levelling-out, plus a screenshot. What it exists to measure is a **slope, not a position**: the settle is tied to ground covered, so it runs the same flight at `speedScale` 3 and 9 and asserts both shed the same height per unit travelled. "It ends up at `hoverHeight`" passes on a build that snaps it there, and a descent rate in units/sec passes on a build that arrives from overhead in a fast round — the two scales are what separate those.
  - The band is **pinned through `__game.config`** (`spawnHeightMin = spawnHeightMax = h`, restored immediately) for every measured case, because the expected slope depends on the spawn height and a driver that re-derived it from a random spawn would be reimplementing the formula it's checking. The distribution checks use the real random band: 60 spawns, all inside it, spread over most of it, and landing on both sides of the hover height.
  - Arrival is sampled **every frame**, since the failure to rule out is an overshoot that a before/after pair steps straight over. It asserts the descending case never dips below `hoverHeight` and the *rising* case never crosses above it — the rise gets its own case because the settle is signed and a sign slip is invisible on the descending half. The height at contact is checked against `hover + slope * lastDistance` rather than against `hover`: contact happens ~1 unit out, so a correct implementation still has one stride of height left, and asserting it arrives exactly level would fail on working code. **That residual's tolerance is one stride, and the stride is measured out of the samples rather than picked** — the flight runs at `speedScale` 12, where a frame covers 0.28u at 95fps but 0.74u at 36, which is more than the whole contact reach: the enemy then sheds the last of its height in one step and arrives dead level, and the fixed band it used to carry fails a perfectly correct build. It started doing so when the portals' two lights slowed the frame, the same way the roll driver's did.
  - Also: `spawnDistance` is still the **horizontal** distance at every height (folding the height into it would pull high spawns closer on the plane contact is measured on), the band clears the floor and the walls by `ENEMY.radius` at both ends, an enemy spawned level has `levelSlope === 0` and doesn't drift, 20 `spawnBoss()` draws all sit at exactly `BOSS.hoverHeight`, and **an enemy near the top of the band can still be shot down** — placed along the *real* camera forward after the pitch is synced, so it tests the aim path rather than the driver's trigonometry, with the resulting height asserted so it can't quietly become a level shot.
  - The screenshot lays the band out evenly and **in order at 11 units**, not at the 25-unit spawn distance: the whole 5-unit band is only ~150px tall out there and reads as a flat row, so the shot can't be judged. It also waits out `POPUP.life + EFFECTS.particleLife` first — the previous case's popup and sparks are on timers, so `removeAll()` doesn't clear them and they land in the middle of the frame.
- `%TEMP%\doomslop-music.mjs` — 36 assertions on the `M` music toggle, plus a matched screenshot pair of the panel corner on and off. Run it after touching `sound.js`'s music path, main.js's key reads or `hud.updateMusic()`. Three things it encodes:
  - **"Starts from the beginning" is taken off the `start()` *argument*, not off a game variable.** It wraps `ctx.createBufferSource` and records every music start's `offset` (filtered by `node.buffer === sound.musicBuffer`, since the noise bursts come through the same factory), then asserts each one is exactly `SOUND.music.loopStart`. A build that resumed mid-track would satisfy every other check in the file — "a new source exists and it's audible" is true of a resume too.
  - **Audible is measured on the music bus with an `AnalyserNode`**, like the sound driver: `musicSource !== null` only says a node was built. The silence side matters as much — the peak has to come back under the floor after a toggle off, which is what separates "stopped" from "still playing at the same level".
  - **Its own wiring guard has to consume the press it dispatched.** The check that a synthetic `keydown` reaches `input.js` is a real tap, so letting a frame drain it turns the vacuity guard into the first toggle and every default-off assertion after it fails. It reads `presses.has('KeyM')` synchronously and then calls `consumePress()` itself.

- `%TEMP%\doomslop-sound.mjs` — 53 assertions on the audio. **Its music section has to turn the music on first**, with a real `M` keydown, since the bed is off by default; the pair of checks before that is what says the default is real rather than the toggle being untested. Note it *scales* the shell's material colors rather than retuning `brightness` through config, because `createShell()` bakes it at import time — and it deliberately leaves the fog and background alone, since how far the shell has to sit above them is the question the sweep answers. `%TEMP%\doomslop-viewcost.mjs` prices the two extra renders: **~3.9 ms/frame at `resolution` 0.5** (1280×800 → res 0: 25.5fps, 0.5: 23.2, 0.75: 20.6, 1: 18.9; at 480×300 all four are 60fps), near-exactly quadratic in resolution, which is the same fill-rate finding `-lightcost.mjs` and `-portalcost.mjs` record. `resolution` 0 is the honest floor rather than an off switch — `renderViews()` clamps to 1×1, so both renders still happen and everything but their fill is still paid.
  - **Those two costs compound, and they are why several drivers had to stop counting frames.** Two permanent point lights plus two preview renders is ~9 ms/frame at 1280×800, so a fixed frame count now covers far more wall clock than it used to. It broke the roll driver's recovery sample and the spawn-height driver's contact tolerance (both recorded above), and then this driver's own mid-jump case, which waited three frames after a launch and stepped into the portal on the frame the player touched down. Its airborne state is now *written* rather than taken off the live arc, the same thing `velocityY` always was.
- `%TEMP%\doomslop-hitmarks.mjs` — 70 assertions on the damage feedback and the two vitals readouts, plus six screenshots. Run it after touching `player.js`, `enemies.js`'s contact checks, the HUD's full-screen layers, or the bottom-center vitals stack.
  - **Nothing in it calls `hud.hitFrom()` directly.** Every directional case stages a *real* contact hit — a floater placed just inside `kind.radius + PLAYER.radius` along a computed bearing, then two frames — so the path under test is `enemies.update()` → `takeDamage(amount, source)` → `onDamage` → `bearingTo()` → the wedge. A driver that called the HUD method with an angle it computed itself would be asserting its own trigonometry.
  - **The wedge is measured in screen space off `getBoundingClientRect()`**, not by reading the inline `rotate()` back. The bearing lives on an outer anchor and the animation's `translateY` on the child, so the placement only exists as a composition of the two — and a string comparison would pass on an indicator pinned at the crosshair. 25 (yaw, bearing) pairs, the same sweep the minimap driver runs and for the same reason.
  - **Both negative cases carry their own vacuity guard.** "A hit at 0 HP raises nothing" and "a kill raises nothing" would pass on a build where nothing ever flashes, so each is preceded by a positive case proving the feedback does fire. The 0-HP one takes damage directly with no frame boundary, because letting that frame run trips `endGame()` and stops the loop every later case needs.
  - **The harness must not top health up through `player.refillHealth()`.** That fires `onHeal`, which flashes the green vignette the baseline was about to assert was absent — it's what broke four checks on the first run. Write `player.health` instead, the same thing `player.reset()` does, and strip the classes *after*. `player.armor` is written the same way and for the same reason, even though `refillArmor()` has no hook: the blue flash is raised by `main.js`'s `onCollect`, so a *collection* staged to set up an armor level would tint the frame the next case measures.
  - The vignette's opacity is read by **seeking** its animation (`getAnimations()[0].pause()`, then `currentTime`) rather than sampling over wall clock, which is what makes the peak and tail figures exact. Both tints are parsed out of the computed `background-image`, taking the **last** `rgba(...)` match — `transparent` computes to `rgba(0, 0, 0, 0)` and is the first stop in the gradient.
  - Also: the pool built from `HITMARK.pool` and recycled round-robin, six wedges up at once from six sides, pitch invariance at ±70°, the boss's cooldown call site as well as the floater's contact one, paint order (the tint under every readout), a heal landing inside a damage flash *replacing* the red, the boss-death refill flashing green (reached the config-derived way), and placement/size checks on both vitals labels measured with a `Range` — including that `HP` and `AP` are **typographic twins** rather than a heading and a footnote (same font size, same weight, same tracking, differing only in color), which is the one thing a stylesheet slip would undo.
  - **Both bars are measured in pixels off `getBoundingClientRect()`, never by reading the fill's inline width back.** A percentage width that never lays out — a fill outside the element it's meant to be filling, an auto-width track — agrees with itself perfectly in the style attribute. Three levels are sampled and the fraction is checked against `health / PLAYER.maxHealth` (and the armor bar's against **`PLAYER.maxArmor`, not `maxHealth`** — the one assertion that catches a copy-pasted divisor), with the *track* asserted to keep its width and the fill to keep its left edge: a build that resized the whole element would pass proportionality and read as the HUD shrinking rather than as health draining. Two traps: the fill carries a **CSS transition**, so a sample has to wait out the 140ms or it measures the animation instead of the level; and every level is reached by writing `player.health` / `player.armor` rather than through the refill methods, for the reason two bullets up. One case lands a **real contact hit** and asserts the bar dropped by `ENEMY.touchDamage`, since the written levels can't show the game drives it.
    - **The absorption order is asserted through the bars, not just through the numbers.** A hit inside the AP pool has to move the armor bar and leave the health bar *and* the HP number exactly where they were; a hit bigger than the pool has to spend it and spill the remainder onto health, with **both** bars moving — which is what proves the overflow was split rather than dropped or double-charged.
    - **The stack's grouping is measured as well as its contents**: the armor pair above the health pair rather than beside it, the two tracks the same width and on one center line, and the seam *between* the pairs wider than the gap inside either one. That last is the whole point of `#armor`'s bottom margin — four rows evenly spaced read as four unrelated readouts instead of two labelled bars.
    - **The killing blow is the last thing in the file, and it has to be.** `endGame()` releases the pointer lock, so nothing after it can measure a live frame — the case asserts that (`isRunning()` false, overlay up) before asserting the bar emptied. It's worth its own case because `hud.update()` runs *outside* main.js's `if (running)`: the bar is written on the death frame, and CSS ignores a negative width outright, so an unclamped fraction would leave it sitting wherever it last was behind `YOU DIED`.
  - Six screenshots, since none of the above says whether any of it reads: the red flash, the green one, a matched control with the wedges up and no vignette at all, the health bar at a quarter full and empty, and the whole four-row vitals stack with both pools part-spent. The wedge control is what showed they were too small and too close to the reticle — they passed every assertion while reading as debris stuck to the crosshair; the vitals shot is the equivalent for the stack, since "green above blue, grouped in pairs" is a thing to look at rather than a number.
- `%TEMP%\doomslop-pages.mjs` — 14 assertions on the **production build under a path prefix**, which is the only way to catch a wrong Vite `base`. It runs its own static server that serves `dist/` at `/DoomSlop/` and logs a status per request, so a 404 on an asset is reported rather than just showing as a blank screen. Everything is asserted through the DOM, since Vite strips `window.__game` from a production build — reading `HP 100` out of `#health` is the proxy for "the bundle booted and reached the frame loop". Run it after touching `vite.config.js`, `index.html`, `bosses.js`, `sound.js`, or anything about the deploy. It also owns the `#build` checks — the build number is static HTML, so this is the driver that proves it survived the bundle, and it measures the corner placement with `getBoundingClientRect()` against `#readout` and `#minimap` rather than trusting the CSS. Note that neither `npm run dev` nor `npm run preview` can catch this class of bug: both serve from the root, where a base of `/` works.
  - **Its per-request log is the check on every imported asset**: every portrait and the music file have to come back hashed from `/DoomSlop/assets/`, which is what proves the ES-import path survived the build rather than resolving above the prefix. The roster is hardcoded here rather than read out of the bundle, same reasoning as the rounds driver's — a dropped or renamed file has to fail rather than be agreed with. **The music assertion has to run after a real `M` keypress**, not just after the overlay click: the bed is off by default, so the toggle is now the only thing that fetches the mp3. That also makes this the one driver exercising the toggle against a bundle with no `window.__game` in it — a synthetic `keydown` carrying `code` and `#musicstate`'s text are all it has, which is exactly the user's path. The 404 sweep is repeated after the click as well as before it.

When a driver places an enemy by hand, **keep it above the floor.** The arena is solid, so a target buried under `y=0` is legitimately unhittable — a test that positions one there is testing nothing. This is how the gameplay driver used to place its target.

A driver that places a **pickup** by hand has the opposite problem: `pickups.update()` rewrites Y from `PICKUP.hoverHeight` every frame, so a drop parked on the ray for a raycast test has to be fired at in the same `evaluate()`, with no frame boundary in between.

`main.js` exposes `window.__game` (player, enemies, pickups, weapon, effects, sound, hud, minimap, rounds, input, config, score/state getters) behind `import.meta.env.DEV`, which is how the gameplay driver reaches in. Vite strips it from production builds — verified by grepping `dist/`.

Two things the gameplay driver learned the hard way, worth preserving in any replacement:

- **Let real frames elapse after setting player state.** Writing `player.yaw` then immediately calling `weapon.fire()` tests the harness, not the game — `_syncCamera()` hasn't run. Wait ~120ms.
- **Freeze `enemies.spawnTimer` to a huge value** during targeted assertions, or the spawn timer injects an extra enemy mid-check and the count assertions fail spuriously.
- **Read effect buffers after a frame boundary.** `effects.update()` writes `drawRange` and the position buffer later in the same frame as the shot, so reading them synchronously after `fire()` sees stale values. `await` a `requestAnimationFrame` first.
- **`window.__game.config` lets a driver retune live** (the config objects are read at use time). The effects screenshots stretch `tracerLife`/`particleLife` this way, since a 0.07s tracer is otherwise impossible to capture.

Two more assertions worth keeping:

- Read `#health` / `#armor` / `#score` text. They start as literal `HP --` / `AP --` / `SCORE --` in the HTML and are only filled in by `hud.update()`, so `HP 100` proves the loop actually reached the HUD rather than dying at import time. `AP 0` is the useful one for the armor pair — a run starts with no armor, so the placeholder is what distinguishes "empty" from "never written".
- Always check `console --errors` / `pageerror`. A dark scene and a failed scene are hard to tell apart in a screenshot.

Headless Chrome needs `--use-angle=swiftshader --enable-unsafe-swiftshader` or WebGL won't come up at all. Pointer lock *does* work headless, so the click-to-play path is testable.

## Architecture

`src/main.js` owns everything: it constructs the renderer, scene, camera, and each system, then drives them from one `requestAnimationFrame` loop. Systems never call each other's `update()` and never schedule their own frames — if something needs to run per-frame, main.js calls it.

Boundaries that are load-bearing:

- **`config.js` is the only place tunable numbers live.** Speeds, damage, spawn rates, sensitivity. Gameplay code reads from it; it must not hardcode values. Balancing should stay a single-file edit.
  - **`PICKUP` is split into a shared part and three *faces*.** Everything physical about a drop — `size`, `radius`, `hoverHeight`, the bob, the spin, `life`, `shrinkTime`, and both rolls — sits on `PICKUP` itself, because the items are one cube with a different picture on it and a tunable that differed between them would be a tunable that shouldn't exist. `PICKUP.health`, `PICKUP.armor` and `PICKUP.boots` hold only what *is* different: three colors and a `glow` block. That's also the block a drop's `kind` points at, so the split is the thing shared code reads through rather than a filing convenience.
    - **`PICKUP.boots` carries two fields the other faces don't — `duration` and `boost` — and that's the rule holding rather than bending.** A face holds what differs, and what differs about the boots is that collecting them starts a timer instead of filling a pool. They are *effect* numbers, not physical ones, so they don't belong on the shared block; a `duration` on `PICKUP` would be a tunable the other two faces have no meaning for.
      - **`boost: 3` means move speed and jump *height*, and `player.js` takes its square root.** The apex is `jumpSpeed² / (2 · gravity)`, so tripling the height is `jumpSpeed × √3` — applying 3 to `jumpSpeed` directly is a *nine*-fold hop. This is the one config number in the file that's interpreted rather than just applied, which is why the note lives next to it as well as here.
      - The same balance constraint `PLAYER.jumpSpeed` carries caps it: `eyeHeight` plus the boosted apex has to stay under `WORLD.wallHeight` or a jump sees out over the arena. At 3 that's 1.7 + 3.17 against a wall of 8; at 8 the player clears them. A constraint noted in `config.js`, not a clamp in code — same as the uncapped `speedStep` ladder.
    - `dropChance` is "does anything drop" and the shares are "which one" — **two rolls, not one chance per item**, so the overall drop rate stays a single number and a fourth item would move the split rather than dilute it. `_rollFace()` is a cumulative walk over `armorShare` (0.35) and `bootsShare` (0.15) with **health as the fall-through**, which is why there's no `healthShare` to keep in step: the three always sum to 1 because the last one isn't a number.
      - The weighting is deliberate in both directions. Armor is a minority because health gets the player out of trouble they're already in where armor buffers trouble they haven't met, so the other weighting would mostly hand shields to a player at 20 HP. The boots are rarest because they're the only drop that changes how the game *plays* rather than what the bars read — common enough to be a state the player is sometimes in, not one they expect.
  - Two blocks hold **CSS strings rather than `0x` literals**, and for the same reason: their colors are consumed by the Canvas 2D API, not by three. `MINIMAP`'s are drawn on the radar canvas; each `PICKUP` face's `bodyColor`/`iconColor`/`edgeColor` are drawn into that face's generated texture. `iconColor` is named for the job rather than the shape — one field paints the health cross, the armor shield and the boot — and a face's `glow.color` is a `0x` literal, because that one goes to a three light and material, so the one block carries both conventions on purpose.
  - **`HITMARK` holds exactly one field, `pool`, and that's the whole split.** `hud.js` reads the count to build the wedges, so it's a number something in the game consumes; the wedges' size, their distance from the reticle, their color and their lifetime are pure appearance and live in `style.css`. Same division `POPUP` makes, in the same direction — and the distance in particular is a *tuning* number that was got wrong once and fixed by looking at a screenshot, not by reading a config file.
  - `PICKUP.health.glow.intensity` (9) is less than half `ENEMY.glow.intensity` (20) even though the drop reads as the brighter effect, and that's geometry rather than taste: intensity is candela at 1/d², and a cube at `PICKUP.hoverHeight` 1 lights a floor `(1/1.6)² ≈ 0.39` as far away as a floater's at 1.6. Same reasoning as `BOSS.glow` in the other direction, where a radius-3 orb needs 120 because nothing it lights is nearer than 3 units.
    - **The armor and boots cubes' 11 against the health cube's 9 is the one number here set by the eye rather than by geometry**, since all three hover at the same height and light the same floor. Blue at equal candela reads dimmer than green against a dark floor (yellow sits between them), and what the drops should match is how *present* they look from across the arena, not what the number says. Every `haloScale` is the 2.2 everything glowing in the game holds — see `BOSS.glow`.
    - **Yellow is the fifth and last hue, and the palette is why there won't be a sixth.** Red and purple are trying to kill you, green and blue are levels on the bars; yellow was available precisely because it's neither. A fourth drop can't be told apart by color alone and would have to be distinguished some other way.
  - **`PORTAL` holds one constraint that stands in for code: `exitOffset` must stay above `depth`.** Arriving `exitOffset` out from the exit wall has to be *outside* the exit's own trigger depth, or the arrival immediately counts as stepping through and the player ping-pongs between the two. That's what lets `portals.js` carry no cooldown and no travel state at all — a constraint noted in `config.js` rather than clamped in code, same as the uncapped `speedStep` ladder. `depth` has a floor too: `_clampToArena()` stops the player `PLAYER.radius` short of every wall, so anything under 0.4 could never fire.
    - **Its cyan is the deliberate bend of the five-hue rule two bullets up**, and the only one. `PICKUP.armor` already owns azure, so this is a sixth hue by the letter of it — affordable because a portal and an armor cube are never told apart *by color* in the first place: one is a 3-unit square standing in a wall, the other a small cube bobbing at knee height. The rule is about things that have to be distinguished at a glance on a radar, which is why a fourth *drop* still can't have a color of its own.
    - `glow` is the same block shape `ENEMY`, `BOSS` and every `PICKUP` face carry, and `haloScale` is again over 1 for the reason it is there — the glow is the part outside the square. `intensity` is read against `lightOffset` and `size/2`, not against the area it covers, which is why a doorway several times a drop's size wants a number near the drop's.
    - **`PORTAL.view` holds the three preview numbers, and each of them is a different kind of thing.** `resolution` (0.5) is a fraction of the live drawing buffer and is the **performance knob** — the cost is fill rate and `-viewcost.mjs` measures it as near-exactly quadratic, so halving it is the first thing to turn down, exactly as `EFFECTS.glowPool` is for the lights. `tint` (0.22) is appearance, mixed in display space. `brightness` (1) is the odd one: it's **baked into the shell's materials at import time**, so unlike every other number in this file it can't be retuned live — and it's a deliberate lie. The photometrically honest figure is ~0.41 (the shell is lit by nothing, where the arena's walls catch the ambient and the key light), and at that value the doorway reads as *more wall* rather than as an opening. The shell has to sit visibly above the fog it shares with the arena, which is the thing `-viewtune.mjs`'s brightness sweep exists to judge.
  - `MINIMAP`'s three drop blips are `healthColor`/`healthArm`/`healthThickness`, `armorColor`/`armorArm` and `bootsColor`/`bootsArm`, rather than the `…Color`/`…Radius` pair the two dots use, because none of them is a dot: `arm` is the half-length of a cross stroke, the shield's half-width, and the boot's half-*height*; `thickness` is a stroke's width. Naming any of them `…Radius` would invite someone to draw it with `arc()`. The filled silhouettes need no `thickness`, and `armorArm` is a touch under the cross's for that reason — matching their extents would leave the filled shape much the heavier of the two. **Every glyph's proportions live in `minimap.js`, not here**, alongside the cube icons' in `pickups.js`: which marks make a shield is the shape, not a tunable.
    - **`bootsArm` is deliberately the largest of the three (4.8 against the cross's 3.4), and that's legibility rather than importance.** A cross is two bars and a shield is one tapering outline, either of which survives being six pixels across; a boot is a collar, a leg and a sole that only read as a boot *together*, and at the cross's size all three land inside about six pixels and it comes out a yellow smudge. This is the smallest it survives at, and still small enough that an enemy dot drawn over it wins the spot.
  - **`wallColor`/`wallThickness` and `portalColor`/`portalThickness` are the arena outline, and they carry the one hue on this canvas that's outside the five-color palette.** The cyan is `PORTAL.glow.color` written out again in this file's CSS-string convention rather than converted from the `0x` literal at runtime — the two are read by different APIs (a three light and a 2D context), and a blip that didn't match the doorway it points at would stop tying them together. It's the same exception `PORTAL.glow` itself makes, and affordable for the same reason: a portal and an armor cube are never told apart *by color*, since one is a segment welded into the outline and the other a small upright shield somewhere inside it.
    - **The portal is thicker than the wall rather than longer, and that's the whole tuning decision.** `PORTAL.size` is 3 units of a 60-unit arena — about 7px at `MINIMAP.size` 148 — so the temptation is to stretch it to something findable. Don't: the segment's *ends* are where the doorway's edges are, and a player who walks to them has to find a portal there. Weight is the free dimension; length isn't.
    - `wallColor` carries its alpha in the string rather than getting a separate field, since nothing reads it as a number. It's deliberately dim: the walls are the only *static* thing on the canvas and the only reason the rim reads as a distance rather than as an arbitrary window, but they're the backdrop everything else is standing on — at full strength the box competes with the dots for the eye, and the corner is all the player actually needs.
- **`input.js` reports hardware, not intent.** Held keys, accumulated mouse delta, whether the trigger is down. It has no notion of "forward" or "shoot" — `player.js` and `weapon.js` interpret. Keep gameplay meaning out of it.
  - `consumeMouseDelta()` is destructive: it returns the accumulated delta and zeroes it. Exactly one caller per frame, or look input gets eaten.
  - **`presses` / `consumePress(code)` is the edge, `keys` / `isDown(code)` is the held state.** Anything that should happen once per tap — the `~` skip, the `M` music toggle — has to use the former: `isDown()` in the frame loop is true every frame the key is down, so one tap on a 60fps display fires sixty times. (The jump is the one deliberate exception, and only because `grounded` gates it — see `player.js`.) `consumePress()` is destructive for the same reason `consumeMouseDelta()` is, and one physical tap therefore reads true for exactly one caller. `keydown` filters `e.repeat` so the OS auto-repeat isn't a stream of presses, and it records `e.code` rather than `e.key` because `~` only arrives as a key with Shift held while `Backquote` is the physical key either way.
  - Losing pointer lock clears held keys and the trigger, so nothing sticks after Esc or alt-tab. It clears unread `presses` too, alongside the mouse delta and for the same reason — main.js only drains them while running, so a tap during a pause would otherwise fire on the frame after resume.
  - **Two guards in here exist because the camera used to jump to a random heading. Both are load-bearing and neither is obvious from reading the happy path.**
    - **A mousemove whose `movementX`/`movementY` exceeds `INPUT.maxLookDelta` is discarded whole.** Under pointer lock the browser can report half a screen width of movement in one event when the underlying cursor gets warped; at `PLAYER.lookSensitivity` a 960px reading is a 121° teleport, which is exactly what the bug looked like. The event is dropped rather than clamped — a spike is a bad *reading*, so the honest response is to have seen nothing, where clamping still swings the view 50° on invented data. Both axes go together: a reading wrong on X isn't trustworthy on Y.
      - **This has to live here, not in `player.js`.** It's only decidable per-event; by the time `_look()` reads the accumulator the events are summed and a single 960px spike is indistinguishable from legitimate fast movement across a slow frame. That's also why the cap is a per-*event* ceiling and must never become a per-frame one — a real flick arrives as several events and has to add up.
      - The threshold sits in its own `INPUT` block rather than next to `PLAYER.lookSensitivity`, because sensitivity is interpretation (`player.js`'s job) and this is noise rejection (`input.js`'s job).
    - **`pointerlockchange` zeroes the accumulator, in both directions.** `player.js` only consumes it while the game is running, so movement landing after a session's final `update()` — a flick that ends in the same breath as Esc — used to sit there through the whole pause and get applied as one jump on resume. Same path on death, where it would rotate a view `player.reset()` had just zeroed. The `if (!this.locked)` block below it handles keys and the trigger; this is deliberately outside it.
- **The camera *is* the player.** No body mesh — nothing renders from another viewpoint. `player.js` keeps `yaw`/`pitch` separately from `camera.rotation` and applies them via `YXZ` Euler order so pitch can be clamped without gimbal problems. Mutate `player.position`/`yaw`/`pitch`, then let `_syncCamera()` push to the camera.
  - **`_roll()` is the strafe lean, and it's the third camera angle — but not a third *input*.** `roll` eases toward `±PLAYER.strafeRoll` while A or D is held and back to 0 when they're released, so unlike yaw and pitch it's state the game owns rather than a reading it accumulates. It's read off the **keys**, not off movement achieved: walking is positional with no velocity to read, and a player strafing into a wall is still leaning. A+D cancel, like they do in `_walk()`.
    - **`_syncCamera()` writes it to `camera.rotation.z`, and `YXZ` order is what makes that safe.** Z is innermost in that composition, so it's a roll *about* the already-aimed view axis — it can't disturb the pitch clamp, and `getWorldDirection()` is unchanged, so a shot from a rolled camera goes exactly where the crosshair is (the roll driver fires one for it). The muzzle *does* swing with the view, because `weapon.js` takes its screen-space offset off the camera's own right/up columns — which is what keeps the tracer starting from the same spot on screen.
    - Eased on an exponential approach at `PLAYER.strafeRollSpeed`, clamped at 1 so a long frame can't overshoot and oscillate. The recovery matters more than the tilt-in: releasing a strafe key stops the player dead, and snapping the horizon back reads as the camera being knocked.
    - `reset()` zeroes it, like `velocityY` and `boostTime` — dying mid-strafe would otherwise open the retry with the horizon tilted and nothing to level it until the player strafed again. **This is the one place in the game where the horizon moves**, which is why `strafeRoll` is a few degrees and has to stay there; see `config.js`.
  - **`teleport(x, z, turn)` is the whole of what a portal can do to the player**, and it's four lines: X and Z, `turn` **added** to the yaw, then `_syncCamera()`. X/Z only because `_jump()` owns Y — going through a portal mid-hop keeps the arc, which is what makes a jump through one read as a jump. The turn is added rather than assigned so the heading the player walked in with survives the trip; `portals.js` computes the difference and this has no idea which walls were involved. The `_syncCamera()` is not optional: the camera would otherwise be raycast from the old position for a frame (see the matrixWorld invariant).
  - **`_jump()` owns Y and nothing else does.** `velocityY` is the only piece of motion state carried between frames — walking is positional, with no acceleration or inertia — and `_clampToArena()` deliberately touches X/Z only, since there's no ceiling. `PLAYER.eyeHeight` doubles as the ground.
    - **Grounded is a height test, not a flag.** The floor is flat and at a known height, so there's no landing event to detect and no second piece of state that can drift out of step with the position. The early return while resting is what stops gravity accumulating a growing downward velocity while standing still — harmless against the landing snap, but it would fire the player through the floor the first time that snap was loosened.
    - **The launch reads `isDown('Space')` — the *held* key — and not the press edge, which is what makes holding Space bounce.** The question is asked again on every grounded frame, so a key still down at touchdown launches on that frame. It also means a press is never banked: a tap that goes down and back up while airborne is gone by the landing and does nothing, which is deliberate — a queued jump fires from input the player has already let go of. Double-jumping stays impossible for the reason it always was, that the launch needs `grounded` and nothing reads the key anywhere else.
      - **`isDown()` in a frame loop is normally the bug** (see `input.js`: one tap reads true sixty times), and it's safe here *only* because `grounded` gates it — the launch takes the player off the floor, so the repeat rate is the arc and not the frame rate. That gate is the whole argument for using held state here; don't copy the pattern to something ungated.
      - The cost is that a tap has to outlive a frame to exist at all, since the state is polled once per `update()`. Irrelevant to a human hand (~100ms), but it's why the jump driver's `tap()` helper holds for three frames and why it has to dispatch `keyup` — a driver that only ever sent `keydown` would leave the key down for the rest of the run.
    - **Jumping is not a dodge, and that's structural.** `enemies.js` measures steering and contact on the XZ plane only, so height buys nothing defensively at any `jumpSpeed`. Nothing needs to enforce it — but making that distance check 3D would silently turn jump into invulnerability, which is why the jump driver asserts a hit still lands mid-air.
    - `PLAYER.jumpSpeed`/`gravity` fully determine the arc: apex `jumpSpeed² / (2 * gravity)`, airtime `2 * jumpSpeed / gravity`. `eyeHeight` plus that apex has to stay under `WORLD.wallHeight` or a jump sees out over the arena — a balance constraint noted in `config.js`, not a clamp in code, same as the uncapped `speedStep` ladder.
  - **`player.js` owns the SUPER BOOTS buff, and it is three fields and a getter.** `boostTime` counts down in `update()` (so it pauses with the game, for free, because main.js only calls `update()` while running), `boostMultiplier` is what it multiplies, and `boostDuration` is what the timer started at — kept *only* so `hud.updateBoost()` can draw a fraction without the HUD needing a config import. `boostScale` is a getter returning the multiplier while the timer runs and `1` otherwise, which is what lets both call sites read one number and have no idea a buff exists.
    - **The numbers arrive through `boost(multiplier, duration)` rather than being read off `PICKUP.boots` here.** `player.js` has no business importing the drop config — main.js's `onCollect` already knows which face it got, so it passes them in. Same shape as `takeDamage(amount, source)`.
    - **It refreshes rather than stacks.** A second pair mid-buff resets the timer and doesn't multiply the multiplier — two pairs of boots aren't 9× speed, and a stacking timer would let a lucky round run indefinitely.
    - **`_jump()` applies the *square root* of it, and that asymmetry with `_move()` is the whole reason the config field is named `boost` and documented as height.** `velocityY = jumpSpeed * sqrt(boostScale)` triples the apex because the apex goes as the square of the launch velocity; `_move()` multiplies the step directly. Airtime therefore grows by √3 while height grows by 3, which is what the boots driver asserts as a pair — it's the only way to tell the root was taken in the launch rather than `gravity` being lowered.
    - **`reset()` zeroes `boostTime` and nothing else**, like armor and for the same reason: it's something the last run earned, so a new one starts without it. There's no need to restore `boostMultiplier`, since `boostScale` reads 1 off a dead timer regardless.
    - **There's no `onBoost` hook to match `onHeal`**, the same asymmetry armor has and for the same reason: the buff has one source, so main.js's `onCollect` raises the notice and the vignette at the one call site. A hook would be a seam with nothing on the other side of it.
  - **`player.js` holds two health pools, and `takeDamage()` is the only thing that knows they're ordered.** `armor` soaks first and only the remainder reaches `health`, so a 25-point hit against 10 AP spends those 10 and puts 15 on the bar — not one pool absorbing the whole thing. Health is floored at 0; armor needs no floor because it never absorbs more than it has. Nothing else in the game distinguishes the two: `enemies.js` and the boss both just call `takeDamage()`, and `isDead()` is still `health <= 0`.
    - **`onDamage`'s "only a real loss" guard is measured across *both* pools** (`health + armor` before against after), not against health alone. A hit soaked entirely by armor cost the player something real, so the sound and the wedge still have to fire — a guard on health would have gone silent for exactly the hits armor exists to take.
    - **Armor is filled only by `refillArmor()`, and `refillHealth()` deliberately doesn't touch it.** That's the spec — recoverable from an armor drop and nothing else — which is also why a boss dying tops health up and leaves AP where it was, and why `reset()` zeroes armor rather than filling it: a new run starts with whatever the last one earned, which is nothing.
    - **There is no `onArmor` hook to match `onHeal`, and that asymmetry is the rule working rather than an omission.** `onHeal` exists because *two* unrelated callers heal (a medkit and a boss going down) and neither should have to know the HUD exists. Armor has one source, so `main.js`'s `onCollect` raises the blue flash at the one call site — a hook would be a seam with nothing on the other side of it.
  - **`player.js` owns the two feedback hooks for health changing, and both exist because nothing else can see the change happen.** `onDamage(amount, source)` fires from `takeDamage()` — `enemies.js` calls that directly and main.js never sees it — and `onHeal()` fires from `refillHealth()`. `main.js` attaches the sound, the vignette and the hit indicator to them.
    - **`onHeal` hangs off `refillHealth()` rather than off the two things that call it, and that placement is the feature.** A medkit (`pickups.onCollect` in main.js) and a boss going down (`rounds.js`) have nothing in common except that method, so one line there covers both — and it's what lets `rounds.js` flash the HUD green while still having no DOM access and no HUD reference. Duplicating `hud.vignette('heal')` at both call sites is the easy wrong move.
    - **It reports unconditionally, where `onDamage` guards on health actually dropping.** A refill at full health is still something the player earned, and the `HP RESTORED` notice and the choir already fire there. `onDamage`'s guard is about one degenerate case — a hit landing on the death frame, over the top of `YOU DIED`.
    - **`source` is the attacker's live position vector, not a copy.** A floater is removed from the scene on the line after it lands its hit, so a handler has to read it synchronously — the same rule `hud.scorePopup`'s position argument follows, and the same rule the shot object's scratch vectors follow.
  - **`bearingTo(point)` is the seam between the player and the hit indicator.** An on-screen bearing is a screen-space angle, but deriving it needs `yaw` and `position`, so the angle is computed here and the drawing is `hud.js`'s. XZ-planar and **deliberately free of `pitch`** — looking up shouldn't swing the wedges, and flattening the camera's world direction instead (the obvious alternative) degenerates when looking straight up. It's the same rotation `minimap.js` applies, for the same reason it comes out clockwise-from-up; the sign is easy to talk yourself into, which is why the hit driver sweeps (yaw, bearing) pairs instead.
- **Pointer lock drives pause.** Locked means running; unlocked means paused. `running` is derived from the lock state via `input.onLockChange`, not tracked independently. Game over calls `document.exitPointerLock()`, and the overlay doubles as the pause and death screen.
- **Damage and heal feedback is wired in main.js off `player.onDamage` / `player.onHeal`**, the same shape as `enemies.onDefeat` and `pickups.onCollect`: the system reports, main.js decides what it means. `onDamage` plays the hit sound, flashes the red vignette, and turns the attacker's position into a bearing for the wedge. `onHeal` flashes the green one — and because it hangs off `refillHealth()` rather than off its callers, that one line covers both a medkit and a boss going down. The blue armor flash and the yellow boots one are the exceptions, raised from `pickups.onCollect` itself, because a drop is each one's only source. That handler is where the three faces are told apart at all: one `if` per face deciding between `refillHealth()`, `refillArmor()` and `player.boost()`, plus the notice text and the tint. Nothing else in the codebase branches on which drop it was.
- **Score flows weapon → main via callback.** `Weapon` takes an `onKill(score)` and doesn't own the tally; `EnemyManager.damage()` returns points earned and the weapon forwards them. Enemies and the weapon stay ignorant of the score.
- **Enemies share one geometry and one material** at module scope in `enemies.js`. At this fidelity per-enemy assets are pure waste. Iterate the enemy array backwards when removing mid-loop. The boss gets its own module-scope pair rather than a scaled-up floater — at radius 3 a 20-facet icosahedron reads as a few flat slabs, and the different hue is what makes it legible as a different tier of thing.
  - **Both tiers' bodies are `MeshBasicMaterial` — unlit — and that is the whole mechanism keeping one enemy's glow off its neighbours.** three has no per-object light masking: lights are gathered as `object.isLight && object.layers.test(camera.layers)`, so `light.layers` filters against the **camera**, not against the mesh. The only single-pass way for a body to be immune to the point light riding every enemy around it is for its material not to read lights at all. Without it a cluster lights each other's facets flat red while the one in the middle goes black, and it gets worse with every light added to `EFFECTS.glowPool` and every unit added to `ENEMY.glow.distance` — i.e. the failure grows with exactly the two numbers the glow was made more generous on. A two-pass render with camera layers was the alternative and was rejected: it breaks the additive halos' and sparks' sort against opaque geometry drawn in the other pass, doubles the draw calls, and contradicts the one-`render()`-per-frame arrangement main.js is built on.
    - **`shaded()` is what buys back the facet shading that costs, and it's a bake, not a shader.** Per facet, one grey written to all three of its vertices as a hemispheric dot product against `SHADE_DIR` (the world's key-light direction), consumed via `vertexColors: true` — which multiplies the material color, so the brightest facet lands near where a Lambert body's lit side read. Two things make it cheap and safe: `IcosahedronGeometry` is **non-indexed**, so every three vertices are one triangle and writing them the same value is what makes the shading flat (an indexed geometry would share vertices between facets and smear it — hence the `toNonIndexed()` guard); and the geometry is a convex polyhedron centred on the origin, so a facet's outward normal is just the direction of its centroid — no cross product, and therefore no winding order to get the sign of.
    - What's given up, on purpose: the pattern rides the mesh's tumble instead of staying put in the world, so a facet turning toward the key no longer brightens — invisible at a floater's ~30 screen pixels, and on the boss the silhouette and the portrait carry the read. `flatShading` is gone with the Lambert materials — the bake is flat by construction.
    - **Being unlit costs a body every *other* light too, and those are handed back by hand.** The muzzle flash going off in its face and the drop it's floating over are lights an enemy *should* read; only another enemy's glow isn't. So each enemy wears a **clone** of its tier's material and `effects.lightBodies()` writes a CPU-evaluated light term into that clone's color every frame (see `effects.js`). Three consequences worth knowing before touching this:
      - **The material is the one asset here that is deliberately not shared per tier**, because a per-enemy dynamic color has nowhere else to live — a shared material would paint the whole tier whatever the last enemy written got. `remove()` therefore has to `dispose()` it, or a run's worth piles up in the renderer's program cache; the geometry and both sprite materials are still shared and must not be touched.
      - **`enemy.bodyColor` is a *reference* to the tier template's color and is read-only.** It's the unlit base the light term is added to, so it costs nothing and can't drift from the template — but writing it would retint the entire tier.
      - The term is rebuilt from that base every frame rather than accumulated, which is what makes the call idempotent and makes a light going out put the body straight back.
  - **Every enemy carries `kind`, a pointer at the config block it was spawned from** (`ENEMY` or `BOSS`), and `update()` reads speed/radius/damage/spin off that rather than off an import. So a new per-enemy tunable has to be added to *both* blocks — one of them missing it is an `undefined` that silently means "0" or "NaN", not an error.
  - **Enemies spawn somewhere in a height band and *level out* to `kind.hoverHeight` as they close**, so a wave arrives at mixed heights instead of all on one plane. Two halves, and the second is what makes the first safe.
    - **The settle is a slope against the horizontal step, not a rate against `dt`.** `levelSlope` is frozen at spawn as `|y - hoverHeight| / spawnDistance` — vertical units to shed per horizontal unit travelled — and `update()` multiplies it by the same `step` that already carries `speedScale`. So the descent finishes on arrival at *any* round: a round-8 floater crosses the arena four times faster and comes down four times faster with it. A per-second rate would look identical in round 1 and leave enemies attacking from overhead in round 8, which is why the driver measures the same flight at two speed scales rather than reading `levelSlope` back.
  - **Both `takeDamage()` call sites pass the attacker's `mesh.position`** — the floater's contact death and the boss's cooldown hit — so the HUD can point at where the hit came from. Passed, not copied: `remove()` takes the mesh out of the scene on the very next line, so the hook reads it synchronously (see `player.js`).
    - **That convergence is what keeps the XZ-planar contact check honest.** `update()` steers and measures contact on the plane only (which is also why jumping isn't a dodge — see `player.js`), so something still 6 units overhead landing a hit would read as damage out of nowhere. Height is deliberately *not* part of the pursuit: enemies never dive at the camera. The one way to meet one before it has come down is to charge a fresh high spawn, and that's the player's doing. **Don't "fix" this by making the contact check 3D** — it would silently turn jump into invulnerability, which the jump driver asserts against.
    - `Math.sign(remaining)` handles both directions and the step is clamped to `Math.abs(remaining)`, so it stops exactly level rather than oscillating across the target on a long frame. The clamp is the only thing stopping a fast round from overshooting, and the driver checks both signs for it.
    - **The boss opts out by setting both ends of its band to its hover height**, which makes the settle a no-op for that tier — its entrance is staged, and a radius-3 orb arriving at a random altitude reads as a glitch rather than as variety. The fields are *present* rather than omitted, per the `kind` rule above: a missing one is a NaN, not an error. `config.js` holds the shared number in a module-local `const` so it isn't written three times.
  - **Every enemy carries a halo sprite from `_halo()`** — the aura burning around the body, the other half of the glow whose point light lives in `effects.js`. The light is what the enemy throws on the floor; the halo is what the enemy looks like. **Both read the same `kind.glow.color`**, which is the whole reason those fields live in one block: let them drift and the pair stops reading as one glow.
    - **What makes it a halo rather than a blob painted over the enemy is depth testing against the body it's centered on.** The near facets hide the middle of the quad, so all that's left is the overhang past the silhouette — which is why `haloScale` has to be over 1, and why the gradient in `HALO_TEXTURE` puts its brightness in the outer half. This is the opposite call from the boss portrait below, which turns depth testing *off*; the contrast is deliberate, and `depthWrite` is off on both so overlapping sprites don't punch holes in each other.
    - **The silhouette's edge lands at `1/haloScale` of the gradient's radius, so that ratio is what decides how the aura reads — not its world size.** Every glowing thing in the game therefore holds the same `haloScale` of 2.2 — both enemy tiers and `PICKUP` (see `BOSS.glow` in `config.js`): the boss shipped at a smaller one first, on the reasonable-sounding grounds that a multiple of a radius-3 body is already big, and ended up with a fainter aura than the floaters it towers over. A wider aura is *not* the fix for a weak one — past ~2.6 it stops belonging to the body and just tints the wall behind it. Opacity is.
    - The texture is one `CanvasTexture` built at import time, shared by both tiers, with the per-tier color as the sprite material's tint over white — asset-free for the same reason `sound.js` synthesizes its effects. One material per tier, like the shared geometry. **Those materials read `config.js` at import time**, unlike the light, which reads it per frame, so a driver retuning `glow.color` live moves the light and not the halo.
    - **The halo is parented first and the portrait second, and the order is load-bearing.** Both sit at the orb's centre, so they tie on depth and the transparent sort leaves them in scene-graph order; with the additive halo drawn second it paints over the face and washes the portrait purple. The rounds driver asserts the ordering.
  - **The boss's portrait is a `Sprite` parented to its orb**, built in `_portrait()` from the material on the `bosses.js` entry it was spawned with. A sprite because it billboards — the face turns toward the player with nothing per-frame driving it — and parented rather than tracked so it rides the orb and vanishes with it. The orb's cosmetic tumble can't spin it: a sprite takes only position and scale off its world matrix. It's added *before* the `updateMatrixWorld()` in `_add()`, which recurses.
    - **It is never a hit target, and `weapon.js`'s non-recursive `intersectObjects(TARGETS, false)` is what guarantees that.** Flip that flag and a shot to the face returns the sprite, which misses `damage()`'s `e.mesh === mesh` lookup — leaving the boss unkillable from the front, which is the only side you ever see. The rounds driver fires one shot dead into the portrait for exactly this, and the lighting driver does the same through a floater's halo — **every** enemy has a sprite over it now, so that flag stopped being a boss-only concern.
  - **`BOSS.spawnDistance` must stay below `arenaSize/2 - BOSS.radius`.** `_spawnPoint()` rejects bearings that land out of bounds; if the distance exceeds the limit then *every* bearing is out of bounds and it falls through to its center-ward fallback on every attempt, so the boss always arrives from the same spot.

- **`glow.js` holds the halo machinery, and it exists because two unrelated modules need the *same* texture.** `enemies.js` and `pickups.js` both put an aura on their meshes, and neither should import from the other — exporting `HALO_TEXTURE` from `enemies.js` would make the drop system depend on the enemy system for a canvas gradient. So the texture and the two tiny builders (`haloMaterial(glow)`, `haloSprite(material, diameter, haloScale)`) live here and both callers import down into them.
  - **One `CanvasTexture` for every halo in the game, built at import time**, with the per-thing color as the sprite material's tint over white — asset-free for the same reason `sound.js` synthesizes its effects. Five materials over it now (two enemy tiers, three pickup faces); the pickups driver asserts `pickupHalo.material.map === enemyHalo.material.map`, which is the single check that justifies this file.
  - **`haloMaterial()` takes a `glow` block, not a `kind`.** A `kind` is a whole enemy tier and a pickup face isn't one; the block (`{ color, intensity, distance, haloScale, haloOpacity }`) is the actual shared shape, and it's the same block `effects.js` reads the point light off. Materials are still **one per kind of thing**, like the shared geometry — and they read `config.js` at *import* time, unlike the light, which reads it per frame. A driver retuning `glow.color` live therefore moves the light and not the halo.
  - The rest of why a halo reads the way it does — depth testing against the body, `haloScale` over 1, brightness in the gradient's outer half — is under `enemies.js` above, since that's where the tuning constraints bite.

- **`pickups.js` owns drops, and it's one system for three items that are one cube with a different picture on it.** `PickupManager` holds the items, floats and spins them, expires them, and reports a collection out through `onCollect` — it does not know what being collected *means*. main.js decides that (`player.refillHealth()` / `player.refillArmor()` / `player.boost()`, `sound.itemPickup()`, `hud.notice()`), which is the same shape as `enemies.onDefeat`: the manager reports, main.js interprets. **The armor cube is what that promise was written against, and it cost what it said it would**: a `config.js` face, a branch in `onCollect`, and an icon to draw — no second manager, no type field, and nothing in this module that knows what either item does.
  - **The boots are the test of that promise against an item that isn't a resource, and this module came out unchanged apart from a third `ASSETS` entry and a line in `_rollFace()`.** Everything that makes them a *buff* lives in `player.js`, `hud.js` and main.js's `onCollect`. That's the boundary working: a drop is a cube with a picture and a `kind`, and what collecting one does was never this file's business.
  - **The drop roll hangs off `enemies.onDefeat`, and that hook is what gives it the right rules for free.** `onDefeat` fires only from `damage()` — never `remove()` (contact deaths) or `removeAll()` (round sweeps) — so a floater that suicides into the player and a field wiped between rounds leave nothing behind. You have to actually kill them, the same rule the score and the round count already follow. Don't move the roll to `remove()` to "catch every death"; that's the bug, not the fix.
  - **Every drop carries `kind`, pointing at the *face* it was made from — `PICKUP.health`, `PICKUP.armor` or `PICKUP.boots`, not the `PICKUP` block they share** — exactly as an enemy points at `ENEMY`/`BOSS`. That's what lets `effects.js` read a drop's glow through the same `item.kind.glow` path it reads an enemy's, with no branch for which it got, so `_assignGlows()` is one function over two arrays; it's what `minimap.js` compares to pick a glyph; and it's what `main.js` branches on to decide what collecting one means. A `type: 'armor'` string would have needed all three of those places to learn a vocabulary — and adding the boots touched none of them, which is the evidence for it.
  - **`_rollFace()` is the second roll, and health is its fall-through.** A cumulative walk over `PICKUP.armorShare` then `bootsShare`, returning `PICKUP.health` if neither hits — so there is no `healthShare` that could drift out of sum with the others. Adding a face is a share, a line here, and an `ASSETS` entry.
  - **The per-face three.js objects live in an `ASSETS` `Map` keyed by the face block**, built at import time — one `MeshLambertMaterial` over one generated `CanvasTexture` and one halo material per face, the same "one per kind of thing" rule the enemy tiers follow, with the halo *texture* still the single shared one from `glow.js`. A `Map` rather than fields hung on the config blocks, which would make `config.js` a place that holds three.js objects; built eagerly rather than on first drop because there are two of them and a decode landing mid-fight stutters.
    - `faceTexture(face, drawIcon)` is the shared half and `drawCross` / `drawShield` / `drawBoot` are the difference. The icon comes in as a **callback rather than a shape name in `config.js`**, because which marks make a cross or a shield is the drawing's business — which is the same split that leaves every glyph's proportions hardcoded in this file while their three colors live in config. Note `faceTexture()` draws into a plain 64×64 canvas with no translate, so where an icon sits inside that square is entirely the callback's business.
    - **`drawShield()`'s Bézier control point sits *above* the bottom edge, and that one number is the whole read of the icon.** A quadratic's end tangent points from the control at the endpoint, so a control level with the bottom corner brings both sides in horizontally and they meet in a flat curve — which at the ~50px this is seen at reads as a *cup*. Pulled up, they converge at about 45° and come to a point. The minimap blip draws the same construction a tenth the size and repeats the same pull for the same reason.
    - **`drawBoot()` is the expensive one, and everything in it is fighting a single failure: at ~50px a boot wants to read as a capital letter L.** Drawn the obvious way — a shaft over a foot with an instep curve between them — the silhouette is a rectangle with a notch out of one corner, which is *exactly* what an L is. Four things failed to fix it: a fatter shaft, a rounded toe, the instep dip, and a three-part collar/leg/sole width on its own. What finally worked is three properties together, all about making the leg unable to be a *stroke*:
      - It is narrower than both the collar above it and the sole below it — a width that steps out, in and out again can't be two bars of a letter. **But the steps have to be big.** At ~4px each they're invisible and the icon still reads as an L while the row profile is perfectly correct, which is how it shipped once.
      - It is **wider than it is tall**. An L needs something readable as a vertical bar, and a leg squatter than it is broad can't be one at any weight. That's what the deep collar band and the barely-past-halfway ankle buy.
      - The foot is a **mass bounded by curves**, not a bar: the heel rounds back up to the leg instead of stepping in at a right angle, so the sole is the only straight edge on it. A right-angled heel leaves the foot a bar of about the leg's own weight, and two bars of equal weight read as a letter however wide the collar above them is.
      - **None of this was visible to an assertion.** The row profile was correct at every stage, and the shape assertions that check it were *written against* a version that read wrong — one of them had to be loosened to let the fix in. This is the entire justification for photographing the three cubes side by side, and the reason the close-up stages them at one depth so nothing is clipped.
  - **Collection is an XZ-plane distance test, like enemy contact, and here it's load-bearing even standing still.** The cube hovers at `PICKUP.hoverHeight` 1 while the eye is at `PLAYER.eyeHeight` 1.7, so a 3D test against the same `PICKUP.radius + PLAYER.radius` reach would miss a drop the player is standing right next to — never mind mid-jump. Same reason jumping isn't a dodge; same warning against "fixing" it.
  - **The Y position is written outright every frame, not accumulated.** `hoverHeight + sin(phase + age * bobSpeed) * bobAmplitude`, off a per-drop random `phase` so a handful spawned together don't bob in lockstep. Accumulating would let a long life walk the item off its hover height, which is also the height the collection reach was chosen against.
  - **A drop is not in `weapon.js`'s `TARGETS` at all, so it neither stops a bullet nor can be shot.** That's by omission rather than by a guard, and it's the right call: the arena's `solids` are what bullets hit, and adding drops to either list would mean a medkit between you and a floater absorbed your shots. Don't "fix" the fact that you can shoot through one.
  - **The icon is a generated `CanvasTexture` on the cube, not a sprite.** A sprite billboards, which is right for a boss's face and wrong here: the cube *rotates*, and a face that stayed square to the camera while the body turned under it would destroy the read. Spin is `rotation.y` only for the same reason — a tumble hides the icon half the time.
  - **Drops expire (`PICKUP.life`), shrinking away over the last `shrinkTime`.** Not asked for, and a judgment call: at ~3.5 drops a round with no expiry the arena silently fills with medkits and the health bar stops mattering. The shrink is `mesh.scale`, which scales the halo for free through the parent's world matrix — a full-size aura around a vanishing cube would read as the item leaving its glow behind. The point light is the one part that doesn't follow, and it's gone within a frame.
  - **`pickups.update(dt)` sits between `weapon.update()` and the `player.isDead()` check, and both edges are deliberate.** After the weapon, so a drop rolled by a kill *this* frame is already bobbing at its hover height before it's ever drawn — spawned at the kill's raw X/Z, it would otherwise paint one frame unmoved. Before the death check, so walking onto a medkit on the same frame a floater lands its hit still saves you.
  - **`clear()` has exactly one caller, `restart()`.** Drops deliberately survive round changes — one left over at the end of a round is still there to use in the boss fight, which is the point of a drop you can save. That's also why `rounds.js` holds no reference to the manager: a round change must not be able to sweep the floor.

- **`portals.js` owns the two portals, and it is the only system that moves the player.** A pair of glowing squares mounted in two different walls, placed by `rounds.js` at the start of every round and ticked by main.js right after `player.update(dt)`. It has no DOM access; the only thing it reaches into is the player, and only through `player.teleport()`. It reports a traversal out through **`onTraverse`**, which main.js hangs `sound.teleport()` on — the same shape as `enemies.onDefeat` and `pickups.onCollect`: the system reports, main.js decides what it means, and this module learns nothing about audio. Nothing in the game holds a reference back to it except `rounds.js`, which asks for a placement and nothing else. `minimap.js` is handed `portals.portals` once a frame by main.js — the same arrangement the enemy and drop arrays have, and read-only for `center` and `wall.run`, so the radar is a viewer rather than a second owner.
  - **The `WALLS` table's `faceYaw` does double duty, and that's the one thing to understand before touching the turn.** For a wall with inward `normal`, `faceYaw = atan2(normal.x, normal.z)` is both the Y rotation that turns the portal's quads to face inward *and* the player's yaw while walking into that wall — both because a plane's front is local +Z and a camera at yaw Y looks along `(-sin Y, 0, -cos Y)`. So `turn = exit.faceYaw + π - entry.faceYaw` hands the player the difference between "walking into the entry wall" and "walking off the exit wall into the room", which is what preserves the heading they walked in with relative to the wall. The sign of that is exactly as easy to talk yourself into as the minimap's `ctx.rotate(player.yaw)`, and the driver sweeps all 12 ordered wall pairs rather than reasoning about it.
  - **Placement goes through `rounds._startRound()`, so a real round change, a `~` skip and a retry all get it** and nothing else can move them. The constructor places them once as well — that's about the gap between construction and the first render, not about the round.
  - **Exactly two, built once and moved, never rebuilt — and the reason is the lights.** Each portal carries one `PointLight`, added at construction and never added, removed or hidden again, because the scene's light count is compiled into every material's shader program (see `effects.js`). Two permanent portals satisfy that without needing `effects.js`'s pooling: there is nothing to reassign. They cost what any two lights cost under a software rasterizer — measured at **~5 ms/frame at 1280×800 and nothing at 480×300**, the same fill-rate finding `doomslop-lightcost.mjs` records, and enough that two frame-count-based assertions in other drivers had to be rewritten to sample on wall clock.
  - **The aura is a `Mesh`, not `glow.js`'s `haloSprite()`**, over the same shared `HALO_TEXTURE`. A sprite billboards, which is right for a body it surrounds and wrong for something mounted *on* a surface — a billboarding halo would swing off the wall as the player walked past. Both layers stand a couple of centimetres off the wall in the group's local frame to avoid z-fighting it, aura in front of core.
  - **A portal is not in `weapon.js`'s `TARGETS` and not in the arena's `solids`**, so shots pass through the square exactly as the player does. By omission rather than by a guard, the same call `pickups.js` makes.
  - **The square shows a perspective preview of the far side, and the whole of it is one matrix.** `_aimView()` puts a virtual camera at `exit.center + Ry(turn) · (camPos − entry.center)` facing `Ry(turn) · camFwd` — where `turn` is *the same angle* `player.teleport()` gets, because the view transform `exit.frame · Ry(π) · entry.frame⁻¹` collapses to exactly that. One derivation serves both, which is the point: the picture in the doorway and the place you come out cannot drift apart, and the driver ties them together over all 12 wall pairs rather than checking each against its own arithmetic. Since `Ry(turn)` maps `entry.normal` to `−exit.normal`, the virtual eye lands *behind* the exit wall at precisely the player's inset from the entry wall, at the player's own eye height — which is the geometry that makes it a hole rather than a camera feed.
    - **The core's UVs are screen-space (projective), not the quad's own.** `gl_FragCoord` over the drawing buffer, so the preview is sampled where the doorway *lands on screen* — which is what makes the view shift the opposite way as you walk past it. Mapped with the quad's UVs it would hold still and read as a television hung on the wall, and `-portalcheck.mjs`'s oblique pair is the only thing that shows the difference.
    - **The projection matrix is *copied* from the player's camera, not built.** The UVs above are only a window if the two frustums agree; a vcam with its own `fov`/`aspect` puts a subtly differently-scaled picture behind a correctly-placed hole.
    - **The targets are `HalfFloatType`, and that is not an upgrade — it's the difference between a picture and a flat panel.** The shell is dim on purpose (see `PORTAL.view.brightness`), so the whole preview lives inside a linear range of about 0.01, which an RGBA8 target quantizes to two byte levels. The precision is spent in the shader instead, where there's some left.
    - **The tint is mixed *after* `colorspace_fragment`, in display space, and both sides of the mix have to be converted.** Working-space math over a range that small loses most of the contrast the half-float target was chosen to keep; `linearToOutputTexel()` is applied to `uTint` as well, or the tint is a differently-encoded color being blended into an encoded picture. three emits that function for any non-raw material, so it can be called from an `onBeforeCompile` patch.
    - **The core is `ShaderMaterial` and **opaque**, and the aura is parented *first* so it draws *behind* it.** That ordering is the opposite of the enemy halo's and it's load-bearing: the aura is additive and 2.2× the doorway, so the core has to write depth to reject the middle of it — transparent, or not writing depth, and the aura paints over the window and the portal is a flat cyan panel again, which is exactly how the preview shipped the first time. Each portal gets **its own core material**, since each samples its own target; the aura material is still shared, like every other halo in the game.
    - **`renderViews()` is called from main.js immediately before `renderer.render()` and *outside* the running check**, alongside the glows and the minimap and for the same reason — the doorways keep showing the far side behind the pause overlay rather than going flat. It has to run *after* `player.update()`, or the preview is a frame behind the wall it's painted on, which reads as the window sliding as you walk. It restores the render target to the canvas on the way out.
    - **A portal outside the frustum is skipped, which is a real saving and not a micro-optimisation**: two extra renders cost ~3.9 ms/frame at `resolution` 0.5 under a software rasterizer, and the cost is per *fragment* (`-viewcost.mjs` measures it as near-exactly quadratic in `resolution`). Culled here rather than left to three, which would still run the whole render before discarding every object in it. The consequence a driver has to know: **a culled portal is not aimed, so it keeps its last matrix** — any assertion on a preview has to sentinel `vcam.matrixWorld` first or it can pass on stale state, and a target is only *resized* on a frame its portal is rendered.
    - **The preview is the seamless continuation, but the arrival is pushed `PORTAL.exitOffset` into the room**, which `exitOffset > depth` requires — so there's a slight pop on stepping through. Accepted: closing that gap means either a cooldown and travel state (which the offset exists to avoid) or letting the player ping-pong between the two squares.
  - **`createShell()` in `world.js` is what the previews render, and it is a separate `Scene` with no lights in it.** The walls-only copy the request asked for: a floor, the grid and four walls, all `MeshBasicMaterial`, carrying the arena's own fog and background so the doorway's picture recedes into the same haze the room does. Two reasons it's a second scene rather than the arena with things hidden — hiding meshes per render would fight the light-count rule above, and a lights-free scene compiles its materials against zero lights, which is most of why the two extra renders are affordable at all. It's built once at import time from `PORTAL.view.brightness`, which is **baked into the material colors** rather than read per frame, so a driver retuning it live has to scale the colors (`-viewtune.mjs` does).
  - **`_entering()` is an XZ-plane test with no height component**, like enemy contact and pickup collection. The visible consequence is that a portal takes at the top of a SUPER BOOTS hop, which reads as a doorway rather than a hoop to thread — and it's the same solid-rule-everywhere argument, so don't make this one 3D either.

- **`bosses.js` is the boss roster: an enum of the portraits in `assets/images/`, keyed by name.** The only module that imports an asset file. Each entry is `{ name, material }`, and the enum keys double as the displayed names so there's no second list to keep in step — add an image to `PORTRAITS` and that's the whole change.
  - **The `SpriteMaterial`s are built at import time, which is the point.** Reaching a boss takes `ROUNDS.killsPerRound` kills, so every texture is decoded long before one is needed and there's no lazy-load path to get wrong. One shared material per boss, same reasoning as the shared geometry in `enemies.js`.
  - **`depthTest: false` on those materials is load-bearing and arena-specific.** The sprite sits at the orb's center, where the near facets of a radius-3 icosahedron would hide nearly all of it. It's safe here only because the arena is one open box with nothing standing in it and floater spawning is off for the boss fight, so nothing can legitimately occlude a boss. Add cover to the level and this becomes wrong.
  - `randomBoss()` is a uniform pick with no memory, so the same boss can turn up twice running. At this roster size that's an occasional repeat, not something worth tracking state to avoid. Adding a face is an image in `assets/images/`, an import, and a line in `PORTRAITS` — plus the two drivers that pin the roster by hand (`-rounds.mjs`, `-pages.mjs`), which is the point of their hardcoding it.

- **`rounds.js` owns the phase machine, and it's the only module that knows what a "round" is.** `fighting → incoming → boss → breather → fighting`. It drives `EnemyManager` (wiping the field, gating spawns, summoning the boss) and reports announcements out through a callback, so it needs the manager but nothing needs it. It has no DOM access, like every other system here.
  - **Kills are tallied in `enemyDefeated()` but every phase change happens in `update()`.** The kill is reported from inside `EnemyManager.damage()`, so acting on it immediately would call `removeAll()`/`spawnBoss()` re-entrantly — mutating the enemy array from inside a method that's iterating it. Deferring to the next frame boundary is the cheap fix; don't "simplify" it back.
  - **`rounds.js` draws which boss is coming, and it does it at the field wipe rather than at the spawn a beat later** — because the `BOSS ROUND` flash is what names it, and that flash fires `ROUNDS.bossDelay` before the orb walks in. The pick is held in `rounds.bossIdentity` and handed to `enemies.spawnBoss()`, so the face on the orb is the name that was announced. `reset()` nulls it, or a retry would carry the dead run's boss into the next flash. `spawnBoss()` defaults the argument to a fresh `randomBoss()` so a bare call still works.
  - **`_startRound()` is also where the portals are re-placed**, which is why `Rounds` holds a `portals` and is the third gameplay system to take a constructor dependency it only calls one method on (after `enemies` and `player`). One line there covers a real round change, a skip and a retry, and the placement can't drift from the speed push beside it. **Deliberately not the same arrangement `pickups` has**: drops survive a round change, which is why `rounds.js` holds no reference to that manager at all, where portals *have* to move on one.
  - **`skip()` is the `~` cheat, and it's one implementation for all four phases.** It wipes and gates spawning unconditionally: from `fighting` that clears a live field, and from the other three it's a no-op on an already-empty arena. Two things it deliberately doesn't do, both of which existing boundaries hand over for free — **no score or kill credit**, because the sweep goes through `removeAll()`, which never fires `onDefeat`, so skipping past a live boss can't pay out its 5000; and **no heal**, because `refillHealth()` is the boss-death transition's payment for actually killing it, and a skip that healed would double as a medkit. It routes through `_startRound()` rather than repeating its two steps, so a skip can't drift from a real round start — skipping to round 5 and fighting round 1's floaters is exactly the drift that method exists to prevent. main.js reads the keypress and calls this; `input.js` never learns what `~` means.
  - **`rounds.js` formats its own readout strings** — `label` (`ROUND 3`, `ROUND 3 BOSS`) and `progress` (`KILLS 12/25`) — plus `speedLabel` (`ENEMY SPEED: 1.32x`) for the flash's second line, and `hud.update()` just writes them. `_pending` is therefore a `{ text, sub }` object rather than a string, and the flush passes both to `onAnnounce`. `progress` returns **null during the boss fight**, which the HUD treats as "hide the field": a frozen `25/25` sitting there looks like it's still counting. Because null is a real value, the HUD's change-cache for it starts as `undefined`, not null.
  - **Announcements are queued in `_pending` and flushed at the top of `update()`**, which main.js only calls while running. That's what keeps `reset()` from flashing `ROUND 1` behind the click-to-start overlay, and it's why the inter-round timers pause with the game.
  - **`removeAll()` vs `clear()` is load-bearing.** `clear()` also calls `reset()`, which zeroes `elapsed` — using it for the between-rounds wipe would restart the difficulty ramp every round and the game would never get harder. The round wipe uses `removeAll()`; only a player restart uses `clear()`.
  - **`onDefeat` fires only from `damage()`, never from `remove()` or `removeAll()`.** Contact deaths and between-round sweeps stay silent, so floaters suiciding into the player can't advance the round and a restart can't credit a kill for every enemy it swept. Same rule the score already follows: you have to actually kill them.
  - **`rounds.js` owns the per-round speed growth, and `EnemyManager` just holds the number.** `speedScale` is a getter over `1 + ROUNDS.speedStep * (round - 1)` — a step **added** to round 1's speed, not a rate compounded on the previous round, which is why the field is `speedStep` rather than `speedGrowth`; and derived from the round rather than accumulated in a field, so it can't drift out of step with it. `_startRound()` pushes it via `enemies.setSpeedScale()`. `EnemyManager.update()` multiplies `kind.speed` by it, which covers the boss for free since both tiers read speed off `kind`.
    - **The same multiplier scales the spawn *rate*, so `currentSpawnInterval()` divides by it** rather than scaling `ENEMY.spawnInterval` alone. Dividing the already-ramped interval moves both ends of the ramp together; scaling only the starting interval would flatten it against a fixed `spawnIntervalMin` and every late round would converge on the same pressure. Rate is the reciprocal of interval, so a 1.15× rate is a division, not a multiplication — the sign of that is easy to get backwards and the driver measures spawns per second rather than reading the interval.
    - **Push the scale *before* `setSpawning(true)`.** `setSpawning()` re-derives `spawnTimer` from `currentSpawnInterval()`, so the order is load-bearing in `rounds.reset()` — `_startRound()` first, then `setSpawning()`. Reversed, a retry after dying on round 7 opens with the dead run's compressed interval.
    - `EnemyManager.reset()` deliberately leaves `speedScale` alone. `rounds.reset()` is the only writer, and it runs right after `clear()` on a restart.
    - The ladder has no ceiling, so it eventually passes `PLAYER.moveSpeed` (round 6 for floaters, 10 for the boss at the shipped 0.5) and enemies stop being outrunnable; the spawn interval likewise shrinks past `spawnIntervalMin` with no floor under it. Both are balance calls to make in `config.js`, not bugs to fix in `enemies.js`.
  - **The boss dying refills the player to full**, via `player.refillHealth()` at the `boss → breather` transition. That's why `Rounds` takes a `player`: it's the second gameplay system to hold one and move health, after `EnemyManager`. Two placements that look equivalent and aren't — hanging it off `onDefeat` heals on every floater, and putting it in `reset()` is dead code, since a restart goes through `player.reset()`, which is already full health.
  - **The boss is not consumed on contact.** Floaters are removed when they touch the player; the boss sits on them and hits on an `attackInterval` cooldown instead. Removing it on touch would let a 50-shot enemy be beaten by walking into it, and with no cooldown it would land a hit every frame and erase a full health bar in a fraction of a second.
- **`hud.js` anchors two things to world points, both DOM, both through `_place()`:** the boss health bar and the floating `+points` score popups. `_place()` projects, converts NDC to CSS pixels, and returns false for anything behind the camera — `project()` mirrors x/y through the origin there and would put the element somewhere plausible-looking but wrong. Off to the sides needs no such check; it clips at the viewport edge. Keep both callers on that one helper rather than reimplementing the `z >= 1` rule.
  - **`#announce` is a wrapper, not the text.** It holds `#announce-title` (`ROUND 3`, `BOSS ROUND`) and `#announce-sub`, and the `flash` class plus the `opacity: 0` base live on the *wrapper* so both lines fade as one thing. The second line is in normal flow under the first rather than pinned to its own `top`, so the title's font size can change without re-deriving an offset. **`#announce-sub` carries two unrelated things** — the round's enemy speed (`ENEMY SPEED: 1.32x`) on a round flash, and the boss's name (`KYLE`) on `BOSS ROUND` — hence the generic id; it was `#announce-speed` before the bosses got names. `hud.announce(text, sub)` writes both children and empties the sub for any announcement that doesn't have one. **Anything reading the announcement out of the DOM must read `#announce-title`** — the wrapper's `textContent` concatenates both lines plus the whitespace between them, so it is never `''`.
  - **`#notice` (lower center) is `hud.notice(text, kind)`, and it is deliberately not a third argument to `announce()`.** `HP RESTORED`, `AP RESTORED` or `SUPER BOOTS` when a drop is taken, where `kind` (`'heal'` / `'armor'` / `'boots'`) doubles as the CSS class that tints it — exactly as `vignette()`'s argument does, so there's no mapping table here to keep in step with the stylesheet. It's tinted rather than left one color because the vignette going up with it is the item's color, and a green message under a blue flash reads as two unrelated events; the retrigger strips the tint with the `flash` class, so back-to-back drops of different kinds can't leave one message wearing the other's color. Two reasons they're separate: `#announce` owns the center of the screen and is *timed against* — `ROUNDS.bossDelay`/`roundDelay` have to stay longer than its 1.2s by hand — while nothing waits on this one, so its whole duration lives in `style.css` and it needs no config number at all. And they can be on screen together: a drop from the last kill of a round is collected while `ROUND 4` is still flashing, so one has to be above the crosshair and one below. Same remove-reflow-add retrigger as `announce()` and the muzzle flash.
  - **Score popups are pooled**, like everything in `effects.js` — a fixed set of divs built in `_buildPopups()` from `POPUP.pool`, with a kill on a full pool recycling the one closest to expiring. Kills come several a second, so creating and dropping DOM nodes per kill would give the GC steady work.
  - **`hud.updatePopups(dt)` must run after `weapon.update()` in the frame.** A popup spawned by a kill this frame is placed by that call; run it earlier and a fresh popup paints one frame at the top-left corner before jumping to the kill.
  - **The popup's rise and fade are driven in JS, not by a CSS animation**, so `POPUP.life` is the single source of truth. `#announce` does it the other way — its 1.2s is in `style.css` and `ROUNDS.bossDelay`/`roundDelay` have to be kept longer by hand. That coupling is tolerable for one number; don't add a second. The popup's *color and font* are still CSS, like the rest of the HUD.
  - The popup's number comes from `enemy.kind.scoreValue` via `enemies.onDefeat`, while the score tally comes from `damage()`'s **return value** forwarded through the weapon's `onKill`. Same number, two hooks — safe only because `damage()` has exactly one real caller. A second caller would make the popup and the readout disagree.
  - **`#vignette` and `#hitmarks` are the damage feedback, and `hud.vignette(kind)` / `hud.hitFrom(bearing)` are the whole interface.** Neither knows what hit the player; main.js works that out from `player.onDamage` / `player.onHeal`.
    - **`#vignette` is one element, one gradient and one keyframe serving all four colors.** The class (`damage` / `heal` / `armor` / `boots`) supplies a `--tint` custom property that the `radial-gradient()` reads, so red, green, blue and yellow can't drift into four different fades — they're the same event shape ("something about what you can do just changed, look at the readouts") pointing in different directions. It's **first inside `#hud`** — later siblings paint over earlier ones, so a full-screen tint has to sit under every readout, or it dims the numbers you read through it. Its duration lives in `style.css` like `#notice`'s, since nothing waits on it. `vignette()` strips *every* tint class before re-adding one: a heal landing inside a damage flash has to replace the red, not stack on it.
    - **A wedge is two nested divs, and the nesting is not decoration.** A CSS animation on `transform` overwrites an inline `transform`, so the bearing `rotate()` lives on a zero-size outer anchor pinned at the screen center and the keyframes live on the child. That also makes the child's `translateY` radial at every bearing for free, since it runs in the parent's already-rotated frame. `rotate()` takes radians and is clockwise for positive angles, which is exactly what `player.bearingTo()` returns — no conversion.
    - **The wedge pool is walked round-robin, not searched for a free slot like the popups'.** `hud.js` holds no lifetime for these — the CSS animation *is* the duration — so there's nothing to search on. `HITMARK.pool` is 6 because floaters arrive in a swarm and several can land in the same second.
  - **`#vitals` is the bottom-center stack, and it is deliberately no longer part of `#readout`.** Two permanent pairs — `#armorbar` over `#armor` above `#healthbar` over `#health` — plus `#boots` above them while the buff runs, because these are the readouts that change what the player should do next, and at 18px in the bottom-left corner health was being missed until the screen went red. Only the wrapper is positioned; everything inside it is in normal flow, so any label's font size is free to change without re-deriving an offset — the same arrangement `#announce-sub` has under `#announce-title`. It sits after `#muzzle` in the source so the flash glows behind the numbers rather than over them. Anything reading the HUD's layout has to know these are out of the `#readout` flex block — the rounds driver's field-order assertion had to be corrected for exactly that.
    - **Each bar is the *redundant* half of its pair on purpose**: a number has to be read, where a length is taken in by the eye that's already on the crosshair. Armor sits above health rather than beside it because it's the pool that gets spent first — the two read top-down in the order damage comes off them.
    - **`_vital(labelEl, fillEl, label, value, max)` is one helper for both pools, and the number and the fill are written together inside it**, off the caller's single change check (`if (health !== this._health)` / `if (armor !== this._armor)`). The two are views of one value and must not be able to disagree, which is also why neither tracks its own cache. A third pool would be a third call, not more code here.
    - The fraction is clamped to `[0, 1]` even though `takeDamage()` already floors both pools at 0: they're also written directly (`player.reset()`, the drivers), and CSS ignores a negative width outright, so a bar would sit at its last value on the death frame rather than emptying.
    - **`max` is passed in rather than read here, which is the one thing that keeps the armor bar off `PLAYER.maxHealth`.** A copy-pasted divisor is the natural bug in a second pair, and it would read as a bar that only ever fills halfway; the hitmarks driver asserts the armor fraction against `maxArmor` specifically for it.
    - **`hud.updateBoost(remaining, duration)` is the boots row, and it deliberately does *not* go through `_vital()`.** Three differences, each of which would have to become a parameter: the row is hidden entirely when the buff isn't running (a `SB 0` sitting there permanently is noise for a state the player is almost never in), the bar is a fraction of `duration` rather than of a config maximum, and the label steps in **whole seconds** while the bar drains continuously — `_vital()` writes a number and a width off one value precisely because they must not disagree, and here they must. Its change-cache is therefore two fields: whether the row is shown, and the last whole second written.
      - **`#bootsbar-fill` is deliberately outside the `transition: width 140ms linear` rule the other two fills carry.** A health bar moves in steps and the transition smooths them; this one is already moving every frame, and a transition on it makes the bar lag its own timer — the fill would still be draining after the buff has expired.
      - It's above the armor pair because the three read top-down in the order they stop mattering: a timer that's about to run out, then the pool that gets spent first, then the one that kills you.
    - Sizes and colors are `style.css` — nothing in the game reads them, the same split `HITMARK` and `POPUP` make. The two numbers it needs, `PLAYER.maxHealth` and `PLAYER.maxArmor`, are already tunables gameplay reads, so `hud.js` divides by them rather than gaining a config block of its own. **HP and AP are typographic twins there** (one shared rule for size, weight and tracking; only the color differs), so neither reads as a footnote to the other; the gap *between* the pairs is wider than the gap inside one, or four evenly spaced rows read as four unrelated readouts. Both fills carry a `transition`, and any driver measuring a bar has to wait it out.
  - **`#controls` (top left) is static text apart from one row.** `hud.updateMusic(enabled)` writes `#musicstate` — the action half of the `M` row — as `MUSIC ON` / `MUSIC OFF`, lit when on and dim with the rest of the panel when off. The state lives next to the key that changes it because the music starts off, so a player noticing the silence and a player hunting for the key are the same person, and because every other corner is occupied. It starts as `MUSIC --` in the markup for the reason `HP --` does: unwritten, it says so. Everything else in the panel is a literal. It's in the one corner nothing else occupies, which is the reason it can be absolutely positioned at a flat `top`/`left` with no coordination: the radar's `MINIMAP.size` and the readout's length both move things it isn't next to. It's a two-column grid so the actions line up against keys that run 1 to 5 characters, both columns left-aligned so the panel's left edge stays flush with the screen edge it's anchored to. **It's the only list of the controls anywhere.** The overlay used to repeat the movement keys in a second `<p>`; that's gone, so there's one copy to keep current. It stays drawn behind the pause overlay like the rest of the HUD, which is what lets it cover the start screen too — dim there, but legible. Note the removal left `hud.showOverlay()`'s `querySelector('p')` matching exactly one element, and re-adding a paragraph above the subtitle would silently turn it into the pause message.
  - **`#build` (bottom right) is the one HUD element `hud.js` doesn't own.** The build number is a literal in `index.html` — no JS reads or writes it, and it is deliberately not in `config.js` (tunables are numbers gameplay reads; nothing reads this) nor derived from `package.json`'s `version`, git, or a build timestamp. It's bumped by hand, so the value lives next to the element that shows it and changing it is a one-line HTML edit. The pages driver asserts the *shape* (`/^BUILD \d+\.\d+$/`), not the value, so bumping it doesn't break a test — but emptying the element, or "tidying" it into `hud.update()` and leaving it unwritten like `HP --`, still fails.
- **`effects.js` draws; `weapon.js` doesn't.** The weapon has no scene access — it reports `{ muzzle, endpoint, direction, hit }` through `onShot` and main.js turns that into tracers and sparks. Keep it that way; handing `Weapon` a scene reference is the easy wrong move.
  - The vectors in that shot object are **module-scope scratch**, overwritten on the next shot. Handlers must consume them synchronously, never retain them.
  - Everything in `effects.js` is preallocated: a fixed tracer pool and a particle pool with a contiguous `[0, live)` active prefix, dead particles swapped with the last live one so `drawRange` stays valid. Effects fire several times a second, so per-shot allocation would give the GC steady work during play.
  - Ray origin is the **eye** (so aim matches the crosshair exactly), but the tracer is drawn from an offset **muzzle**. These are deliberately different points.
  - **The arena is solid.** `createWorld` returns a `solids` array (floor + four walls) and `weapon.fire()` raycasts it in the *same* cast as the enemy hitboxes, so the nearest surface wins. Don't split this into two casts — an enemy behind a wall would become hittable through it. The floor grid is deliberately excluded from `solids`: it's `LineSegments` 1cm above the floor, and raycasting it would scatter sparks off invisible wires.
  - **`shot.hitEnemy` is what gates gameplay, not `shot.hit`.** Scenery stops bullets and throws sparks but deals no damage, awards no score, and must not flash the crosshair hitmarker — otherwise the marker fires on every shot and stops meaning anything.
  - `shot.normal` is the **world-space** surface normal, already flipped to face back toward the shooter. `face.normal` is object-local and enemies tumble, so it has to be run through a normal matrix; `_impactNormal()` does that and falls back to the reversed shot direction if a hit carries no face data.
  - **`WEAPON.muzzleOffset` is specified in screen space, not world units** — `screenX`/`screenY` are normalized device coords (`0,0` is the crosshair, `-1` is the bottom/left edge) and `forward` only sets depth. `weapon.fire()` converts them using the live `camera.fov`/`aspect`, so the muzzle holds its on-screen spot when the FOV or window changes. Expressing it as a world offset instead looks right at one FOV and drifts at every other.
  - That offset puts the muzzle ~1.3 units *below* the eye, which swings it under the floor past ~15° of downward pitch and lets the floor clip the start of the tracer. `muzzleOffset.minHeight` clamps world Y to stop that. Don't remove it without re-running the pitch sweep in the effects driver.
  - **`effects.js` also owns the scene's dynamic lights** — the red glow riding each enemy and the flash when the player shoots — for the same reason it owns the particles: they're pooled, and the pool has a harder constraint than the others.
    - **The light count in the scene must never change, and that is what makes the glows a fixed pool rather than one light per enemy.** Three bakes the number of lights into every material's shader program, so adding a light, removing one, *or setting `visible = false`* makes it rebuild all of them — and it would happen on every spawn and every kill. An unused slot therefore idles at `intensity = 0` and stays in the scene; `clear()` dims them rather than removing them. `EFFECTS.glowPool` is the budget, and the nearest `glowPool` enemies win it.
      - Nearest rather than first-come: the pool is smaller than a late round's field, and a distant enemy holding a light while one in the player's face has none is the single arrangement that would be obvious. The pick is redone every frame by insertion into a preallocated window, so it survives spawns and kills without allocating.
      - The cost is **fill rate**, not light count as such, and it is linear in the count: under swiftshader at 1280×800 a full field measures 48fps with the pool hidden, 36 with 7 lights and 29 with the shipped 13 (12 glows plus the flash), while at 480×300 all three are 145fps and the lights are free. That's a software rasterizer's per-fragment shading, i.e. the one thing a real GPU is built for — but it's also why the budget exists and why `glowPool` is the knob to turn if a machine struggles. `ENEMY.glow.distance` is *not* part of that cost: a cutoff is evaluated per fragment either way, so a wider reach lights more of the screen for nothing.
      - **The bodies are immune to all of it, and that's paid for elsewhere.** The lights land on the floor, the walls and the drops only — enemy bodies read no lights at all, since three can't mask a light against a mesh (see `enemies.js`). So the glow is a thing an enemy *throws*, never a thing that lights another enemy, and raising `glowPool` or `glow.distance` can't make a crowd wash each other out.
    - **`lightBodies(items)` is the other half of that, and it's the lighting the GPU can't do for us.** Being unlit costs a body the flash and the drops as well as its neighbours' glows, so those two are evaluated per enemy on the CPU and added to the body color the facet bake multiplies. Five things hold it together:
      - **`bodyLights` is `[flash, ...pickupGlows]` and deliberately *not* `glows`.** That one omission is the whole rule — the enemy pool is the only thing a body must not read. It's built once in the constructor, which is safe precisely because both pools are fixed for the life of the scene.
      - **`attenuation()` mirrors three's own point-light falloff on the CPU**, windowed cutoff and all, so a body brightens on the same schedule as the ground under it. A hand-rolled curve is what would make the pair read as a light *and* a tint rather than as one light.
      - **A gain exists because this term stands in for a per-fragment N·L that isn't there.** It's flat across the body — one color write, and at ~30 screen pixels there is no near side to light — so it can't be the candela the floor sees.
        - **There are two of them, `flashGain` and `dropGain`, and the loop picks between them on `light === this.flash`.** Not a uniformity the array could keep: a drop's candela was set against a floor one unit under it at inverse-square and the flash's against a whole room at decay 1.2, so one gain over both makes the drop term ~4× the flash's at the same distance. The term is also added in three's **linear** working space, where a floater's base is `(0.58, 0.08, 0.05)` — a green term of 0.6 doesn't tint that body, it replaces it, and a floater passing a health cube came out olive. `dropGain` is a quarter of `flashGain` for that reason, and the drop screenshot pair is the only thing that says so: every assertion passed at the olive value, because they predict from the config number they're checking.
      - **`max` is applied by scaling the sum back, not by clamping per channel.** Clamping shifts the hue as it bites, so a point-blank warm flash would reach white by way of losing its red first.
      - **It's called from inside `updateGlows()`, last, rather than from main.js**, because it reads the pickup lights that pass has just placed. That ordering isn't something a caller should be able to get wrong — it's the same question as the two assignments above it: who lights what.
      - **There are two glow pools, not one: `glowPool` for enemies and `pickupGlowPool` for drops.** Deliberately separate budgets rather than one shared nearest-wins window, because the two have opposite lifetimes — a drop lies on the floor for the whole of `PICKUP.life`, so on a shared pool a couple of them near the player would sit there holding lights that closing enemies need. That is exactly the arrangement nearest-wins exists to prevent, and it's why the pickups driver lights six crowding enemies and a distant drop in the same frame.
      - **`updateGlows(enemies, pickups, viewpoint)` is a dispatcher over `_assignGlows()`**, which runs the nearest-wins insertion for one array into one pool. It works on both because a drop carries `kind` pointing at a `PICKUP` *face* just as an enemy points at `ENEMY`/`BOSS`, so `item.kind.glow` is the only thing it reads — which is also why a green health cube, a blue armor cube and yellow boots need no branch anywhere in this file — there is no branch for which kind of thing it got. Two arrays rather than one concatenated, since joining them would allocate every frame.
    - **Glow color, intensity, and reach come off `kind`**, like speed and radius, so `ENEMY` and `BOSS` each carry a `glow` block and the boss's orb glows purple while floaters glow red. The boss's intensity is several times a floater's, and that part is geometry rather than taste: intensity is candela at 1/d², and nothing a radius-3 orb lights is nearer than 3 units where a floater's light works at 1.6.
    - **The glow lights the floor, not the enemy.** A point light at a mesh's center is inside it, and the arena renders front faces only, so what reads is the pool of colored light under each enemy. That is the effect, and it's also why intensity has to be read against `hoverHeight` — the numbers were chosen by looking, not derived.
    - `effects.updateGlows()` is called from main.js **outside** the `if (running)` check, alongside `minimap.draw()`, so the arena keeps its glows behind the pause overlay instead of going flat. It takes `enemies.enemies` raw for the same reason the minimap does: `hitboxes()` allocates.
    - The flash is **one light, not a pool** — `EFFECTS.muzzleFlash.life` is shorter than `WEAPON.fireInterval`, so two can't be alight at once and retriggering just restarts the decay. It gets the same **grace frame** as a tracer (`flashBorn`), because `update()` runs after the shot that armed it and the flash is shorter than a clamped worst-case frame. Its `decay` is deliberately below the physical 2: the muzzle sits ~0.4 units off the floor and is clamped nearly onto it when aiming down, where inverse-square is a blown-out spot at the barrel and nothing beyond it.

- **`sound.js` synthesizes every *effect*; `assets/audio/doom.mp3` is the one audio file.** Oscillators plus one shared noise buffer, via the Web Audio API — a deliberate match for the flat-color visuals. The music is the exception because a minute and a half of it isn't something oscillators produce; that's not licence to add samples for the effects.
  - **The `AudioContext` is built lazily, inside `resume()`.** Constructing one at import time leaves it suspended and logs an autoplay warning, and the drivers treat console warnings as failures. `resume()` is called from the overlay click, which is the one gesture every path (start, resume, retry) passes through.
  - `OscillatorNode`/`AudioBufferSourceNode` are single-use by spec — they can't be restarted, so each sound builds fresh ones. Unlike the effects pools, there is nothing poolable here; that is not an oversight.
  - **The music is a looped segment, and that's why it's an `AudioBufferSourceNode` rather than an `<audio>` element.** `loopStart`/`loopEnd` are sample-accurate and gapless; seeking an element from a `timeupdate` handler is quantized to ~250ms and audibly stutters at the seam. The cost is decoding the whole 2.4MB file on one click, once. `src.start(t, loopStart)` also offsets the *first* pass, so the trimmed lead-in never plays at all.
    - A `loopEnd` past the end of the buffer is **not an error** — the spec treats it as the buffer's end — so an over-long window's symptom is the loop running long, not a failure. `_startMusic()` clamps it and the sound driver asserts the clamp didn't fire.
  - **The music is off by default and `M` is the only thing that starts or stops it.** `SOUND.music.enabled` is the *default*, not the live state — `sound.musicEnabled` is the flag, `toggleMusic()` flips it, and nothing writes back to config. So the start click is silent, and the mp3 isn't even fetched until the player asks: the pages driver's music assertion therefore hangs off the toggle, not off the click. main.js reads the press edge and calls `toggleMusic()`, the same shape as the `~` skip — `input.js` never learns what `M` means, and `hud.js` only reports the state main.js hands it.
    - **Turning it on always starts at `loopStart`, and that's structural rather than a choice.** An `AudioBufferSourceNode` has no pause and a stopped one is spent, so "off" leaves a dead node and "on" builds a fresh one — there is nothing to resume *from*. The music driver reads the offset off the `start()` call rather than trusting a flag, since a build that resumed mid-track would pass every other check.
    - **It still plays through pause, round changes, death and retry, and that half is unchanged: nothing else in the codebase can reach the source.** There is no stop, no restart and no seek on any *reset* path — `restart()`, `rounds.reset()`, `player.reset()` and the pause don't touch it, and pausing only stops main.js's frame loop, which the `AudioContext`'s own clock doesn't depend on. The toggle is a deliberate exception, not permission to add audio teardown elsewhere; both drivers still assert every one of those paths keeps the same source object.
    - **The decoded buffer is cached in `musicBuffer` and deliberately survives a stop.** It's the expensive part (2.4MB, a few hundred ms), any number of sources can share it, and a toggle mid-fight can't afford to hit the network — the driver asserts one mp3 request across several on/off cycles and a sub-400ms return.
    - **The guard is set before the `await`, not after.** Two clicks in quick succession both land while the decode is in flight, and the second source wouldn't replace the first — a single-use node means it would start a second copy of the track playing over the top of it.
      - **`_musicGen` is the same problem one layer out, and it's what the toggle added.** The `_musicStarted` guard covers start-then-start; a start *then a stop* while the decode is in flight would otherwise land a source the player has already switched off — and since a spent node can't be reused, the next start would play over the top of it. Every start and every stop bumps the generation, and the `.then` only builds a node if its own generation is still current. Only reachable on the *first* toggle (after that the buffer is cached and the promise is already resolved), which is why the music driver tests it on a fresh page.
  - **The music has its own gain node straight to the destination, not through `master`.** Two reasons: `masterVolume` is headroom for several *effects* stacking, which one sustained bed doesn't participate in; and the sound driver taps `master` to measure whether each effect generates signal, which music underneath would swamp. So `SOUND.music.gain` is an **absolute** level and has to be read against an effect's *effective* peak (`masterVolume` × that effect's gain), not against the other gains in the block.
  - **`_voice()` is the counterpart to `_tone()`, and the pickup choir is the only caller.** It's `itemPickup()`, not a sound per item: all three drops are the same event ("you picked something up") and the vignette, the notice and the readouts already say which — a second chord would be a fourth thing saying it, and the generic name is why the boots didn't invite one. `_tone()` is percussive: it opens at full level and sweeps down. `_voice()` holds a pitch and *fades in* — a linear attack from an epsilon, then an exponential release — which is what makes a sine sound like a voice rather than a blip. The choir is `SOUND.pickup.ratios` (a major triad plus the octave) sounded as **detuned pairs**: two oscillators ±`detune` cents apart beat against each other, which is the cheapest thing that reads as a section rather than one singer. `stagger` brings them in low-to-high so the chord blooms upward.
    - `gain` in that block is **per voice**, not for the chord — eight of them sound at once, so the effective ceiling is `masterVolume × gain × 8`. It's the one place `masterVolume`'s headroom is actually spent, and it's why the sound driver gives the choir its own clipping check.
    - The exponential release means the tail is ~-26dB by 70% of `duration`. That's by design (it's a short sound, as asked), and it's why the driver asserts the *shape* of the decay rather than a level late in it.
  - **`teleport()` is the third synthesis pair in the file — `_swoop()` and `_airSweep()` — and it's built the same way `itemPickup()` is: a tonal layer in detuned pairs over a noise layer.** Two `_swoop()`s at ±`detune` cents plus one `_airSweep()`, all on the same swelling envelope, which is what makes it read as a machine winding up rather than as a zap. It's the **second** effect in the game that swells instead of striking (the choir is the other), so it shares `_voice()`'s envelope shape — `setValueAtTime(0.0001)`, a linear ramp to `gain` over `attack`, then an exponential release — and deliberately not `_tone()`'s, which opens at full level and decays.
    - **`_swoop()` is a triangle, not a sawtooth**, which is the non-obvious call: a saw is the more obvious choice for machinery, but this climbs nearly three octaves and lands at 1.5kHz, where a saw's harmonic stack is simply shrill. The grit it would have contributed is already coming from `_airSweep()` underneath, where a bandpass can shape it.
    - **`_airSweep()` differs from `_noiseBurst()` in every part, which is why it's a second function rather than an argument.** Bandpass instead of lowpass so there's a *pitch* to track, a swept center frequency rather than a fixed cutoff, and the swelling envelope rather than a percussive one. A wide band (`noiseQ` ~1.4) is what keeps it a rush of air rather than a second whistle competing with the tone. It takes a random start offset into the shared noise buffer for the same reason `_noiseBurst()` does — walking back through a portal shouldn't replay an identical fragment of static.
    - **main.js hangs it on `portals.onTraverse`**, the same shape as every other effect's wiring: `portals.js` reports a traversal and has no idea it makes a sound.
  - **Damage feedback hangs off `player.onDamage`.** `enemies.js` calls `player.takeDamage()` directly and main.js never sees it, so without that hook there is nowhere to attach a hit sound. `takeDamage` only fires it when health actually drops, so a hit landing at 0 HP stays silent.
  - Death releases the pointer lock, which would otherwise fire the pause click on top of dying. `onLockChange` gates the click on `!gameOver` for that reason.

- **`minimap.js` is a 2D canvas, not three.js.** It's part of the HUD layer, drawn with the Canvas 2D API on its own `<canvas id="minimap">`; the scene never contains it and the WebGL renderer never touches it. Same reasoning as the rest of the HUD — cheaper and far easier to style than in-scene geometry. Consequently `MINIMAP` colors in `config.js` are **CSS strings**, not the `0x` literals everything else uses.
  - **The map rotates; the player doesn't.** The player sits pinned at the center pointing up and the world spins around them, so map-up is always straight ahead. That's why the view cone is drawn *fixed*, pointing up, rather than swung around by the yaw — swinging it would be the non-rotating (north-up) convention, and doing both at once is the classic way to get a radar that's subtly wrong.
  - The whole rotation is one `ctx.rotate(player.yaw)` before plotting enemies at their raw world `(dx, dz)` offsets. Positive `yaw` is the right amount in the right direction only because world `+X/+Z` map to canvas `+x/+y` and canvas rotation is clockwise; flipping either convention needs `-yaw`. Verify with the minimap driver rather than by reasoning — this sign is easy to talk yourself into.
  - Cone half-angle is the **horizontal** FOV, `atan(tan(vFov/2) * aspect)`, read from the live camera. `camera.fov` is vertical, so using it directly draws a cone narrower than what the player actually sees.
  - **The arena walls are drawn, and they're the only *static* thing on the canvas — which is what turns the circle from an arbitrary window into a position.** One `ctx.rect()` of side `WORLD.arenaSize` plotted at the player's own offset from it, inside the same single `ctx.rotate(player.yaw)` everything else uses. Being backed into a corner is now something the radar says, which it couldn't before: with nothing fixed on it, a player surrounded by three dots looked identical in the middle of the room and against a wall.
    - **A square has nothing to keep upright, so unlike a glyph it takes no counter-rotation** — it turns with the room, which is the whole point of drawing it. That makes the walls the one place on this canvas where the rotated frame is used as-is, and the reason the driver's wall assertions pair "lit at the arena distance on this bearing" with "dark on the opposite one": a box drawn centered on the map instead of at the player's distance from each wall looks entirely correct until you walk off center.
    - The whole box is stroked rather than clipped to the visible arc. The circular `ctx.clip()` already set for the frame handles the three quarters of it that are off the map, and working out which walls are in range would cost more than the one `rect()` call.
  - **The two portals are drawn as segments *over* their own stretch of wall, along that wall's run axis** — the cyan is a section of the outline rather than a mark stuck beside it, because a doorway is a hole in a wall and the map should say so. `portal.wall.run` is the wall's along-axis unit vector, so half of `PORTAL.size` either way off `portal.center` is the segment, and the map never asks which portal leads where: both ends are identical, which is what they are.
    - **This one gets no counter-rotation either, and for the opposite reason to the walls': a segment's *direction* is information.** Left upright it would lie across the wall it's set into at most headings. The driver asserts the bounding box rotates — 8×3px at yaw 0 against 3×8px at yaw 90 — which is deliberately the inverse of the assertion every glyph gets.
    - Drawn under the cone with the walls rather than with the blips, because it's part of the room and not a thing standing in it. `MINIMAP.portalColor` is `PORTAL.glow.color` in this file's CSS-string convention — see `config.js`.
  - **Drops are drawn too, as small upright glyphs rather than three more colors of dot** — a cross for health, a shield for armor, a boot for the boots. Both dots on the radar are things trying to kill you; the things on it that aren't shouldn't be told apart from them by hue alone. Each is the same symbol painted on its own cube, which is what ties a blip to the thing you walk over to collect.
    - **Which glyph is chosen in `_blip()` by comparing `item.kind` against the face blocks**, not by a shape name stored in one. How a shield is drawn belongs to the thing drawing it; `config.js` holds the color and the size. Health is the **fall-through** here for the same reason it's the fall-through in the drop roll, so a face added to `config.js` without a line in `_blip()` still draws *something*.
    - **Each glyph is counter-rotated by `-player.yaw` inside the rotated frame**, so it stays square to the screen while the map turns. The dots don't need this because a circle is rotation-invariant; a cross left in the rotated frame leans into an X at most headings, and a shield hangs sideways and stops reading as a shield at all. Positioning is still the one shared `ctx.rotate(player.yaw)` with raw world offsets plotted into it — that part is identical to the enemies' and is what the driver measures.
    - Drawn **under** the enemy dots on purpose: drops don't move, so one briefly covered costs nothing, where a closing threat hidden under a medkit is the arrangement that gets the player killed.
    - The cross is two arms as overlapping `fillRect`s rather than a stroked path — at a couple of pixels wide a `lineWidth` lands between device pixels and comes out grey. The shield and the boot are **filled** silhouettes for the mirror-image reason: at 6 pixels across an outline closes up into a smudge. Both are taller than they are wide, which is what separates them from the round dots at a glance before the color does, and the shield's two quadratics take the same above-the-edge control point `drawShield()` uses in `pickups.js` — level with the bottom, the sides meet in a flat curve and it reads as a cup.
    - **`_boot()` repeats `drawBoot()`'s whole construction** — bold collar flare, a leg squatter and narrower than both neighbours, a rounded heel — because that build is what stops it reading as a letter L at *any* size, and the trap is worse here. The one deliberate deviation is the aspect: the cube's icon is squat where this stays taller than wide, which it can afford because the collar and the sole carry the read on their own. See `drawBoot()` in `pickups.js` for why each part is load-bearing.
  - main.js passes `enemies.enemies` (the raw `{mesh, health}[]`), not `hitboxes()` — the latter allocates a new array via `.map()` and this runs every frame. `draw(player, enemies, pickups, portals)` takes the three arrays separately for the same reason `effects.updateGlows()` takes two: joining them would allocate here too, and all three are drawn differently anyway. The portal array is read for `center` and `wall.run` only.
  - `draw()` is called **outside** the `if (running)` check, alongside `hud.update()`, so the radar stays visible behind the pause overlay instead of going blank.
  - The circular mask is CSS `border-radius: 50%` *and* a `ctx.clip()` arc. Both, deliberately: the CSS handles the rim border, the clip keeps a dot near the rim from being drawn into the square's corners. Note that a clip region survives until `restore()`, hence the `save()`/`restore()` around the whole frame.

## The matrixWorld invariant (read this before touching hit detection)

`Raycaster` reads `object.matrixWorld` and **never refreshes it**, and three only recomputes world matrices inside `renderer.render()` — which runs *after* every system's `update()` in a frame. So anything that mutates a transform and is then raycast in the same frame must call `updateMatrixWorld()` itself.

Three places depend on this, and dropping any of them produces a silent aiming bug rather than an error:

- `Player._syncCamera()` — without it, `weapon.fire()` aims along the *previous* frame's rotation and aiming lags the mouse by a frame.
- `EnemyManager.update()` after moving each mesh — without it, shots test against last frame's enemy positions.
- `EnemyManager.spawn()` — most severe. A new mesh has an identity `matrixWorld`, so until the next render a raycast treats it as sitting at the **world origin**, not where it spawned.

If shots visibly pass through enemies, suspect a missing `updateMatrixWorld()` before suspecting the raycaster.

## three.js notes

- **Use `THREE.Timer`, not `THREE.Clock`.** Clock is deprecated in the pinned version and warns. Timer is exported from core; `timer.connect(document)` wires up the Page Visibility API so a backgrounded tab resumes with a sane delta. Call `timer.update()` once per frame before `getDelta()`.
- The per-frame delta is additionally clamped to `0.1s` so a GC pause can't tunnel anything through a wall.
- `require('three/package.json')` throws — three doesn't export it. Use `npm ls` to check the installed version.
- Graphics are intentionally minimal: flat colors, `MeshLambertMaterial`, no textures, no shadows. Match that when adding visuals.
- **A scene's light count is compiled into every material's shader program.** Changing it — adding a light, removing one, or hiding one with `visible = false` — makes three rebuild all of them. That's why the enemy glows are a fixed pool that dims to `intensity = 0` instead of a light per enemy; see `effects.js`. It's also why the two portal lights are built at construction and only ever *moved* — a fixed pair needs no pool, but it does have to be fixed. Point-light `intensity` is also candela falling off as 1/d² in the pinned version, so a glow's number only means anything read against how far its surfaces are.
- **There is no per-object light masking.** Lights are collected with `object.isLight && object.layers.test(camera.layers)`, so `light.layers` filters lights against the **camera** — it cannot exempt one mesh from one light. Making a material immune means making it not read lights at all (`MeshBasicMaterial`), which is what the enemy bodies do; the alternative is a second `render()` with a different camera layer, and that reorders every transparent/additive object against the opaque geometry. See `enemies.js`. The lights such a body *should* still read then have to be evaluated on the CPU and added to its color — `effects.lightBodies()`, which is the price of this limitation and the reason the falloff curve is mirrored in JS.
- **`PointsMaterial` uses `sizeAttenuation: false`** in `effects.js`, making `EFFECTS.particleSize` a **pixel** value rather than world units. With the default world-space attenuation, muzzle sparks spawning ~0.5 units from the camera rendered as screen-filling squares. Don't "fix" this back.
- `LineBasicMaterial.linewidth` is ignored by the WebGL renderer — tracers are always 1px. That suits the look, so there's nothing to work around.
- `PointsMaterial` has no per-particle alpha, so particle fade-out is done by scaling vertex color toward black under `AdditiveBlending`. That only reads as a fade against a dark background; it would look wrong on a light one.

## Conventions

Plain ES modules, no TypeScript, no JSX, no build step beyond Vite. The HUD is DOM on top of the canvas (`hud.js`, `minimap.js`, `style.css`), not drawn in the scene — cheaper and easier to style. Comments explain *why* a boundary exists, not what a line does; match that density.
